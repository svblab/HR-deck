# ANCHOR_CORE — базовые принципы проекта

Статус: действующий документ. Источник истины по требованиям — актуальная версия
`ТЗ_HR_uchet_dostupnosti.docx`. Этот файл операционализирует ТЗ для повседневной
разработки в Cursor. При расхождении ТЗ имеет приоритет; расхождение фиксируется
как задача на уточнение ТЗ, а не тихо обходится в коде.

Название проекта (рабочее): «Журнал доступности персонала».

---

## 1. Незыблемые архитектурные решения

Эти пункты нельзя менять в рамках обычной задачи. Изменение любого из них —
всегда отдельная ADR (см. `docs/adr/`), а не побочный эффект другой задачи.

| # | Решение | Источник в ТЗ |
|---|---|---|
| A1 | Целевая ОС — Linux, семейство Debian/Ubuntu. Windows/Wine/VM не поддерживаются. | Разд. 2.2 |
| A2 | Язык — Python 3. UI — PySide6 (Qt 6), нативное приложение, без браузера/веб-сервера. | Разд. 7 |
| A3 | БД — SQLite с шифрованием на уровне файла (SQLCipher или аналог). Один файл базы. | Разд. 7, 4.3 |
| A4 | Работа полностью офлайн. Никаких сетевых вызовов в обычном режиме работы. | Разд. 2.2, 9 |
| A5 | Один ноутбук, несколько учётных записей по очереди, не более одной активной сессии одновременно. Сетевой многопользовательский режим — вне рамок текущей версии. | Разд. 2.1, 9 |
| A6 | Три роли: Администратор, Сотрудник HR, Наблюдатель. Матрица прав — раздел 4.1 ТЗ, а не то, что покажется удобным по ходу разработки. Одновременно активен ровно один Администратор (см. ADR-0003). | Разд. 4.1 |
| A7 | Ключ шифрования БД не привязан к паролю рядового пользователя — отдельный мастер-ключ, доступный роли «Администратор», плюс резервный код восстановления, выдаваемый один раз. | Разд. 4.3 |
| A8 | Сотрудник идентифицируется внутренним ID, не ФИО. Все справочники (филиал/департамент/отдел/статус/должность/тип занятости) — тоже с внутренним ID, не текстовым значением как ключом. | Разд. 3.1 |
| A9 | История статусов и журнал действий пользователей — только добавление. Обычное удаление или редактирование задним числом через интерфейс не предусмотрено ни для истории статусов, ни для журнала действий. | Разд. 3.2, 4.6 |
| A10 | Модель шаблонов отчётов архитектурно отделена от бизнес-логики: новый шаблон подключается без изменения кода, если использует существующий механизм полей/маркеров. | Разд. 5, 3.8.2 |
| A11 | Структура БД версионируется; миграции не должны терять данные; неудачная миграция откатывается на резервную копию, а не оставляет базу в промежуточном состоянии. | Разд. 5, 11 |

## 2. Модель данных — обязательные свойства

- Каждая доменная сущность (сотрудник, филиал, департамент, отдел, должность, тип
  занятости, статус, шаблон отчёта, учётная запись) имеет собственный суррогатный
  ID. Внешние ключи ссылаются на ID, не на текстовое значение.
- Карточка сотрудника с первого дня содержит зарезервированные поля из раздела 3.1
  ТЗ (дата приёма, контакты, домашний адрес, номер социального/пенсионного
  страхования), даже если они скрыты в интерфейсе. Задача «включить поле X»
  должна решаться миграцией + пунктом интерфейса, а не проектированием схемы
  заново.
- Поля повышенной чувствительности (домашний адрес, номер социального/пенсионного
  страхования) при активации обязаны поддерживать: маскированное отображение по
  умолчанию, отдельное разрешение на просмотр полного значения (не равное праву
  роли «Сотрудник HR» автоматически), обязательную запись факта просмотра/правки
  в журнал действий. Эта возможность закладывается в модель доступа сейчас, даже
  если поля пока не включены.
- Любое изменение схемы — через миграцию с номером версии. Ручные ALTER TABLE
  вне механизма миграций запрещены.

## 3. Принцип работы со статусами (важно для логики, не только для UI)

Программа **фиксирует** факты, но не принимает кадровых решений за пользователя.
Практическое следствие для реализации:

- Автозакрытие предыдущего открытого периода при вводе нового статуса —
  техническая операция с датами, выполняется без подтверждения.
- Любая корректировка, которая меняет уже существующий период (ввод задним
  числом, пересечение периодов) — только через предложенный вариант +
  обязательное подтверждение пользователем. Никогда не выполняется автоматически
  и молча.
- После истечения срока статуса система не выбирает новый статус сама —
  сотрудник помечается «Требует уточнения статуса».

## 4. Безопасность — обязательные инварианты

- Без валидного пароля учётной записи — нет доступа к расшифрованным данным.
  Ни при каком состоянии ошибки это условие не должно смягчаться «для
  отладки» в продовой сборке.
- Пароли — только хэш с солью. Хранение пароля в открытом виде или обратимо
  зашифрованном виде — блокирующий баг, а не техдолг.
- Роль, не имеющая права на действие, не должна даже видеть соответствующий
  элемент управления как активный — сокрытие/дизейбл на уровне UI, а не только
  проверка на бэкенде (нужны обе).
- Каждое действие, изменяющее данные (сотрудники, статусы, справочники, шаблоны,
  учётные записи, бэкапы), обязано писать запись в журнал действий пользователей
  в той же транзакции, что и само изменение — не «допишем логирование потом».
- Учётные записи отключаются (`is_active=0`), не удаляются: публичного API
  удаления нет, строки `accounts` сохраняются для журнала действий и FK.

## 5. Структура репозитория (ориентир)

```
/src                 — исходный код приложения
  /domain            — модели, бизнес-правила (без Qt-зависимостей)
  /data              — доступ к БД, миграции, репозитории
  /services          — статусы, роли, шаблоны отчётов, импорт/экспорт, бэкап
  /ui                — экраны PySide6
  /reports           — стандартные отчёты и движок пользовательских шаблонов
    /migrations        — версии схемы БД (package data пакета data)
/tests
  /unit
  /integration
  /fixtures
/docs
  ANCHOR_CORE.md
  ANCHOR_PROTOCOL.md
  ROADMAP.md
  TESTING.md
  /adr
/templates_samples   — примеры Excel/PDF-шаблонов для документации (см. ТЗ 11)
/packaging           — сборка .deb, скрипты поставки
```

Точную структуру можно уточнять по ходу EPIC-001, но домены (domain/data/
services/ui/reports) не смешиваются — это прямое следствие требования ТЗ о
разделении бизнес-логики, работы с БД, отчётности и интерфейса (разд. 7).

## 6. Что явно вне рамок текущей версии

Не реализуем, пока не появится отдельная ADR/задача от заказчика:

- Сетевой/серверный многопользовательский режим.
- Интеграция с 1С и системами учёта рабочего времени.
- Более гибкая настройка прав внутри ролей (сейчас — три фиксированные роли).
- Поддержка произвольного PDF/Excel-файла без подготовки под механизм шаблонов.

Эти пункты — раздел 5 и 9 ТЗ («Требования к расширяемости» и «Ограничения»).
Архитектура должна не мешать им появиться позже, но реализовывать их сейчас —
скоуп-крип, а не выполнение текущего ТЗ.
