# ANCHOR_PROTOCOL — правила работы над проектом в Cursor

Этот документ описывает **как** мы работаем, а не что строим (что — см.
`ANCHOR_CORE.md` и ТЗ). Обязателен к прочтению перед первой задачей и после
любого изменения самого протокола.

---

## 0. Граница полномочий агентов (Agent Scope Boundary)

Раздел действует одинаково для Cursor, фоновых и автономных агентов и любой другой ИИ-модели, которая открывает оболочку или делает коммиты в этот репозиторий, независимо от способа запуска. При расхождении с остальными разделами настоящего документа действует §0.

0.1. **Остановка в точке согласования.** Агент не добавляет коммитов в ветки `epic/*` и `docs/*` после того, как документ-предложение этой ветки (или её последний коммит) сообщает «Awaiting human approval» или «Proposal only», либо ветка достигла контрольной точки diff-first (§5), смотря что наступит раньше, без явного разрешения мейнтейнера на каждый коммит в текущей сессии. Довод «задача казалась связанной» или «это небольшая правка» разрешением не является.

0.2. **Находка не даёт права на правку.** Если при проверке функции обнаружены ошибка, пробел или отсутствующая возможность интерфейса, агент не проектирует и не коммитит исправление в той же ветке или сессии. Агент останавливается, описывает находку простым языком (симптом, предполагаемая причина, предполагаемый объём исправления) и возвращает её человеку на разбор, даже если человек просил о другом, исправление выглядит очевидным или это «всего одна строка».

0.3. **Новая пользовательская возможность.** Изменение, вводящее пользовательскую возможность, которой нет в утверждённом человеком задании (например: удаление типа записи, у которого удаления не было; изменение поведения сессий или аутентификации; изменение правил видимости по правам), выходит за рамки текущей ветки или коммита в любом EPIC. Оно требует собственного EPIC и собственной ADR до реализации, а не после. Это правило действует сверх случаев, перечисленных в §4 настоящего документа и в разделах 1 и 6 `ANCHOR_CORE.md`.

0.4. **Инварианты.** Ослабление или обход существующего инварианта (например: переключение `PRAGMA foreign_keys` ради операции, которую схема иначе отвергает; удаление строк из таблицы только для добавления; отключение проверки вместо устранения причины её срабатывания) никогда не является допустимым исправлением само по себе. Если инвариант мешает законной потребности, это и есть находка по 0.2.

0.5. **Сводка коммита и описание PR.** Каждая сводка коммита и описание PR явно указывают, для какого EPIC или какой ветки они написаны, и подтверждают, что файлы вне этой области не затронуты. Если выход за область всё же произошёл, это указывается, а не опускается.

## 1. Роли участников

- **Cursor** — реализует задачи по EPIC/тикету, пишет код и тесты, коммитит и
  пушит в свою ветку, готовит PR с описанием.
- **Тимлид/ревьюер (человек)** — проверяет diff перед мержем в `master`,
  утверждает ADR, имеет право отклонить реализацию, даже если тесты зелёные, если
  нарушены принципы `ANCHOR_CORE.md`.
- `master` — защищённая ветка. Прямые пуши запрещены. Только через PR с
  прошедшими проверками.

## 2. Ветвление и именование

- Ветка на EPIC/задачу: `epic/EPIC-0NN-краткое-описание`,
  например `epic/EPIC-006-status-lifecycle`.
- Ветка на исправление бага вне эпика: `fix/краткое-описание`.
- Ветка на ADR-обсуждение (если нужен код-прототип для решения): `spike/тема`.
- Никаких долгоживущих личных веток. Ветка эпика мержится и закрывается по
  завершении эпика (не копится «на будущее»).

## 3. Коммиты

Формат (Conventional Commits, адаптированный):

```
<тип>(<EPIC-0NN>): краткое описание в повелительном наклонении

Тело коммита при необходимости — что и почему, не как (как видно из diff).
```

Типы: `feat`, `fix`, `test`, `refactor`, `docs`, `chore`, `migration`.

Примеры:
```
feat(EPIC-006): автозакрытие предыдущего открытого статуса
migration(EPIC-002): добавить резервные поля адреса и СНИЛС в employees
test(EPIC-011): проверка версии шаблона в сформированном отчёте
```

Коммиты, затрагивающие схему БД, **обязаны** быть отдельными от коммитов с
логикой UI — миграция должна читаться и ревьюиться отдельно.

## 4. Когда обязательна ADR

Cursor обязан остановиться и предложить ADR (не реализовывать сразу), если
задача:

1. Меняет схему БД способом, не описанным в существующей ADR или ТЗ дословно.
2. Меняет модель прав ролей (кто что может) относительно матрицы в разделе 4.1
   ТЗ.
3. Вводит новую зависимость/библиотеку, которой нет в разделе 7 ТЗ
   (технологический стек).
4. Меняет контракт механизма шаблонов отчётов (формат маркеров, способ привязки
   PDF-полей и т.п.) — это ломает совместимость с уже подготовленными заказчиком
   шаблонами.
5. Затрагивает модель шифрования, ключей или резервного восстановления пароля.
6. Любое отступление от «Незыблемых архитектурных решений» из `ANCHOR_CORE.md`.

Формат — файл `docs/adr/ADR-0NNN-краткое-название.md` по шаблону
`docs/adr/ADR-TEMPLATE.md`. Без утверждённой ADR реализация по пункту выше не
мержится в `master`.

## 5. Diff-first для больших изменений

Если изменение затрагивает файл более **300 строк** (после изменения) или
вводит новый файл длиннее 300 строк — Cursor сначала присылает на ревью diff/
предложение структуры **без полной реализации всех веток логики**, и ждёт
подтверждения перед тем, как достраивать оставшееся. Это касается в первую
очередь:

- миграций схемы БД,
- сервиса статусов (жизненный цикл + пересечения периодов),
- движка шаблонов отчётов,
- модуля разграничения прав.

Маленькие и средние файлы (< 300 строк) — обычный цикл «реализация → PR →
ревью».

## 6. Тесты — обязательное условие, не пожелание

- Ни один PR с кодом в `src/domain`, `src/services`, `src/data` не мержится без
  сопровождающих unit-тестов на новую или изменённую логику.
- Изменение в `src/reports` (стандартные отчёты и шаблоны) сопровождается хотя
  бы одним интеграционным тестом «параметры → сформированный файл».
- Миграция схемы сопровождается тестом «применяется на непустой тестовой базе
  без потери данных» (см. `TESTING.md`).
- Тесты — не «покрытие ради покрытия»: каждый тест должен быть трассируем к
  конкретному пункту раздела 11 ТЗ («Критерии приёмки») или к пункту
  `ANCHOR_CORE.md`. Тест без понятного «зачем» — сигнал пересмотреть тест, а не
  просто добавить его для количества.

## 7. Definition of Done для задачи внутри EPIC

Задача считается завершённой, когда выполнено всё:

- [ ] Код соответствует границам эпика (см. `ROADMAP.md`), не тянет куски
      другого эпика «заодно».
- [ ] Есть тесты, соответствующие правилу п.6, и они проходят локально.
- [ ] Если менялась схема БД — есть миграция с номером версии и тест на неё.
- [ ] Если действие изменяет данные — есть запись в журнал действий
      пользователей (п.4 `ANCHOR_CORE.md`).
- [ ] Если задача подпадала под п.4 (нужна ADR) — ADR существует и утверждена
      до, а не после реализации.
- [ ] `ANCHOR_CORE.md`/`ROADMAP.md` обновлены, если задача меняет что-то из
      зафиксированного там (например, закрывает пункт «вне рамок текущей
      версии»). Обновление **статуса или DoD** в `ROADMAP.md` — по
      [`ROADMAP_STATUS_VERIFICATION.md`](ROADMAP_STATUS_VERIFICATION.md)
      (проверка UI, тестов и `docs/manual/*` по `origin/master`, без
      необоснованных `[x]`).
- [ ] PR содержит: ссылку на EPIC/ТЗ-раздел, краткое описание решения, список
      затронутых миграций (если есть), чек-лист выше отмечен.

## 8. Порядок ревью

1. Cursor реализует задачу в своей ветке, пишет тесты, коммитит и пушит.
2. Cursor открывает PR по шаблону (см. `.github/PULL_REQUEST_TEMPLATE.md`).
3. Ревьюер проверяет: соответствие ТЗ, соответствие `ANCHOR_CORE.md`,
   осмысленность тестов, отсутствие побочных изменений вне скоупа задачи.
4. Правки — новыми коммитами в той же ветке, без force-push поверх уже
   отревьюенной истории, пока PR открыт (чтобы diff между итерациями оставался
   читаемым).
5. Мерж — squash в `master` с сообщением коммита в формате из п.3.

## 9. Работа с файлами примеров и чувствительными данными

- В репозитории не хранятся реальные ФИО, адреса, номера социального
  страхования и другие персональные данные — только синтетические тестовые
  данные (см. `tests/fixtures`).
- Примеры Excel/PDF-шаблонов для документации (`/templates_samples`) готовятся
  на вымышленной компании, без реальных логотипов/реквизитов заказчика, если
  заказчик явно не согласовал обратное отдельно.

## 10. Что делать при конфликте между ТЗ и удобной для разработки реализацией

Реализация подстраивается под ТЗ, не наоборот. Если пункт ТЗ кажется
избыточным, нереалистичным по срокам или противоречащим другому пункту —
это тема для отдельного обсуждения и, при необходимости, правки самого ТЗ
(как документа), а не тихого решения в коде «сделаем чуть иначе, так удобнее».

## 11. Git-координация Cursor / GitHub / LLM

Правила п.2–8 этого документа остаются авторитетными. Дополнительно, чтобы
Cursor, человек на GitHub и LLM-ревьюер не расходились в понимании «готово» /
«смержено», действует протокол Git-координации:

- человекочитаемый: [`CURSOR_GIT_COORDINATION.md`](CURSOR_GIT_COORDINATION.md);
- постоянное правило Cursor: [`.cursor/rules/git-coordination.mdc`](../.cursor/rules/git-coordination.mdc).

Ключевые инварианты (не дублируют п.2–8, а дополняют их):

- **`origin/master` — источник истины**, локальный `master` может отставать;
- три явных состояния задачи: **WORKING → PR READY → MERGED**;
- «PR ready» ≠ «merged»; merge верифицируется по **содержимому** в
  `origin/master`, особенно после squash;
- upstream `[gone]` **не** означает автоматически безопасное удаление ветки;
- деструктивные Git-операции и перезапись untracked — только с явного
  разрешения.

Принцип: **VERIFY → DIFF → ACT → VERIFY → REPORT**.
