# ROADMAP — дорожная карта проекта

Источник требований — `ТЗ_HR_uchet_dostupnosti.docx` (актуальная версия).
Каждый эпик ссылается на разделы ТЗ и на блок критериев приёмки (раздел 11
ТЗ), которым он закрывается. Порядок эпиков — рекомендуемый порядок
реализации с учётом зависимостей; внутри эпика задачи дробятся в трекере
(issues), сам эпик — не единица работы на один PR.

Общий принцип: **эпик не считается закрытым, пока не закрыты сопутствующие
пункты раздела 11 ТЗ**, а не когда «код вроде работает».

## EPIC-001 — Инициализация проекта и окружения

**Цель.** Готовый к разработке репозиторий: структура каталогов, сборка и
запуск пустого окна приложения на целевой Linux-системе, базовая CI-проверка
(линт + тесты), документы governance на месте.

**В скоупе**
- Структура репозитория по `ANCHOR_CORE.md` (domain/data/services/ui/reports).
- Скелет PySide6-приложения: полноэкранное окно, логотип-плейсхолдер, часы с
  датой, панель управления — как заглушки без бизнес-логики (эта часть уже
  есть в прототипе интерфейса — переносится в реальный код, не рисуется
  заново).
- Базовая настройка packaging (заготовка под .deb, см. EPIC-015 для полной
  реализации).
- CI: запуск тестов и линтера на каждый PR.
- ADR-0001, ADR-0002 в репозитории (перенесены из проработки ТЗ).

**Вне скоупа:** реальная бизнес-логика, БД, авторизация.

**Зависимости:** нет, стартовый эпик.

**DoD / трассировка на ТЗ:** раздел 11, блок «Безопасность и роли» (первый
пункт — установка и запуск на целевой Linux-системе), раздел 8.

## EPIC-002 — Модель данных и миграции

**Цель.** Схема БД, версионированные миграции, шифрование файла БД,
инфраструктура репозиториев данных.

**В скоупе**
- Таблицы: сотрудники (с зарезервированными полями — дата приёма, контакты,
  домашний адрес, номер соц./пенсионного страхования), филиалы, департаменты,
  отделы, должности, типы занятости, статусы, история статусов, учётные
  записи, роли, журнал технических событий, журнал действий пользователей,
  шаблоны отчётов и их версии.
- Все сущности — с суррогатным ID (см. `ANCHOR_CORE.md`, п.2).
- Механизм миграций с номерами версий, применяемый при старте программы.
- Шифрование БД на уровне файла (ADR-0002); проверка целостности при открытии.
- Тестовые фикстуры (синтетические данные) для дальнейших эпиков.

**Зависимости:** EPIC-001.

**DoD / трассировка на ТЗ:** раздел 3.1 (структура карточки), раздел 5
(версионирование и миграции без потери данных), раздел 11 блок «Данные и
надёжность».

## EPIC-003 — Учётные записи, роли и вход

**Цель.** Полный цикл аутентификации и авторизации: создание первого
Администратора, вход, роли, ограничение действий по ролям, автоблокировка,
защита от подбора пароля.

**В скоупе**
- Первичная настройка: создание учётной записи Администратора, генерация и
  показ (один раз) резервного кода восстановления с обязательным
  подтверждением сохранения.
- Вход по логину/паролю, хэш с солью.
- Три роли и матрица прав из раздела 4.1 ТЗ — как проверяемый, а не
  описательный артефакт (единый источник правил доступа в коде, не
  разбросанные по экранам проверки).
- Автоблокировка по бездействию (по умолчанию 15 минут, настраивается и
  отключается Администратором).
- Задержка после неудачных попыток входа (настраивается и отключается).
- Восстановление пароля Администратора через резервный код.
- Управление учётными записями (создание/роли/пароли) — доступно только
  Администратору.

**Зависимости:** EPIC-002.

**DoD / трассировка на ТЗ:** раздел 4.1, 4.2, 4.3; раздел 11 блок
«Безопасность и роли» целиком.

## EPIC-004 — Справочники и организационная структура

**Цель.** Филиалы, департаменты, отделы, должности, типы занятости —
редактируемые справочники с ID и архивированием.

**В скоупе**
- CRUD справочников (доступность действий — по роли).
- Каскадная связь филиал → департамент → отдел.
- Архивирование значения справочника: не предлагается для новых назначений,
  существующие связи и история сохраняются.
- Переименование значения справочника не рвёт связи (ID, не текст, — ключ).

**Зависимости:** EPIC-002, EPIC-003 (права на редактирование).

**DoD / трассировка на ТЗ:** раздел 3.1 (внутренние ID справочников), раздел
3.5, раздел 3.9 (архивирование справочников).

## EPIC-005 — Карточка сотрудника

**Цель.** Создание, просмотр, редактирование карточки сотрудника с
обязательными и зарезервированными полями.

**В скоупе**
- Форма карточки: ФИО, должность, филиал, департамент, отдел, тип занятости
  — обязательные; резервные поля скрыты, пока не активированы.
- Идентификация по внутреннему ID; корректная работа при совпадении ФИО
  разных сотрудников (различение по должности/подразделению/дате приёма в
  UI поиска).
- Инфраструктурная (не UI) готовность полей повышенной чувствительности
  (адрес, номер соц./пенсионного страхования) к будущей активации —
  маскирование и отдельное разрешение на просмотр закладываются в модель прав
  сейчас (см. `ANCHOR_CORE.md` п.2), даже если сами поля не включены в этом
  эпике.

**Зависимости:** EPIC-002, EPIC-004.

**DoD / трассировка на ТЗ:** раздел 3.1 целиком; раздел 11 блок
«Расширяемость и персональные данные».

**Срез сервиса:** PR #5 — `EmployeeService` / репозиторий, RBAC, аудит,
маскирование чувствительных полей. Форма карточки в #5 не поставлялась
(статус «✅» после #5 относился только к сервисному слою). UI-форма
закрывает оставшийся скоуп «Форма карточки» вместе с EPIC-008 (кнопка
«+ Добавить сотрудника»).

## EPIC-006 — Статусы доступности и история

**Цель.** Полный жизненный цикл статуса: назначение, автозакрытие
предыдущего периода, ввод задним числом и заранее, контроль пересечений,
неизменяемая история.

**В скоупе**
- Список статусов (В офисе / Удалённо / Командировка / Больничный / Отпуск /
  Отгул / Уволен-неактивен) как редактируемый справочник.
- Автозакрытие предыдущего открытого статуса при вводе нового с более поздней
  датой начала.
- Ввод статуса с будущей датой начала (плановый, не текущий, пока не
  наступит дата).
- Ввод статуса задним числом: предложенная корректировка соседних периодов +
  обязательное подтверждение (не автоматически и не молча — см.
  `ANCHOR_CORE.md` п.3).
- Проверка пересечения периодов перед сохранением.
- История статусов — только добавление; исправление ошибок — через
  подтверждаемую операцию, не уничтожающую факт истории.

**Зависимости:** EPIC-005.

**DoD / трассировка на ТЗ:** раздел 3.2 целиком; раздел 11, пункты про смену
статуса, автозакрытие, пересечения периодов.

**Примечание по рискам.** Это один из двух эпиков с наибольшей логической
сложностью (второй — EPIC-011). Подпадает под правило diff-first из
`ANCHOR_PROTOCOL.md` п.5.

**Срез сервиса:** PR #6 — `StatusHistoryService` / справочник статусов, RBAC,
аудит. **UI назначения периода** (диалог из popup/карточки) закрывает
оставшийся пользовательский скоуп «Карточка → назначить период».

## EPIC-008 — Главный экран: доска, таблица, поиск, фильтры

**Цель.** Наглядное отображение занятости — оба режима главного экрана,

**В скоупе**
- Режим «Доска» (колонки-статусы, карточки-сотрудники) и «Таблица»,

- Группировка списка/доски по филиалу или департаменту как альтернатива

- Всплывающая карточка сотрудника «на лету» из списка/доски.
- Кнопка «+ Добавить сотрудника» открывает форму карточки (UI EPIC-005);

**DoD / трассировка на ТЗ:** раздел 3.4, 3.5, 3.6; раздел 11, блок

**Примечание.** Визуальная логика уже провалидирована в интерактивном
HTML-прототипе (см. согласованные макеты) — переносится как референс
поведения, а не проектируется с нуля.

## EPIC-009 — Импорт и экспорт сотрудников

**Цель.** Перенос существующих Excel/CSV-списков в программу и обратный

## EPIC-011 — Механизм пользовательских Excel/PDF-шаблонов

**Цель.** Полноценный движок пользовательских шаблонов отчётов с фирменным
оформлением: загрузка, проверка, привязка данных, версии, права, аудит.

**В скоупе**
- Загрузка и валидация Excel/PDF-шаблона, сохранение исходного файла
  неизменным.
- Механизм маркеров/полей (`{{ФИО}}` и т.п.) и табличных областей
  (повторяющаяся строка).
- Формирование отчёта по Excel-шаблону с сохранением форматирования и
  формул, не затронутых заполнением.
- Формирование отчёта по PDF-шаблону через именованные поля формы или
  заранее определённые координатные области; отказ на этапе загрузки, если
  конкретный PDF не поддерживает подстановку.
- Параметры формирования и (где технически возможно) предварительный
  просмотр.
- Библиотека шаблонов: версии, архивирование/восстановление, привязка
  сформированных отчётов к конкретной версии шаблона.
- Права доступа к шаблонам по ролям (раздел 3.8.2.7 ТЗ).
- Аудит операций с шаблонами в журнале действий пользователей.
- Документация по подготовке шаблонов + минимум один рабочий пример Excel- и
  один PDF-шаблона (сдаётся вместе с эпиком, не откладывается «на потом»).

**Зависимости:** EPIC-002, EPIC-003, EPIC-005, EPIC-013 (журнал действий).

**DoD / трассировка на ТЗ:** раздел 3.8.2 целиком; раздел 11, блоки
«Пользовательские Excel/PDF-шаблоны» и «Документация по шаблонам».

**Примечание по рискам.** Самый крупный и самый рискованный эпик по объёму
неопределённости (поведение реальных PDF-файлов заказчика заранее не
известно). Дробится на подэпики/задачи по подпунктам 3.8.2.1–3.8.2.8 ТЗ.
Подпадает под diff-first (`ANCHOR_PROTOCOL.md` п.5). Контракт маркеров и
формат PDF-полей зафиксированы в **`docs/adr/ADR-0005-report-template-marker-contract.md`**
(Step 0); реализация движка — только после принятия ADR.

## EPIC-012 — Шифрование, резервное копирование и восстановление

**Цель.** Защита данных на уровне файла БД и надёжный цикл бэкапа.

**В скоупе**
- Шифрование БД по модели ADR-0002.
- Резервный код восстановления при первичной настройке.
- Создание резервной копии (Администратор, Сотрудник HR): выбор места,
  автоматическое имя, шифрование копии, проверка сразу после создания.
- Восстановление из резервной копии (только Администратор): предупреждение →
  бэкап текущей базы → подтверждение → проверка файла → восстановление →
  проверка целостности.
- Журнал технических событий (запуск/завершение, ошибки, бэкап/восстановление,
  сбои) — без записи паролей.
- Транзакционная запись, устойчивость к аварийному завершению, обнаружение
  повреждения БД при повторном запуске.

**Зависимости:** EPIC-002, EPIC-003.

**DoD / трассировка на ТЗ:** раздел 4.3, 4.4, 4.5; раздел 6; раздел 11,
блоки «Безопасность и роли», «Данные и надёжность».

## EPIC-017 — Разработка комплекта документации

**Цель.** Подготовить типовой комплект пользовательской/эксплуатационной
документации и рекламный буклет продукта. Это дополнительный поставочный
артефакт сверх обязательного минимума раздела 11 ТЗ («Документация»),
который уже закрыт в рамках EPIC-011 (инструкция по подготовке шаблонов и
примеры шаблонов).

**В скоупе**
- Руководство пользователя (для роли HR-специалист/наблюдатель): карточка
  сотрудника, статусы, главный экран, поиск/фильтры, импорт/экспорт,
  стандартные отчёты и пользовательские шаблоны, журнал действий (в объёме,
  доступном роли).
- Руководство администратора: учётные записи и роли, резервное копирование
  и восстановление, журнал действий, установка и обновление (со ссылкой на
  артефакты EPIC-015).
- Краткая инструкция по установке/обновлению — согласована с фактическим
  поведением пакета из EPIC-015, а не с ним самим не дублируется дословно.
- Краткая памятка/шпаргалка (1–2 страницы) для нового пользователя.
- Рекламный буклет продукта (маркетинговый артефакт для лиц, принимающих
  решение о внедрении — не для конечного пользователя): назначение продукта,
  ключевые возможности, применимость, отличия от учёта в Excel/на бумаге.
  Скриншоты — на синтетической тестовой компании (см. `ANCHOR_PROTOCOL.md`
  §9), реальные данные заказчика не используются.
- Формат исходников — Markdown в `docs/manual/` (руководства) и
  `docs/promo/` (буклет); при необходимости — скрипт сборки в PDF, если это
  можно сделать существующими зависимостями стека (`reportlab`), без
  добавления новых библиотек (иначе это п.4.3 ANCHOR_PROTOCOL.md — нужна
  ADR).

**Вне скоупа**
- Вёрстка/дизайн буклета в профессиональном инструменте (Figma/InDesign и
  т.п.) — вне возможностей Cursor как кодового агента; на этом этапе буклет
  — текстовый источник с чёткой структурой (заголовок, тезисы, призыв к
  действию), готовый к передаче дизайнеру, не финальный печатный макет.
- Перевод документации на другие языки.
- Видео-инструкции.

**Зависимости:** EPIC-005, EPIC-008, EPIC-009, EPIC-010, EPIC-011, EPIC-012,
EPIC-015 (документация описывает уже реализованный функционал и фактический
установочный пакет, а не планируемый).

**DoD / трассировка:** этот эпик **не соответствует конкретному пункту ТЗ**
раздела 11 — это дополнительный поставочный артефакт сверх обязательного
минимума. DoD определяется содержанием самого эпика выше (см. «В скоупе»),
а не ТЗ.

*Примечание о порядке.* EPIC-017 имеет номер выше EPIC-016, но в дорожной
карте расположен между EPIC-015 и EPIC-016: документация описывает

## EPIC-016 — Приёмочное тестирование и стабилизация

**Цель.** Финальная сверка со всем разделом 11 ТЗ, нагрузочная проверка на
объёме «несколько сотен сотрудников», устранение найденных дефектов.

**В скоупе**
- Прогон полного чек-листа раздела 11 ТЗ как приёмочных тестов (см.
  `TESTING.md`).
- Тестовая база на несколько сотен синтетических сотрудников; проверка
  отсутствия заметных задержек на поиске, карточке, смене статуса,
  стандартных отчётах и отчётах по шаблонам.
- Финальная проверка на сценарии «аварийное завершение — данные не
  потеряны», «неудачная миграция — откат на бэкап».
- Приёмка документации по шаблонам сторонним взглядом (не автором движка
  шаблонов) — годится ли она реально для подготовки нового шаблона без
  участия разработчика.

**Зависимости:** все предыдущие эпики; **EPIC-017 — обязательное условие
закрытия** (EPIC-016 не помечается завершённым, пока EPIC-017 не завершён).

**DoD / трассировка на ТЗ:** раздел 11 целиком, без исключений. Закрытие
эпика в таблице «Статус реализации» — только после завершения EPIC-017.
