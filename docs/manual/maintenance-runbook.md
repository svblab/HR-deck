# Runbook: обслуживание и восстановление

Пошаговые процедуры для администратора. How-to использования функций —
[`administrator-guide.md`](administrator-guide.md) §5.

Код: `services/backup.py`, `data/backup_io.py`, `services/upgrade.py`,
`services/bootstrap.py`.

---

## 1. Регулярное резервное копирование

**Рекомендация:** не реже **1 раза в неделю** и перед каждым обновлением `.deb`.

### Шаги

1. Войти как **Администратор**.
2. **⚙** → **Создать копию…**
3. Указать каталог (удобно: `~/.local/share/personnel-availability/backups/`).
4. Дождаться сообщения об успехе.

### Проверка копии

- В каталоге есть пара: `personnel-<timestamp>.db` и `personnel-<timestamp>.db.keywrap`.
- Опционально: **Восстановить** на тестовой машине (§2) или дождаться
  автоматической verify при создании (`BackupService.create_backup`).

### Где хранить

- Локальный диск **вне** каталога данных — OK для ноутбука HR.
- Для DR — второй носитель / сетевое хранилище (копировать **оба** файла).

## 2. Восстановление из резервной копии

### Когда применять

- Повреждение `personnel.db`.
- Ошибочные массовые изменения данных.
- Неудачное ручное вмешательство в файлы.

### Шаги

1. **Закройте** приложение на всех сеансах.
2. Войти как Администратор → **⚙** → **Восстановить…**
3. Выбрать файл `.db` **проверенной** копии (рядом должен быть `.keywrap`).
4. Прочитать предупреждение → **Да**.
5. Система автоматически:
   - создаст **pre-restore** копию текущего состояния в `backups/`;
   - заменит live db+keywrap атомарно (`swap_live_from_backup`);
   - проверит целостность открытием SQLCipher.
6. Убедитесь, что данные на месте (выборочно: сотрудники, последние записи журнала).

**Важно:** pre-restore копия позволяет откатить неудачное восстановление —
ищите файл `pre-restore-personnel-*.db` в `backups/`.

## 3. Повреждение БД при старте

Сообщение «Повреждение базы данных» — `prepare_database_startup`
(`data/backup_io.py`).

### Что приложение делает само

1. Удаляет **stale `.partial`** от прерванного atomic-copy.
2. Если restore прервался — пытается вернуть live из `.pre-restore.bak`
   (`recover_interrupted_restore`).

### Если ошибка остаётся

1. Запишите текст ошибки и размер файла `personnel.db`.
2. **Не** удаляйте `personnel.db.keywrap`.
3. Выполните **§2** из последней хорошей резервной копии.
4. Если копий нет — данные **не восстановить** без keywrap и валидного `.db`.

## 4. Потеря пароля / резервного кода Администратора

| Ситуация | Действие |
|---|---|
| Забыт пароль, **код есть** | Экран входа → **Восстановление по коду** → новый пароль + **новый код** |
| Забыт пароль, **кода нет** | **§2** — restore БД из бэкапа (пароли в keywrap бэкапа) |
| Потеряны **оба**, бэкапа нет** | **Восстановление невозможно.** Данные зашифрованы; brute-force keywrap не предусмотрен |

Не создавайте «второго администратора» обходом — инвариант одного активного
Администратора (`AccountManagementService`).

## 5. Сбой миграции при обновлении (EPIC-015)

### Автоматическое поведение

При входе после обновления пакета `UpgradeService`:

1. Создаёт `backups/pre-upgrade-personnel-<timestamp>.db` (+ keywrap).
2. Применяет миграции.
3. При **любой** ошибке — откатывает live из pre-upgrade бэкапа и закрывает
   приложение с сообщением.

### Проверка после отката

1. Снова войти в приложение.
2. Убедиться, что функции работают как **до** обновления.
3. В `technical_events` должны быть записи `upgrade.migrate` с
   `rollback success` (если откат сработал).
4. Pre-upgrade файл в `backups/` сохранён для анализа.
5. Сообщите разработчикам о сбое миграции; **не** удаляйте pre-upgrade бэкап
   до решения.

### Если автооткат не помог

1. Остановите приложение.
2. Вручную выполните **§2**, выбрав последний **ручной** бэкап или pre-upgrade файл.
3. Откатите пакет `.deb` на предыдущую версию при необходимости.
