# TESTING — стратегия тестирования

Тесты существуют для того, чтобы подтверждать конкретные пункты раздела 11
ТЗ («Критерии приёмки») и инварианты `ANCHOR_CORE.md`, а не для абстрактного
«покрытия». Каждый раздел ниже привязан к соответствующему блоку критериев.

## 1. Уровни тестирования

| Уровень | Что проверяет | Где живёт |
|---|---|---|
| Unit | Чистая бизнес-логика без Qt и без реальной БД: правила статусов, проверка пересечений периодов, расчёт «Требует уточнения», модель прав ролей, валидация полей карточки | `tests/unit` |
| Integration | Логика + реальная (тестовая) SQLite-база: миграции, репозитории, сценарии импорта, формирование стандартных отчётов и отчётов по шаблонам, журнал действий | `tests/integration` |
| UI/смоук (ручной или автоматизированный) | Ключевые пользовательские сценарии целиком: вход → карточка → смена статуса → отчёт | чек-лист ниже + при возможности автоматизация через Qt Test |
| Безопасность | Шифрование, попытки обхода ролей, восстановление по резервному коду | `tests/integration/security` |
| Производительность | Отклик на объёме нескольких сотен сотрудников | отдельный прогон перед релизом (EPIC-016) |

## 2. Матрица: критерии приёмки → тесты

### 2.1 Безопасность и роли

| Критерий (ТЗ, разд. 11) | Тип теста | Пример проверки |
|---|---|---|
| Без пароля данные недоступны | Integration | Открытие файла БД напрямую без ключа не даёт читаемых данных |
| БД хранится зашифрованной | Integration | Байты файла БД не содержат читаемых ФИО из фикстур |
| Резервный код восстановления работает | Integration | Сброс пароля администратора по коду → вход с новым паролем успешен; без кода — отказ |
| Три роли с разным набором действий | Unit + Integration | Для каждой роли — таблица «действие → ожидаемый результат (разрешено/запрещено)», прогоняется как параметризованный тест |
| Наблюдатель не может редактировать | Integration | Попытка вызова сервисного метода изменения сотрудника от имени роли Наблюдатель — исключение/отказ, не молчаливый no-op |
| Только Администратор управляет учётными записями и журналом | Integration | То же для соответствующих методов |

### 2.2 Журнал действий

| Критерий | Тип теста | Пример проверки |
|---|---|---|
| Каждое изменение данных фиксируется | Integration | После вызова сервиса изменения статуса — в журнале ровно одна новая запись с корректными учёткой/датой/типом |
| Запись журнала неизменяема | Unit | Repository-слой не предоставляет метод update/delete для журнала действий (проверка на уровне API, не только «не используем в UI») |
| Фильтры журнала работают | Integration | Фильтрация по пользователю/дате/типу/сотруднику/шаблону возвращает ожидаемое подмножество на фикстуре |
| Экспорт журнала в Excel | Integration | Сформированный файл открывается и содержит ожидаемые строки |

### 2.3 Стандартные отчёты

| Критерий | Тип теста | Пример проверки |
|---|---|---|
| 5 форм формируются корректно | Integration | На фикстуре с известным ожидаемым результатом — сравнение содержимого сформированного файла (не только «файл создан») |
| Экспорт в Excel и PDF | Integration | Оба формата открываются валидатором формата, PDF не пустой/не битый |
| Фильтры и параметры | Integration | Разные комбинации параметров дают разный, но предсказуемый результат |

### 2.4 Пользовательские Excel/PDF-шаблоны

| Критерий | Тип теста | Пример проверки |
|---|---|---|
| Загрузка и проверка шаблона | Integration | Валидный шаблон из `/templates_samples` загружается; намеренно некорректный — отклоняется с понятной ошибкой |
| Версии шаблонов | Integration | Новая версия не удаляет старую; отчёт, сформированный по старой версии, остаётся читаемым и привязанным к своей версии |
| Формирование отчёта по маркерам | Integration | Табличная область на N строк фикстуры даёт N строк в результате; одиночные маркеры подставлены верно |
| PDF-поля / координатные области | Integration | На заведомо неподдерживаемом PDF — отказ при загрузке, а не при формировании отчёта |
| Права доступа к шаблонам | Integration | Матрица ролей 3.8.2.7 — параметризованный тест, аналогично 2.1 |
| Аудит операций с шаблонами | Integration | Загрузка/версия/архивирование/формирование отчёта — каждое действие пишет запись в журнал действий с шаблоном и версией |

### 2.5 Документация по шаблонам

Не автоматизируется тестом в привычном смысле — приёмка вручную в EPIC-016:
человек, не писавший движок шаблонов, пробует подготовить новый шаблон только
по документации и рабочим примерам. Считается пройденным, если он справляется
без обращения к разработчику.

### 2.6 Расширяемость и персональные данные

| Критерий | Тип теста | Пример проверки |
|---|---|---|
| ФИО не уникальный идентификатор | Unit | Два сотрудника с одинаковым ФИО, разными ID — операции над каждым не задевают другого |
| Статус за 2 действия | UI/смоук | Ручная/автоматизированная проверка сценария «поиск → карточка» |
| Резервные поля адреса/СНИЛС существуют в схеме | Integration | Миграция создаёт колонки; тест читает схему БД и проверяет их наличие независимо от UI |
| Автозакрытие периода | Unit | Открытый статус + новый статус с более поздней датой → предыдущий закрыт корректной датой |
| Пересечения периодов через подтверждение | Unit + Integration | Попытка сохранить пересекающийся период без подтверждения — отказ; с подтверждением по предложенному варианту — сохраняется корректно |
| История неизменяема | Unit | Как для журнала действий (2.2) |
| «Требует уточнения» — весь цикл | Integration | Истечение даты без нового статуса → счётчик и список содержат сотрудника; после назначения нового статуса — не содержат |
| Архивирование и восстановление | Integration | Архивный сотрудник не в текущих списках/сводках; восстановление возвращает с полной историей |
| Доска/таблица/фильтры | UI/смоук | Ручной чек-лист по сценариям прототипа |
| Импорт/экспорт | Integration | Импорт фикстуры XLSX с намеренными дублями → предупреждение, не автосоздание; экспорт открывается и содержит ожидаемые строки |

### 2.7 Данные и надёжность

| Критерий | Тип теста | Пример проверки |
|---|---|---|
| Бэкап создаётся и проверяется | Integration | Создание копии → флаг проверки успешен → файл не пустой и расшифровывается |
| Восстановление из бэкапа | Integration | Восстановление на тестовой базе воспроизводит исходное состояние данных |
| Обновление не теряет данные/шаблоны | Integration | Прогон миграции N→N+1 на непустой фикстуре с шаблонами — данные и шаблоны на месте после |
| Неудачная миграция — откат | Integration | Намеренно ломаем миграцию в тестовом сценарии — база возвращается к состоянию до попытки, не к промежуточному |
| Аварийное завершение — без потери данных | Integration | Симуляция обрыва процесса посреди транзакции — при следующем запуске последняя завершённая транзакция сохранена, незавершённая — не оставляет мусора |
| Работа без интернета | Manual (разовая проверка) | Приложение запускается и работает с отключённой сетью |

### 2.8 Производительность

Прогоняется на синтетической базе ~300–500 сотрудников с реалистичным
распределением статусов/истории (генерируется скриптом в
`tests/fixtures/generate_perf_dataset.py`, создаётся в рамках EPIC-016):

- Поиск по ФИО, открытие карточки, смена статуса — без заметной задержки при
  ручной проверке (нет фиксированного норматива в мс в ТЗ — критерий
  качественный, «не должно ощущаться зависанием»; при появлении измеримых
  требований от заказчика — сюда добавляется числовой порог отдельной
  правкой ТЗ и этого документа).
- Формирование стандартного отчёта и отчёта по типовому шаблону — та же
  качественная проверка.

## 3. Тестовые данные

- Только синтетические данные (см. `ANCHOR_PROTOCOL.md`, п.9). Набор базовых
  фикстур — в `tests/fixtures`, переиспользуется между unit- и
  integration-тестами, чтобы не плодить разные «тестовые компании» в разных
  тестах.
- Отдельный расширенный набор для нагрузочной проверки — генерируется, не
  хранится в репозитории построчно.

## 4. Что блокирует мерж в `main`

- Красный unit- или integration-тест.
- Отсутствие теста для новой логики в `domain`/`services`/`data` (см.
  `ANCHOR_PROTOCOL.md`, п.6).
- Миграция без теста «применяется на непустой БД без потери данных».
- Изменение матрицы прав ролей без обновления параметризованного теста ролей
  (п. 2.1/2.4 этого документа).

## 5. Регресс перед релизом (EPIC-016)

Полный прогон:
1. Все unit- и integration-тесты.
2. Ручной/автоматизированный UI-чек-лист по ключевым сценариям (вход под
   каждой из трёх ролей, полный цикл статуса, стандартный отчёт, отчёт по
   пользовательскому шаблону, бэкап/восстановление, обновление версии на
   тестовой копии данных).
3. Нагрузочная проверка на объёме из раздела 2.8.
4. Сверка построчно с разделом 11 ТЗ — каждый пункт отмечается как
   подтверждённый тестом или явно как «проверено вручную, дата, кем».
