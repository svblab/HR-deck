# Раздел 0. О документе

## 0.1. Назначение

Настоящий документ (далее «ТЗ v2») определяет требования к программе учёта доступности персонала «HR-deck» (репозиторий `svblab/HR-deck`). Он заменяет документ «HR-desk_GRAND_PROMPT-M» от 04.10.2026 (далее «исходное ТЗ») и учитывает результаты эксплуатации прототипов, тестирования, пожелания заказчика и потребителей, а также принятые архитектурные решения (ADR).

ТЗ v2 описывает **что** должна делать программа и **какие ограничения** на неё накладываются. Как это реализуется в коде, определяют ADR и их адденды.

Правила изменения:

1. Раздел утверждается явной командой владельца («принято §N»). Утверждение фиксируется в журнале правок (0.9).
2. Утверждённый раздел меняется только новой записью в журнале правок с указанием причины. Молчаливых правок нет.
3. После выпуска версии 2.0 любое изменение даёт новую минорную версию (2.1, 2.2…).
4. Агенты не вносят правок в ТЗ v2. Обнаруженные противоречия и пробелы они описывают по правилу §0.2 `ANCHOR_PROTOCOL` (симптом, причина, объём) и возвращают человеку.

## 0.3. Иерархия источников истины

При расхождении побеждает источник, стоящий выше:

1. **ТЗ v2** (утверждённые разделы).
2. **ADR вместе с аддендами.** Принятый ADR, противоречащий ТЗ v2, подлежит адденду со ссылкой на раздел ТЗ v2, который его меняет. До выхода адденда действует ТЗ v2.
3. **Issue** репозитория.
4. **Код и тесты.** Расхождение кода с ТЗ v2 является дефектом либо основанием для изменения ТЗ v2 по правилам 0.2. Третьего варианта (код как неявный источник истины) нет.

Процессные и инвариантные документы `ANCHOR_PROTOCOL.md` и `ANCHOR_CORE.md` остаются в силе. Если ТЗ v2 меняет инвариант `ANCHOR_CORE`, это указывается явно в соответствующем разделе, и инвариант правится в том же цикле.

## 0.4. Порядок перехода от требования к реализации

ТЗ v2 не является разрешением на работу агента. Для каждого изменения действует цепочка:

**ТЗ v2 (утверждено) → ADR или адденд (принят человеком) → issue / EPIC → код → pull request → человеческий мерж.**

Новая пользовательская возможность, не входящая в утверждённое задание, требует собственного EPIC и ADR до реализации. Ограничения §0 `ANCHOR_PROTOCOL` (граница полномочий агентов) действуют без изменений.

## 0.5. Границы документа

В объём ТЗ v2 входят: роли и права, база данных и справочники, карточки сотрудников и архив, копии программы и привязка к оборудованию, резервное копирование, транспорт обмена пакетами, Журнал, интерфейс, отчёты, шаблоны, настройки, нефункциональные требования, персональные данные.

Не входят: руководства пользователя и администратора (пишутся после ADR), планы тестирования, процессные правила разработки.

Явно **не является** целью программы: передача данных по сети, ведение централизованной сущности человека, бухгалтерский учёт и прослеживаемость родословной записей.

## 0.6. Нормативная лексика и обозначения

- **«должна», «должен»** — обязательное требование.
- **«не должна», «запрещено»** — запрет.
- **«может»** — допустимое поведение, не обязательное.
- **«следует»** — рекомендация; отступление допустимо с обоснованием в ADR.

Ссылки на источники: «ИСХ §N» — исходное ТЗ, «ADR-NNNN» — решение, «#NNN» — issue. Номера вида «4.10.2» ссылаются на пункт 2 подраздела 4.10 настоящего документа.

## 0.7. Сквозные принципы

Принципы действуют во всех разделах. Раздел, нарушающий принцип, должен делать это явно.

| № | Принцип |
|---|---|
| П1 | Программа работает автономно: сеть не используется. Связь копий осуществляется файловым обменом пакетами. |
| П2 | Запись принадлежит филиалу. Филиал знает свои данные лучше любого другого. Копия экспортирует только записи своего филиала и никогда не ретранслирует чужие. |
| П3 | Карточки сотрудников не удаляются. Ошибочная запись уходит в архив. Допускается обезличивание данных карточки по правилам раздела 15. Восстановление из резервной копии (раздел 6) заменяет состояние данных целиком и не считается удалением карточки. Журнал и история транспорта не изменяются и не удаляются средствами программы. |
| П4 | Идентификация карточки происходит по `external_id`, а не по ФИО. Совпадение ФИО само по себе не доказывает совпадение человека. |
| П5 | Программа фиксирует факты и не принимает кадровых решений молча: там, где решение за человеком, она предупреждает или спрашивает (ANCHOR_CORE §3). |
| П6 | Некорректный или противоречивый пакет отклоняется целиком без частичного применения (всё или ничего). Применение пакета атомарно. |
| П7 | Каждая пара взаимодействующих копий имеет свой канал доверия. Данные не передаются через третью копию. |
| П8 | Защита базы данных рассчитана на неквалифицированного нарушителя (перенос файла на другой компьютер), а не на злоумышленника с физическим доступом и временем. |

## 0.8. Словарь терминов

**Структура и эксплуатация**

| Термин | Определение |
|---|---|
| Компания | Организация, использующая программу. Состоит из филиалов. |
| Филиал | Единица принадлежности записей. Создаётся только Администратором, только вручную, в справочнике филиалов. |
| Департамент, отдел | Первый и второй уровни структуры филиала (филиал → департамент → отдел); оба уровня необязательны. |
| Копия программы | Отдельная установка программы на одном компьютере со своей базой данных. В каждом филиале минимум две. |
| `installation_id` | Идентификатор копии. Создаётся при развёртывании, принадлежит транспорту, не относится к записям сотрудников. |
| Домашний филиал | Филиал, записи которого копия вправе изменять и экспортировать. Назначается Администратором для копии. |
| Свои записи / чужие записи | Свои принадлежат домашнему филиалу копии; чужие приходят импортом и доступны только для просмотра. |

**Идентичность и карточки**

| Термин | Определение |
|---|---|
| Карточка сотрудника | Запись о работе человека в конкретном филиале. |
| `id` | Локальный идентификатор записи внутри одной базы данных. Между копиями не сопоставляется. |
| `external_id` | Стабильный идентификатор карточки для обмена; назначается при создании, не меняется. Не является идентификатором человека. |
| Реплика | Та же карточка в другой копии программы. Опознаётся по `external_id`. |
| Связь идентичности | Подтверждённое человеком в данной копии соответствие входящей карточки локальной. Хранится локально парой ключей, `external_id` не меняет. |
| Классы сопоставления | EXACT (однозначное соответствие), NEW (новая карточка), LOW и AMBIGUOUS (требуют решения человека), CONFLICT (`external_id` совпал, а ФИО или филиал-владелец нет; пакет отклоняется целиком; исключение: обезличенная карточка, 4.10.2). |
| Архив | Хранилище карточек, исключённых из действующих. Карточка в архиве остаётся навсегда. |
| Вид занятости | Атрибут карточки. Архивирующие системные виды: «уволен», «переведён», «ошибочная запись». |
| Возможная двойная занятость | Совпадение нормализованного ФИО у действующих карточек разных филиалов. Предупреждение, не отказ. |
| Чувствительные поля | Домашний адрес и номер страхования. Доступны только HR. |
| Обезличивание | Необратимое стирание персональных данных внутри архивной карточки при сохранении самой карточки (15.7). |

**Справочники и статусы**

| Термин | Определение |
|---|---|
| Базовый набор | Системные записи справочников (статусы, виды занятости) с неизменяемым `code`, одинаковые во всех копиях. |
| Владелец записи справочника | Филиал, создавший дополнительную запись. Распространяет её как свои данные. |
| Модель «5+1» | Копия, связанная с N филиалами, хранит справочники всех N филиалов и собственный. |
| `code` | Неизменяемый код записи справочника. Ссылки в пакетах идут по паре «владелец плюс `code`». |
| Статус | Текущая доступность сотрудника. История статусов остаётся локальной. Текущий статус на дату — последний назначенный статус: статус с самой поздней датой начала среди статусов, начавшихся не позже этой даты; при равной дате начала назначенный позже. Если его дата окончания уже прошла, он остаётся текущим и считается просроченным (11.3.5). |
| Календарный статус | Статус с датой окончания (политика даты окончания не равна 0). |

**Обмен**

| Термин | Определение |
|---|---|
| Пакет | Зашифрованный файл обмена. Принимается только один раз. Содержит дату и время создания. |
| Временная копия пакета | Автоматически сохраняемая копия выпускаемого пакета, из которой файл записывается повторно после сбоя; удаляется сразу после записи файла (7.4.4). |
| Направление | Односторонняя связь «отправитель → получатель» между двумя копиями. |
| Ключи доверия | Публичные ключи абонентов. Управляются исключительно Администратором. |
| Последовательность, поколение | Номер пакета в направлении и номер цепочки ключей направления. |
| Инициализация направления | Повышение поколения и выпуск первого пакета нового поколения: всегда полного экспорта. Публичные ключи заново не обмениваются. Каждая инициализация начинает новое поколение ключей. На форме «Экспорт» это кнопка «Инициализация направления» (HR и Администратор), в том числе без PENDING (9.10.2, 7.8.4). |
| Режим инициализации | Состояние направления после ответа «Не подтверждено»: следующий пакет направления выпускается только как инициализация; снимается фиксацией пакета инициализации (7.6.4, 7.7.2). |
| PENDING | Пакет выпущен, решение оператора не принято, направление заморожено. Состояние есть только у отправителя. |
| CONFIRMED | Оператор подтвердил, что пакет получен и принят получателем. |
| «Заменено инициализацией» | Состояние неподтверждённого пакета после инициализации направления (прежнее CANCELLED). Запись сохраняется. |
| Полный и инкрементальный экспорт | Полный содержит все записи филиала; инкрементальный только изменённые после отметки экспорта. Для кнопки «Обычный экспорт» на форме «Экспорт» вид выбирает программа (7.4.5); пользователь вид не выбирает. |
| Полный экспорт без смены поколения | Пакет цепочки с очередной последовательностью, содержащий все текущие экспортируемые карточки домашнего филиала; поколение не меняется (7.4.6). На форме «Экспорт» это кнопка «Полный экспорт (без смены поколения)» (9.10.2). |
| Внешний импорт | Приём транспортного пакета. |
| Загрузка справочников из пакета | Настроечная операция Администратора в ненастроенной копии: загружает только справочники, пакет не принимается (5.3.3, 7.19.7). |
| Локальный импорт | Ввод неструктурированных данных (XLSX, CSV). |
| «Последний импорт побеждает» | Сценарий импорта: записи пакета замещают локальные соответствующие записи без вопросов. |
| «Выборочный импорт» | Сценарий импорта: пользователь вручную отмечает записи пакета, которые пойдут в обычную обработку. |
| План импорта | Стадия анализа пакета до применения: сводка справочников, классы сопоставления, предупреждения. |

**Резервирование, защита, состояния**

| Термин | Определение |
|---|---|
| Автокопия | Автоматическая копия базы перед импортом; хранятся три последние. |
| Резервная копия Администратора | Копия, создаваемая Администратором вручную; не ротируется. |
| Резервный код | Одноразовый код, который выдаётся Администратору при первичной настройке для восстановления доступа; показывается один раз, после использования недействителен и заменяется новым (5.2.1, раздел 13). |
| Страховочная копия | Копия базы данных, создаваемая автоматически перед полным восстановлением и перед миграцией схемы; не входит в три автокопии; хранится, пока Администратор не удалит её (6.1.3). |
| Привязка к оборудованию | Отказ программы открывать базу данных на другом компьютере (составной отпечаток). |
| Журнал | Единственный документ событий программы, хранится вне базы данных. |
| «Требует уточнения» | Флаг карточки, восстановленной из архива. |
| «Требует внимания» | Флаг карточки с просроченным календарным статусом (только для своих записей). |
| Языковой пакет | Файл с переводами интерфейса и названий терминов для языка или его варианта (9.14). |

# Раздел 1. Бизнес-модель и роли

## 1.1. Организационная модель

1. Компания состоит из филиалов. В каждом филиале развёрнуты минимум две копии программы.
2. Копии работают на компьютерах (ноутбуках) без подключения к сети Интернет. Связь копий осуществляется только файловым обменом пакетами (П1).
3. Одна копия соответствует одному компьютеру и имеет собственную базу данных и собственный `installation_id`.
4. Копия имеет **домашний филиал**: записи этого филиала копия вправе изменять и экспортировать (раздел 5).
5. Данные одного филиала должны быть одинаковыми во всех его копиях. Это достигается обменом пакетами; между обменами копии могут различаться, и это не ошибка.
6. Учётные записи пользователей локальны для копии и между копиями не передаются.
7. Отказ компьютера означает переустановку копии, создание новых транспортных связей и получение недостающих данных пакетами.

## 1.2. Пользователи и роли

1. С программой работают сотрудники компании в трёх ролях: **Администратор**, **HR**, **Наблюдатель**.
2. Учётная запись имеет ровно одну роль.
3. В копии существует **не более одной активной учётной записи Администратора**. Доступ единственного Администратора защищён ключом восстановления (раздел 13).
4. На одном компьютере несколько пользователей работают поочерёдно. Одновременно в копии активна не более одной сессии.

## 1.3. Администратор

Администратор это сотрудник отдела IT или безопасности, отвечающий за развёртывание и сопровождение программы.

**Администратору доступны все функции программы, кроме работы с чувствительными полями (15.3).** Он отвечает за:

- создание и ведение учётных записей и настроек безопасности;
- справочник филиалов, назначение домашнего филиала;
- ключи доверия и направления обмена;
- Журнал, ручные резервные копии и полное восстановление;
- профиль компании, язык и консоль локализации, управление шаблонами отчётов.

Ограничения, которые не снимаются ни для одной роли:

1. В программе нет функции изменения или удаления Журнала и истории транспорта (П3).
2. В программе нет функции удаления карточек сотрудников (П3).
3. Администратор, как и HR, редактирует только записи домашнего филиала (1.6). Для работы с записями другого филиала Администратор назначает копии другой домашний филиал (раздел 5).

Администратор должен иметь возможность решать проблемы эксплуатации средствами программы: восстановление из резервной копии, повторная инициализация направления, получение данных повторным пакетом. Возможный риск повреждения данных его действиями принят. Прямое вмешательство в файл базы данных вне программы также является принятым риском.

## 1.4. HR

HR это сотрудник отдела кадров. Ему доступны все функции работы с базой данных в пределах своих прав:

- создание и редактирование карточек сотрудников домашнего филиала, назначение статусов;
- **просмотр, ввод и редактирование чувствительных полей** карточек своего филиала, включение их в отчёты, обезличивание архивных карточек (раздел 15);
- архивирование и восстановление из архива;
- ведение справочника своего филиала (без изменения базового набора);
- внешний и локальный импорт, экспорт;
- повторная инициализация направления в диалоге экспорта или импорта (без доступа к ключам доверия);
- просмотр автокопий и возврат данных о сотрудниках к автокопии (6.6);
- стандартные отчёты и активные шаблоны.

HR **не имеет** доступа к учётным записям, настройкам безопасности, ключам доверия, Журналу, ручным резервным копиям, полному восстановлению и управлению шаблонами. Записи других филиалов доступны HR только для просмотра.

## 1.5. Наблюдатель

Наблюдатель это сотрудник отдела кадров, отвечающий за актуальность учёта состояния персонала. Он:

- видит **только записи домашнего филиала** копии;
- меняет статусы только этих записей, остальные поля карточки менять не может;
- просматривает справочники, использует стандартные отчёты и активные шаблоны.

Кнопки операций с базой данных (импорт, экспорт, архив, резервные копии, транспорт) Наблюдателю не показываются. Право Наблюдателя назначать статусы (ADR-0015) является нормой.

## 1.6. Принадлежность записей и видимость

| Запись | Администратор | HR | Наблюдатель |
|---|---|---|---|
| Свои (домашнего филиала) | просмотр, редактирование | просмотр, редактирование | просмотр, смена статуса |
| Чужие (реплики других филиалов) | просмотр | просмотр | не видны |

1. Чужие записи не редактируются ни одной ролью: они изменяются только операцией импорта (П2).
2. Свои записи изменяются либо своей копией, либо операцией импорта.
3. Принадлежность записи филиалу определяется самой записью и не зависит от копии, в которой её открыли.

# Раздел 2. База данных

## 2.1. Хранение и защита данных

1. Каждая копия программы имеет одну локальную базу данных на своём компьютере.
2. База данных шифруется целиком. Ключ шифрования не равен паролю ни одной учётной записи; потеря единственного пароля не должна приводить к потере данных (ADR-0002, ADR-0003).
3. Доступ к расшифрованным данным возможен только после успешной проверки оборудования (2.6) и аутентификации пользователя.
4. Основные данные о сотрудниках хранятся в таблице сотрудников и связаны со справочниками. Профиль компании и параметры безопасности хранятся в настройках копии.

## 2.2. Идентификаторы записей

1. Каждая запись имеет локальный идентификатор `id`. Он действует только внутри одной базы данных и между копиями не сопоставляется.
2. Каждая карточка сотрудника при создании получает уникальный `external_id`. Он используется для опознания одной и той же карточки между копиями программы.
3. `external_id` не изменяется при изменении данных карточки. **Перевод сотрудника в другой филиал не сохраняет `external_id`**: в филиале назначения создаётся новая карточка с собственным `external_id` (раздел 4). [Исходное ТЗ утверждало обратное; пункт изменён.]
4. `external_id` идентифицирует карточку, а не человека (П4). Глобального идентификатора человека в системе нет.
5. Правила сопоставления входящих записей (связь идентичности, классы EXACT, NEW, LOW, AMBIGUOUS, CONFLICT) описаны в разделах 4 и 7.

## 2.3. Принадлежность записей

1. Каждая карточка сотрудника принадлежит ровно одному филиалу.
2. **Принадлежность карточки филиалу не изменяется после создания.** Перемещение сотрудника в другой филиал выполняется только как перевод: архив в прежнем филиале и новая карточка в новом.
3. Записи справочников принадлежат либо базовому набору, либо филиалу-владельцу (раздел 3).
4. «Свои» и «чужие» записи определяются относительно домашнего филиала копии (1.6). Права на запись определяются принадлежностью записи, а не копией, в которой её открыли.

## 2.4. Неизменяемость данных

1. **Карточки сотрудников не удаляются** никакой функцией программы и никакой ролью. Ошибочно созданная карточка помещается в архив с видом занятости «ошибочная запись». Ни одна операция импорта не удаляет карточки. Единственное допустимое стирание данных — обезличивание содержимого карточки (раздел 15); восстановление из резервной копии заменяет состояние данных и удалением карточки не считается.
2. История статусов и её исправления только дополняются: изменение и удаление записей запрещено на уровне базы данных.
3. Записи справочников, на которые есть ссылки, не удаляются, а скрываются.
4. Журнал хранится вне базы данных (раздел 8); история транспорта не изменяется и не удаляется средствами программы.
5. Никакая операция над базой данных (миграция, восстановление, импорт) не должна обходить проверки целостности, например, отключением внешних ключей.

## 2.5. Идентичность установки

1. При развёртывании копии создаётся `installation_id` (случайный UUID). Он не изменяется в течение жизни установки.
2. `installation_id` принадлежит транспорту (раздел 7) и не относится к записям сотрудников и к филиалу.
3. Законных переносов копии нет. Копирование файла базы данных на другой компьютер не создаёт новой копии программы; программа откажется её открыть (2.6).
4. Замена или отказ компьютера означает **новую установку**: новый `installation_id`, новые транспортные связи; данные сотрудников возвращаются импортом пакетов от других копий филиала.
5. Резервная копия не переносит идентичность установки на другой компьютер (раздел 6).

## 2.6. Привязка к оборудованию

1. База данных не должна открываться на оборудовании, отличном от того, на котором она создана. Цель защиты: пользователь без специальной квалификации, скопировавший файл (П8).
2. Проверка выполняется при каждом открытии базы данных до аутентификации пользователя.
3. Отпечаток оборудования составной: образуется из нескольких независимых факторов; состав факторов определяет ADR.
4. **Изменение одного фактора** допускается: база открывается, отпечаток обновляется, в Журнал записывается событие.
5. **Изменение двух и более факторов**: программа **отказывается открыть** базу данных, сообщает об этом пользователю без раскрытия технических подробностей и записывает событие в Журнал. При следующем допустимом открытии Администратор видит уведомление о нарушении условий использования (раздел 8).
6. Резервные копии строго привязаны к копии программы: восстановление копии, созданной другой установкой, отклоняется (раздел 6).
7. **Привязка к оборудованию может быть отключена только в тестовых сборках, кроме тестов самой привязки, где она включена. В релизной сборке отключить привязку нельзя ни настройкой, ни параметром запуска; механизм отключения в релизном артефакте физически отсутствует.**
8. Регистрация носителей и аппаратных токенов в ТЗ v2 не входит (отдельный issue).

## 2.7. Филиалы и домашний филиал

1. Филиал создаётся вручную Администратором в справочнике филиалов на первой установке в филиале. На остальных копиях другие филиалы появляются только из пакетов: при первичной настройке загрузкой справочников (5.3.3), затем импортом.
2. Копия считается ненастроенной, пока не назначен домашний филиал (5.3.3). Назначение домашнего филиала предполагает, что в базе данных существует хотя бы один филиал.
3. Копия имеет ровно один домашний филиал, который назначает Администратор из справочника. До назначения работа с записями сотрудников невозможна; доступны транспортные настройки и операция «Загрузка справочников из пакета» (5.3.3).
4. Мастер первичной настройки, предупреждения при создании филиала в пустом справочнике и порядок смены домашнего филиала описаны в разделе 5.

## 2.8. Профиль компании и логотип

1. Профиль компании (название, логотип) локален для копии и пакетами не передаётся.
2. **Логотип хранится в базе данных**, а не как путь к файлу: он сохраняется вместе с резервными копиями и не зависит от наличия внешнего файла. Допустимые форматы и предельный размер определяет ADR.

## 2.9. Допущения

1. На момент утверждения ТЗ v2 реальных рабочих баз данных не существует. Схема базы данных может перестраиваться без миграции существующих данных до выпуска первой рабочей версии.
2. После выпуска первой рабочей версии любое изменение схемы сопровождается миграцией.

# Раздел 3. Справочники

## 3.1. Состав справочников

Программа ведёт шесть справочников:

| Справочник | Содержание |
|---|---|
| Филиалы | Филиалы компании |
| Департаменты | Департаменты филиала |
| Отделы | Отделы департамента; используются, если нужны |
| Должности | Должности, принадлежащие филиалу |
| Виды занятости | Вид занятости карточки; часть видов архивирует карточку |
| Статусы | Статусы доступности сотрудника |

Справочники объединены в две группы с разными правилами идентификации.

## 3.2. Две группы справочников

1. **Организационные** (филиалы, департаменты, отделы, должности) принадлежат филиалу, идентифицируются по `external_id` и передаются пакетами как данные филиала-владельца (ADR-0010).
2. **Справочники значений** (виды занятости, статусы) состоят из **базового набора** и **дополнительных записей филиала**. Они идентифицируются парой «владелец плюс `code`» и передаются пакетами как данные филиала-владельца. Исключение этой группы из обмена (ADR-0010) отменяется ТЗ v2.

## 3.3. Модель «5+1»

1. Копия, связанная с N филиалами, хранит справочники всех N филиалов и свой собственный.
2. Записи справочника домашнего филиала копии редактируются; записи справочников других филиалов доступны только для просмотра и изменяются только импортом (П2).
3. Справочник каждого филиала на всех копиях других филиалов является репликой и не может разойтись с оригиналом иначе как между обменами.

## 3.4. Базовый набор

Базовый набор засевается в дистрибутив, одинаков во всех копиях, не принадлежит никакому филиалу, не изменяется и не скрывается ни одной ролью. Коды неизменяемы.

**Статусы:**

| Код | Название | Дата окончания |
|---|---|---|
| `office` | В офисе | не требуется |
| `remote` | Удалённо | не требуется |
| `trip` | Командировка | обязательна |
| `sick` | Больничный | необязательна |
| `vacation` | Отпуск | обязательна |
| `day_off` | Отгул | обязательна |

**Виды занятости:**

| Код | Название | Архивирует карточку |
|---|---|---|
| `staff` | Штатный | нет |
| `temporary` | Временный | нет |
| `contractor` | Подрядчик | нет |
| `dismissed` | Уволен | да |
| (новый) | Переведён | да |
| (новый) | Ошибочная запись | да |

Коды новых видов «Переведён» и «Ошибочная запись» фиксируются адденом к ADR-0011.

Базовый набор (статусы и виды занятости вместе) имеет **маркер версии** (14.2.1). Базовые записи доступны во всех копиях всегда и не могут быть скрыты.

## 3.5. Дополнительные записи филиала

1. Администратор и HR могут создавать дополнительные статусы и виды занятости **только в справочнике своего (домашнего) филиала**.
2. Код задаётся при создании, неизменяем и уникален в пределах владельца. Коды базового набора зарезервированы. Формат кода определяет ADR.
3. Название и атрибуты (дата окончания, цвет, порядок) редактирует только владелец.
4. Запись не удаляется, а скрывается. Скрытая запись не предлагается для новых назначений, но остаётся видимой в карточках, где уже использована.
5. **Дополнительные виды занятости не архивируют карточку.** Архивирующими являются только три системных вида (3.4).

## 3.6. Ссылки и идентификаторы

1. В пакетах ссылка на запись справочника значений имеет вид «владелец плюс `code`». Для базового набора владелец не указывается.
2. Локальные `id` справочников значений в пакеты не попадают. При приёме `id` определяется заново по паре «владелец плюс `code`».
3. Организационные справочники сопоставляются по `external_id`.
4. Ссылка пакета на запись справочника, которой нет ни в пакете, ни в базовом наборе, ни локально, делает пакет некорректным: он отклоняется целиком (П6).

## 3.7. Приём справочников при импорте

Справочники обрабатываются **до** записей сотрудников, на стадии плана импорта (раздел 7). Применение справочников и записей остаётся одной атомарной операцией.

1. Проверка совместимости версий выполняется по 14.2.4; при несовместимости пакет отклоняется целиком.
2. Для записей вне базового набора формируется **сводка** по каждому справочнику: добавлено, изменено, скрыто; для изменённых показываются значения «локально» и «в пакете».
3. Базовый набор пакетом не изменяется.
4. Новые записи и обновления справочников других филиалов применяются без вопросов, показывается только сводка: пользователь не вправе блокировать обновление справочника владельца, а локально эти записи изменить нельзя (3.3.2).
5. **Диалог.** Если пакет изменяет запись справочника, которую данная копия вправе изменять сама (справочник домашнего филиала), и содержание записи в пакете отличается от локального, программа показывает диалог со сводкой различий. Пользователь выбирает: **заменить локальный справочник импортируемым** (записи пакета добавляются, обновляются или скрываются по паре «владелец плюс `code`»; локальные записи, которых нет в пакете, сохраняются, 2.4.3) либо **отклонить импорт полностью** (ничего не применяется, П6).
6. Решение пользователя фиксируется в плане импорта и в Журнале.

## 3.8. Выбор значений в интерфейсе

1. При назначении статуса и вида занятости в записях своего филиала предлагаются базовый набор (всегда) и справочник домашнего филиала (без скрытых записей).
2. Статусы и виды занятости чужих карточек отображаются без возможности выбора. Дополнительные статусы и дополнительные виды занятости, созданные другими филиалами, отображаются точно как получены (название, цвет) и не переводятся ни в одной локализации. Базовый набор (системные статусы и виды занятости, включая «уволен», «переведён», «ошибочная запись») является терминологией программы и локализуется (9.14).
3. Порядок: базовые записи, затем дополнительные, внутри групп по порядку сортировки.

## 3.9. Организационные справочники

1. Иерархия «филиал → департамент → отдел»; департамент и отдел необязательны (ADR-0008).
2. Требования должности к департаменту и отделу настраиваются у должности (ADR-0009).
3. Должность принадлежит филиалу.
4. Запись нельзя переместить под другого родителя, если на неё ссылаются карточки.
5. Филиал создаёт только Администратор; департаменты, отделы и должности своего филиала создают Администратор и HR.
6. **Название филиала уникально** (нормализованное сравнение: регистр, пробелы, «ё» и «е»). Создание филиала с занятым названием, переименование на занятое название и приход по импорту филиала с занятым названием при другом `external_id` запрещены (5.2.6).
7. **Плановая численность** необязательный атрибут департамента и отдела (целое число). Редактируют Администратор и HR своего филиала; передаётся в пакетах как данные справочника владельца; используется в отчёте «Краткая сводка доступности персонала» (11.2).

# Раздел 4. Сотрудники

## 4.1. Карточка сотрудника

1. Программа ведёт учёт сотрудников филиала. Карточка относится к одному филиалу и содержит сведения о работе в нём.
2. Программа не ведёт единой сущности «человек» (П4). Один человек в разные периоды может иметь разные карточки в разных филиалах; это самостоятельные записи.
3. Одна и та же карточка может существовать в нескольких копиях одного филиала. Такие записи являются репликами и распознаются при обмене по `external_id`.
4. Карточка содержит: ФИО; филиал; департамент; отдел (если используется); должность; вид занятости; дату приёма; контактные и иные предусмотренные сведения; примечание; признак «действующая» или «архивная»; служебный признак «требует уточнения»; служебный признак «обезличена».
5. **Чувствительные поля** (домашний адрес, номер страхования) доступны **только HR** для карточек своего филиала. Никакая другая роль не может вводить, просматривать, редактировать их и выводить в любом виде. По умолчанию они маскированы; просмотр полного значения и правка отдельные действия, каждое записывается в Журнал (раздел 15).
6. Статус доступности не является полем карточки: это история статусов, локальная и неизменяемая (2.4.2).
7. Признак «обезличена» (4.1.4) устанавливается **только программой** при обезличивании карточки (15.7). Импорт и восстановление этот признак не снимают.

## 4.2. Идентификатор `external_id`

`external_id` создаётся автоматически при создании карточки; не вводится пользователем; не изменяется при редактировании, архивировании и восстановлении; передаётся в пакете; одинаков у всех реплик карточки; не используется для определения того, что карточки в разных филиалах относятся к одному человеку. Локальные `id` разных копий между собой не сопоставляются.

## 4.3. Создание карточки

1. Карточки своего филиала создают Администратор и HR.
2. Программа проверяет заполнение обязательных полей, соответствие справочникам, иерархию департамент–отдел и требования должности (ADR-0008, ADR-0009).
3. Программа проверяет совпадение нормализованного ФИО с действующими карточками **своего и других филиалов** (4.9) и предупреждает; решение за пользователем.

## 4.4. Редактирование

1. Редактируются только действующие карточки своего филиала. **Архивная карточка не редактируется**: изменения возможны только через восстановление (4.8).
2. Филиал карточки не изменяется (2.3.2).
3. **ФИО является постоянной величиной и не изменяется после создания.** Смена фамилии или исправление ошибочного ФИО оформляется архивированием карточки и созданием новой. В примечании новой карточки HR указывает, как найти прежнюю; обязательной связи между карточками программа не ведёт.
4. Чувствительные поля редактирует только HR.

## 4.5. Архив и увольнение

1. Карточка не удаляется (2.4.1). Архивирование выполняется присвоением архивирующего вида занятости («уволен», «переведён», «ошибочная запись»; 3.4).
2. Архивная карточка сохраняет данные о работе в филиале и `external_id`, не считается действующей и не участвует в операциях, предназначенных для действующих сотрудников.
3. Архивируют HR и Администратор, только карточки своего филиала.
4. Форма «Архив» показывает архивные карточки **домашнего филиала**. Архивные карточки других филиалов хранятся как реплики, в форме «Архив» не показываются и **не могут быть просмотрены ни в одной форме программы**.
5. Архивные карточки домашнего филиала передаются в пакетах как обычные реплики: копиям того же филиала в полном объёме, копиям других филиалов без чувствительных полей.
6. Данные архива не считаются действующими данными о составе филиала.

## 4.6. Перевод в другой филиал

1. Перевод не выполняется изменением филиала карточки.
2. HR или Администратор исходного филиала архивирует карточку с видом «переведён» и указывает **филиал назначения** из справочника филиалов (не домашний).
3. В филиале назначения HR создаёт новую карточку (с новым `external_id`) либо восстанавливает прежнюю архивную обычной операцией «Восстановить» (4.8).
4. **Автоматического сопоставления, автоматического восстановления и уведомления получателя при импорте нет.**
5. Связь между карточкой в исходном филиале и новой карточкой программа не ведёт. Филиал назначения в архивной карточке справочное поле и на логику не влияет.

## 4.7. Ошибочная запись

1. Ошибочно созданная карточка (дубль, неверное ФИО) архивируется с видом «ошибочная запись».
2. Такие карточки исключаются из отчётов и счётчиков и видны только в форме «Архив» с отдельным фильтром.
3. Архивирование ошибочной записи распространяется на все копии обычным импортом по `external_id`.
4. Восстановление такой карточки допускается как обычное восстановление (4.8).

## 4.8. Восстановление из архива

1. Восстановление отдельная операция, а не редактирование архивной карточки. Выполняется HR или Администратором для карточки своего филиала.
2. При восстановлении карточка становится действующей; локальный `id`, `external_id` и история карточки сохраняются.
3. **Вид занятости не восстанавливается автоматически**: пользователь выбирает его заново (ADR-0011).
4. Устанавливается признак **«требует уточнения»**. Он снимается сохранением актуализированной карточки (орг. данные, вид занятости).
5. Восстановление не создаёт новую карточку вместо существующей архивной.
6. При восстановлении выполняется проверка двойной занятости (4.9).
7. Признак **«требует внимания»** относится не к восстановлению, а к просроченному календарному статусу (раздел 9) и действует только для записей своего филиала.

## 4.9. Возможная двойная занятость

1. Бизнес-ориентир: один человек не должен числиться действующим одновременно в нескольких филиалах. Программа не ведёт единой сущности «человек» (П4) и доказать это не может, поэтому она обнаруживает только **возможную** двойную занятость: совпадение нормализованного ФИО (регистр, пробелы, «ё» и «е») у действующих карточек разных филиалов.
2. Проверка выполняется при создании карточки, восстановлении из архива, применении импорта (на стадии плана) и оформлении перевода (создание карточки в филиале назначения).
3. Результат это **предупреждение, а не запрет**. При локальных операциях окно показывает совпавшие карточки (филиал, должность, вид занятости) и предлагает: «Продолжить», «Отменить операцию», «Это разные люди».
4. При импорте предупреждения входят в план импорта для любого сценария. Пользователь вправе принять импорт или отклонить его целиком (П6).
5. Совпадения видны и позже: счётчик «Возможное двойное числение (N)» на третьей панели (Администратор и HR) открывает список пар с кнопкой «Это разные люди».
6. Пометка «Это разные люди» хранится локально в копии парой `external_id` и в пакеты не передаётся.
7. Архивные карточки (включая «ошибочная запись») в проверке не участвуют.
8. Совпадение ФИО у двух действующих карточек **одного** филиала выводится в тот же список как «возможный дубль». Он разрешается архивированием лишней карточки с видом «ошибочная запись» либо пометкой «Это разные люди».

## 4.10. Сопоставление карточек при импорте

1. Сначала используется `external_id`. Если локальная карточка с таким `external_id` есть (действующая или архивная), она рассматривается как реплика. Проверяется согласованность ФИО (по правилу нормализации) и филиала-владельца. При совпадении класс EXACT, данные пакета заменяют локальные.
2. Если филиал-владелец или ФИО не совпали, класс CONFLICT: пакет отклоняется целиком. Это сигнал нарушения целостности: ФИО постоянно (4.4.3), филиал карточки неизменяем (2.3.2). Исключение (15.7.5): если входящая карточка обезличена (15.7) и её `external_id` и филиал-владелец совпадают с локальной карточкой, несовпадение ФИО не является конфликтом: локальная карточка обезличивается (обязательно, независимо от отметки строки в сценарии «Выборочный импорт», 7.18), прежние персональные данные никогда не восстанавливаются, и пакет по этой причине не отклоняется. Несовпадение филиала-владельца остаётся CONFLICT даже для обезличенной карточки.
3. Если локальной карточки с таким `external_id` нет, класс NEW. Совпадение ФИО само по себе не доказывает соответствия (П4).
4. **Кандидатами на соответствие** считаются только действующие карточки **того же филиала**, что и входящая, с совпадающим нормализованным ФИО и другим `external_id`. Архивные карточки и карточки других филиалов кандидатами не являются: повторный приём на работу порождает новую карточку, а не соответствие архивной.
5. Один кандидат: LOW; несколько: AMBIGUOUS.
6. В сценарии **«Последний импорт побеждает»** вопросы по отдельным записям не задаются: карточка с неизвестным `external_id` создаётся как новая, возможные дубли выводятся отчётом (4.9.8). В сценарии **«Выборочный импорт»** LOW и AMBIGUOUS разрешает пользователь (4.11).
7. Организационные ссылки карточки разрешаются по `external_id` (организационные справочники) и по паре «владелец плюс `code`» (виды занятости, статусы), 3.6. Отсутствующий или противоречивый объект делает пакет некорректным: он отклоняется целиком.
8. Состояние карточки (действующая или архивная) передаётся пакетом и применяется к реплике. Архивирование и восстановление на стороне источника воспроизводятся у получателя: архивированная карточка у получателя становится архивной, восстановленная становится действующей. Архивные карточки в пакете обрабатываются так же, как действующие, по `external_id`.
9. Входящая архивная карточка с неизвестным `external_id` принимается как архивная реплика без сопоставления по ФИО.

## 4.11. Подтверждение соответствия и связь идентичности

1. В сценарии «Выборочный импорт» для LOW и AMBIGUOUS пользователь видит сравнение «в текущей базе» и «в импорте» и выбирает «Это та же карточка» (при нескольких кандидатах выбирает нужную) либо «Это новая карточка».
2. «Та же карточка»: данные пакета применяются к выбранной локальной карточке, её `external_id` не изменяется.
3. Решение запоминается локально как **связь идентичности**: пара «`external_id` входящей карточки, `external_id` локальной карточки». При следующих пакетах с тем же входящим `external_id` карточка сопоставляется как EXACT без вопросов.
4. «Новая карточка»: создаётся карточка с входящим `external_id`; далее сопоставление идёт как EXACT.
5. Связь идентичности действует только в данной копии, в пакетах не передаётся, не является идентичностью человека.
6. Администратор и HR могут просмотреть список связей и отменить связь (после отмены тот же входящий `external_id` снова будет LOW или AMBIGUOUS).

## 4.12. Импорт и перевод

Применение пакета не истолковывает архивирование «переведён» как команду: карточки в других филиалах не создаются, не восстанавливаются и не изменяются. Двойная занятость, возникшая после импорта, обрабатывается по 4.9.

## 4.13. Архив как часть истории

Архивные карточки часть учёта работы в филиале. Архивирование не уничтожает карточку и не меняет `external_id`.

## 4.14. Организационные данные карточки

Карточка ссылается на справочники по разделу 3. Идентификация и разрешение ссылок при импорте определены в 3.6 и 4.10.7. Локальные идентификаторы справочников между копиями не используются.

## 4.15. Основные правила

| № | Правило |
|---|---|
| 1 | Карточка принадлежит одному филиалу; принадлежность не меняется. |
| 2 | `external_id` идентифицирует карточку, а не человека. |
| 3 | Реплики одной карточки имеют одинаковый `external_id`. |
| 4 | Локальные `id` разных копий не сопоставляются. |
| 5 | Увольнение архивирует карточку с видом «уволен». |
| 6 | Перевод архивирует карточку с видом «переведён»; филиал назначения справочное поле. |
| 7 | В филиале назначения используется отдельная карточка: новая (новый `external_id`) или восстановленная обычной операцией. |
| 8 | Автоматического восстановления вместо создания новой карточки нет. |
| 9 | Восстановленная карточка сохраняет `external_id`. |
| 10 | Новая карточка получает новый `external_id`. |
| 11 | Возможная двойная занятость обнаруживается и сообщается, но не запрещается. |
| 12 | Пользователь вправе отклонить импорт целиком по результатам предупреждений. |
| 13 | Отдельного глобального идентификатора человека нет. |
| 14 | Совпадение ФИО не доказывает совпадения человека. |
| 15 | Решение о соответствии не меняет `external_id`; запоминается локально как связь идентичности. |
| 16 | ФИО постоянно. |
| 17 | Ошибочная запись архивируется, не удаляется. |
| 18 | Признак «обезличена» устанавливает только программа при обезличивании; импорт и восстановление его не снимают (15.7). |

# Раздел 5. Копии программы

## 5.1. Дистрибутив и установка

1. Программа распространяется по филиалам в виде дистрибутива с пакетом эксплуатационных документов.
2. Программа устанавливается на компьютерах под управлением Debian 12. Дистрибутив содержит все необходимые системные пакеты и зависимости, включая Python, и устанавливается автономно, без подключения к сети Интернет.
3. Обновление копии выполняется установкой нового дистрибутива; база данных мигрирует по правилам 14.2.3.

## 5.2. Первичная настройка

При первом запуске новой копии выполняется мастер первичной настройки:

1. **Администратор.** Создаётся учётная запись Администратора (логин, пароль). Ему выдаётся **резервный код**: он показывается один раз, и Администратор обязан его сохранить. Порядок использования описан в разделе 13.
2. **Идентичность копии.** Создаётся `installation_id` и запоминается отпечаток оборудования (2.5, 2.6).
3. **Филиал.** Мастер предлагает два сценария:
   - **первая установка в филиале:** Администратор создаёт филиал вручную в справочнике филиалов и назначает его домашним;
   - **не первая установка в филиале:** Администратор настраивает транспорт (раздел 7), загружает справочники из пакета операцией «Загрузка справочников из пакета» (5.3.3), затем отмечает в справочнике, какой из пришедших филиалов является домашним. Данные карточек филиала применяет HR после ввода копии в эксплуатацию обычным импортом.
4. Вне мастера, при создании филиала в **пустом** справочнике, программа повторно предупреждает: «Если это не первая установка в филиале, филиал нужно получить загрузкой справочников из пакета, иначе в системе появится второй филиал с тем же названием».
5. **Пользователи.** До ввода копии в эксплуатацию Администратор создаёт учётные записи пользователей.
6. Если при импорте приходит филиал, название которого (при нормализованном сравнении: регистр, пробелы, «ё» и «е») совпадает с названием локального филиала при другом `external_id`, программа сообщает о конфликте названий и **отклоняет импорт целиком** (П6).
7. Пара `external_id` и название филиала уникальна: в системе не может существовать двух филиалов с одинаковым названием, в том числе скрытых (3.9.6). Конфликт названий устраняет Администратор: переименованием локального филиала либо, если копия настроена неверно, переустановкой копии (5.6).

## 5.3. Домашний филиал

1. Домашний филиал определяет филиал, которому принадлежит копия (1.1.4, 2.7). Для копии может быть назначен только один домашний филиал.
2. Назначение выполняется Администратором в разделе «Филиалы» формы «Справочник». Это отдельная операция настройки копии; данные самого филиала она не изменяет.
3. **До назначения** работа с записями сотрудников невозможна: недоступны просмотр, создание и правка карточек, назначение статусов, архив, локальный импорт, внешний импорт (кроме операции «Загрузка справочников из пакета»), экспорт и отчёты. **Доступны Администратору:** справочник филиалов, настройки (транспорт, безопасность, учётные записи), операция «Загрузка справочников из пакета», Журнал, окно «?». Пользователи других ролей при входе видят сообщение, что копия ещё не настроена. Операция «Загрузка справочников из пакета» загружает **только справочники** из пакета; пакет **не принимается** (7.19.7): состояние входящего направления, поколение, ключи и запись о принятии пакета не изменяются; запись о повторной доставке (REPLAY) не создаётся; инициализация у получателя (7.20) не запускается, даже если класс пакета ИНИЦИАЛИЗАЦИЯ. Операция записывает собственное событие в Журнал; перед ней создаётся автокопия (6.2). После настройки HR применяет тот же пакет обычным порядком. Проверки перед загрузкой, конфликт названия филиала, прогресс, отмена и транзакция описаны в 7.19.7.
4. После назначения домашнего филиала записи этого филиала становятся своими.
5. Копия считается **ненастроенной**, пока не назначен домашний филиал (5.3.3). Основной путь — мастер первичной настройки (5.2.3, 9B.3). Если домашний филиал не назначен и справочник филиалов **пуст** (например, мастер прерван), кнопка «Справочник» (9.2) у **Администратора** открывает модальное окно (другим ролям оно недоступно) с тем же двусторонним выбором, что и в мастере: (a) войти в справочник, создать филиал вручную и назначить его домашним (5.2.3); (b) выбрать «Загрузка справочников из пакета» (диалог выбора пути к файлу пакета, 5.3.3) и после успешной загрузки перейти в справочник и назначить домашним один из загруженных филиалов. Если справочники уже загружены (или филиал создан), но домашний филиал не выбран, остальные пользователи по-прежнему не могут работать (5.3.3), модальное окно больше не показывается: кнопка «Справочник» открывает справочник напрямую, где доступны загруженные филиалы и создание собственного (9.9).

## 5.4. Смена домашнего филиала

1. Менять домашний филиал копии может только Администратор. Это основной способ получить доступ к записям другого филиала (1.3) и сценарий перемещения ноутбука между филиалами.
2. Перед сменой программа показывает предупреждение, в котором перечислено:
   - какие **неэкспортированные изменения** есть у записей прежнего домашнего филиала (по направлениям: количество карточек, изменённых после последнего экспорта), какие направления имеют неподтверждённые пакеты (PENDING) и какие направления находятся в состоянии «режим инициализации»;
   - что записи прежнего домашнего филиала **станут чужими**: только просмотр, редактирование и экспорт будут недоступны;
   - что записи нового домашнего филиала станут своими;
   - что все направления этой копии (входящие и исходящие) автоматически получат тип «между филиалами» (безопасный: чувствительные поля не передаются, 7.2.3).
3. Смена допускается и при наличии неэкспортированных изменений, неподтверждённых пакетов или направлений в состоянии «режим инициализации»: предупреждение информирует, но не запрещает. В процедуру смены входит **обязательный неблокирующий шаг**: после автоматической установки типа (5.4.7) Администратору показывается список всех направлений с человекочитаемыми именами и типами, и он вручную устанавливает тип «внутри филиала» на тех направлениях, которым это нужно. Программа правильность типов не проверяет. Факт показа и просмотра списка записывается в Журнал.
4. Смена не изменяет данные филиалов, не требует инициализации направлений (транспорт привязан к установке, а не к филиалу) и записывается в Журнал.
5. После смены экспорт этой копии содержит записи нового домашнего филиала.
6. Смена домашнего филиала **сбрасывает отметки экспорта всех исходящих направлений**; первый экспорт после смены является полным для нового домашнего филиала. Сброс записывается в Журнал.
7. При смене **все направления этой копии** (входящие и исходящие) автоматически получают тип «между филиалами» (безопасный: чувствительные поля не передаются). Администратор получает уведомление, которое регистрируется в Журнале.
8. Если Администратор не вернёт тип «внутри филиала» до первого экспорта, пакет уходит без чувствительных полей; это не является утечкой; исправление — повторная инициализация направления либо полный экспорт без смены поколения (7.4.6).
9. Чувствительные поля карточек прежнего домашнего филиала остаются в базе данных в зашифрованном виде и недоступны; они не стираются.

## 5.5. Один экземпляр программы

1. С одной базой данных одновременно может работать только один экземпляр программы. Второй экземпляр на том же компьютере не запускается и сообщает причину (#146).
2. Блокировка должна быть устойчива к аварийному завершению первого экземпляра (оставшаяся блокировка не должна мешать запуску). Механизм определяет ADR.
3. Ограничение соответствует правилу одной активной сессии (1.2.4).

## 5.6. Переустановка и замена компьютера

1. Замена или отказ компьютера означает новую установку (2.5.4): новая копия получает новый `installation_id`, настраивается заново через мастер (5.2), устанавливает новые транспортные связи и получает данные импортом пакетов от других копий филиала.
2. Учётные записи, настройки и резервный код создаются заново; из резервной копии прежнего компьютера восстановление не выполняется (2.6.6).

# Раздел 6. Резервное копирование

## 6.1. Виды резервных копий

1. **Автокопия** создаётся программой автоматически перед импортными операциями и операцией «Загрузка справочников из пакета» (6.2).
2. **Ручная копия** создаётся Администратором по команде.
3. **Страховочная копия** создаётся автоматически перед полным восстановлением Администратора (6.5) и перед миграцией схемы (6.9). Она не входит в три автокопии и не вытесняет их. Хранится, пока Администратор не удалит её.
4. Режимов «полное» и «выборочное» из исходного ТЗ больше нет: состояние транспорта никогда не восстанавливается (6.7).
5. Копия включает всё, что нужно для открытия базы на **этой же** установке.

## 6.2. Автокопия

1. Создаётся перед **применением** внешнего импорта, перед применением пакетного ввода в локальном импорте и перед операцией «Загрузка справочников из пакета» (5.2.3, 5.3.3). Она не создаётся при закрытии программы и по расписанию. Миграция схемы не является поводом для автокопии: для неё создаётся страховочная копия (6.1.3, 6.9.2).
2. Копия создаётся в момент подтверждённого начала операции (для импорта — подтверждённого применения), а не при открытии формы.
3. Если создание или проверка копии завершились ошибкой, операция не выполняется.
4. Если операция откатилась без изменений, созданная перед ней копия удаляется.
5. Хранятся **три последние** автокопии в порядке поступления. При создании новой копии при наличии трёх самая старая замещается.
6. Имя копии содержит дату и время создания в сортируемом формате (например, `20261007-142300`); порядок определяется по имени.

## 6.3. Ручная копия

1. Создаётся Администратором и не ротируется автоматически.
2. Администратор может удалять ручные копии. Автокопиями управляет только программа.
3. HR ручные копии не создаёт и не видит.

## 6.4. Форма «Резервные копии»

1. Форма вызывается из форм «Внешний импорт» и «Локальный импорт» (9.10). Наблюдателю недоступна.
2. Для каждой копии показываются дата и время создания, вид (автокопия, ручная, страховочная), версия программы и схемы (14.2.5).
3. **HR** видит только автокопии и может выполнить «Вернуть к копии» (6.6).
4. **Администратор** видит все копии и может создать ручную копию, выполнить «Восстановить базу» (6.5), удалить ручную или страховочную копию.

## 6.5. Полное восстановление (Администратор)

1. База данных заменяется выбранной копией целиком: карточки, справочники, учётные записи, настройки. Порядок полного восстановления:
   1) из выбранной копии собирается база-кандидат;
   2) если копия старше, мигрируется схема **кандидата**;
   3) в кандидат переносится текущее состояние транспорта и неизменяемая история транспорта из рабочей базы (поколения, последовательности, состояния цепочек ключей, ключи доверия, данные о принятых пакетах, состояния направлений, включая PENDING и «режим инициализации»);
   4) сбрасываются отметки экспорта всех исходящих направлений (карточки и статусы), чтобы следующий экспорт был полным;
   5) повторно применяется обезличивание (15.7.6);
   6) выполняется проверка;
   7) рабочая база заменяется кандидатом **одним атомарным шагом**.
   Запись Журнала «начато» пишется до замены (8.9.2); после замены остаётся записать только «завершено». Если сбой произошёл между заменой и записью «завершено», при следующем запуске программа узнаёт уже восстановленную базу по маркеру (маркер определяет ADR) и записывает «завершено».
2. Состояние транспорта при этом **не откатывается** (6.7).
3. Перед восстановлением автоматически создаётся **страховочная копия** «до восстановления» (6.1.3). Она не входит в три автокопии и не вытесняет их. Хранится, пока Администратор не удалит её; программа сама её не удаляет. При нехватке места программа предупреждает и предлагает удалить старые страховочные копии. Если страховочную копию создать нельзя, восстановление **не выполняется**, и Администратору сообщается причина.
4. Копия, созданная другой установкой, отклоняется (2.6.6). Копия с более новой схемой, чем у программы, отклоняется (14.2.5).

## 6.6. Возврат к автокопии (HR)

1. Операция «Вернуть к копии» предназначена для **страховки от ошибок импорта**. HR может выполнить её с любой из трёх автокопий.
2. Возвращаются **данные о сотрудниках**: карточки (включая архивные), статусы и их история, служебные признаки, связи идентичности и пометки «Это разные люди».
3. **Не возвращаются:** справочники, учётные записи, настройки (включая настройки безопасности), состояние транспорта, Журнал.
4. Перед выполнением показываются дата и время копии и предупреждение, что все изменения после неё (включая принятые пакеты) будут потеряны; требуется подтверждение.
5. Возврат **не создаёт новую автокопию и не меняет набор из трёх**. HR может возвращаться повторно к любой из трёх копий в любой последовательности, пока их не вытеснят более свежие (создаваемые при очередных импортах).
6. Копия со старой схемой возвращается с миграцией (14.2.3).
7. Администратор выполняет ту же операцию через «Восстановить базу» (6.5).
8. «Вернуть к копии» считается восстановлением в смысле 6.7: отметки экспорта сбрасываются (карточки и статусы), обезличивание применяется повторно, состояние транспорта и история транспорта сохраняются как в 6.7.

## 6.7. Восстановление и транспорт

1. Восстановление не затрагивает состояние транспорта: последовательности, поколения, ключи цепочек и их состояния, ключи доверия, данные о принятых пакетах, состояния направлений (включая PENDING и «режим инициализации») и история транспорта остаются текущими.
2. После **успешного** восстановления **отметки экспорта всех исходящих направлений сбрасываются**: следующий экспорт по каждому направлению полный.
3. Данные из пакетов, принятых после создания копии, при восстановлении могут быть утрачены, а повторно применить принятый пакет нельзя. Поэтому **до подтверждения восстановления** программа предупреждает об этом и перечисляет **входящие направления**, по которым следует попросить отправителя выполнить **полный экспорт** (при разрыве цепочки ключей инициализацию).
4. Записи истории транспорта неизменяемы: не удаляются, не переписываются и не подменяются содержимым копии.
5. Неуспешная операция не оставляет ни частично восстановленной базы, ни частично сброшенных отметок.

## 6.8. Журнал

Журнал хранится вне базы и восстановлением не затрагивается (раздел 8). Создание, удаление и восстановление копий записываются в Журнал (кто, какая копия, какой режим).

## 6.9. Надёжность восстановления и обновления (#144)

1. Восстановление выполняется так, чтобы при сбое прежняя база оставалась работоспособной: порядок операций 6.5.1 (база-кандидат собирается, при необходимости мигрируется и проверяется до замены рабочей базы одним атомарным шагом).
2. Перед миграцией схемы при обновлении программы создаётся **страховочная копия** (14.2.3); если страховочную копию создать нельзя, миграция не выполняется, и пользователю сообщается причина. При неудаче миграции база возвращается к страховочной копии (состояние до обновления). При следующем запуске программа показывает окно с причиной неудачи; доступны только кнопки «Повторить» и «Выйти»; Журнал при этом можно просматривать; число попыток не ограничено.
3. Пользователь получает понятное сообщение о причине отказа.

## 6.10. Замена компьютера

Восстановление копии прежнего компьютера на новом не поддерживается; выполняется новая установка (5.6).

# Раздел 7. Транспорт

## 7.1. Назначение

Обмен данными между копиями программы выполняется **пакетами** через внешний канал передачи (носитель, оператор). Постоянного соединения между копиями нет. Транспорт обеспечивает формирование и шифрование пакета, его передачу оператором, приём и расшифровку, проверку поколения и последовательности ключей, защиту от повторного применения, атомарное применение, фиксацию результата и защиту от ошибочного повторного использования ключей.

## 7.2. Направления обмена

1. **Направление** это односторонняя связь «отправитель → получатель» между двумя копиями. Для пары копий существуют два направления.
2. Для каждого направления есть собственная цепочка ключей и собственное состояние. Состояние одного направления не изменяет и не блокирует другое.
3. У направления есть **тип**: «внутри филиала» или «между филиалами». Тип определяется филиалом копии-абонента, который Администратор указывает при регистрации направления (раздел 13), и влияет на состав пакета (7.14). При смене домашнего филиала этой копии все направления этой копии автоматически получают тип «между филиалами» (5.4.7).
4. Регистрация направлений и ключей доверия выполняется только Администратором (Настройки → Транспорт). HR работает с уже зарегистрированными направлениями. При регистрации Администратор вводит удобочитаемое имя направления; программа предлагает «Филиал отправителя → Филиал получателя». Имя локально для копии, в пакетах не передаётся, Администратор может его изменить, и оно уникально в пределах копии.

## 7.3. Транспортные ключи

1. Для каждого направления используется последовательность ключей. Ключ определяется парой **поколение плюс последовательность** и принадлежит направлению.
2. Ключ признаётся использованным ровно в двух случаях: (1) оператор вручную подтвердил, что адресат получил пакет (7.7.1); (2) оператор выполнил инициализацию направления (7.8), после чего прежние ключи не применяются. Использованный ключ повторно не используется. **Ключ неподтверждённого пакета повторно не используется никогда.** Повторная запись того же пакета из его **временной копии пакета** (7.4.4) повторным использованием ключа не является.
3. Получатель принимает пакет только если его поколение и последовательность соответствуют ожидаемому состоянию направления. Пакеты старого поколения, уже принятой или пропущенной последовательности не применяются.
4. Доверие между копиями (публичные ключи абонентов) устанавливается однократно Администратором и **не требует повторного обмена** при инициализации направления (7.8).

## 7.4. Формирование исходящего пакета

1. Пакет получает: уникальный `package_id`; направление; поколение; последовательность; идентификатор ключа; зашифрованное содержимое; метаданные транспорта.
2. В метаданные входят **дата и время создания**, версия программы отправителя, версия протокола, маркер базового набора (14.2.4), **домашний филиал отправителя**, вид экспорта («полный» или «инкрементальный»).
3. Пакет должен быть полностью сформирован и зашифрован до передачи оператору.
4. Согласованная фиксация и запись файла выполняются в следующем порядке. (1) Пакет полностью сформирован и зашифрован (7.4.3). (2) Пользователь выбирает место сохранения файла; отмена выбора не оставляет продвинутого состояния. (3) Пакет автоматически сохраняется как **временная копия пакета** (без действия пользователя). (4) Состояние фиксируется атомарно: последовательность, ключ, PENDING, отметки экспорта (запись неизменяемой истории транспорта, 7.9); при выпуске пакета инициализации также снимается режим инициализации направления (7.7.2) — это состояние направления (6.7.1), а не запись истории транспорта. (5) Файл записывается. (6) Временная копия пакета удаляется сразу после записи файла (она не хранится до подтверждения доставки). (7) Запись в Журнал выполняется после фиксации в базе данных (8.9.1); для инициализации направления как критичной операции запись «начато» пишется до фиксации (8.9.2). Журнал не входит в фиксируемое состояние. Факт выпуска обычного пакета подтверждается историей транспорта в базе данных (7.9), а не наличием файла (файл вне программы) и не записью в Журнал (её отсутствие после сбоя не означает, что пакет не был выпущен). Если сбой произошёл после фиксации, но до записи файла, при следующем запуске программы (или при следующей попытке экспорта по этому направлению, когда заморозка 7.6 уже показывает пакет) программа сообщает «пакет не записан», предлагает выбрать место и записать тот же пакет из его временной копии; после записи временная копия удаляется; новый пакет не выпускается (#136).
5. «Обычный экспорт» (9.10.2): вид пакета выбирает программа, пользователь его не выбирает: **инкрементальный** (по отметкам экспорта направления и таблицы) или **полный**. Полный экспорт обязателен: для первого экспорта в направлении, после инициализации (7.8), после смены домашнего филиала (5.4.6), после восстановления (6.7.2). Отметки экспорта продвигаются при формировании пакета и сбрасываются при инициализации. Отметки карточек и отметки статусов ведутся отдельно (7.4.7); инициализация сбрасывает обе. Обезличивание карточки является изменением карточки и попадает в инкрементальный экспорт каждого исходящего направления, которое ещё не получило это состояние.
6. HR и Администратор могут также выпустить **полный экспорт без смены поколения** (#138) кнопкой «Полный экспорт (без смены поколения)» на форме «Экспорт» (9.10.2): для случаев, когда данные утрачены у получателя, а цепочка цела. Такой экспорт берёт следующую последовательность текущего поколения и новый ключ текущей цепочки, получает PENDING (7.5), замораживается как любой пакет цепочки (7.6), продвигает отметки карточек при формировании (7.4.5) и отметки статусов только если опция 7.4.7 включена; поколение не меняет и новую цепочку не создаёт. Доступен только когда по направлению нет PENDING и направление не в **режиме инициализации** (7.6.4). Действие требует подтверждения и записывается в Журнал. Пакет полного экспорта без смены поколения формируется из текущих данных отправителя (не только из изменений с момента последнего экспорта) и включает все текущие экспортируемые карточки домашнего филиала отправителя, действующие и архивные, независимо от отметок экспорта предыдущих экспортов и от содержимого более ранних пакетов.
7. Кнопки «Обычный экспорт», «Полный экспорт (без смены поколения)» и «Инициализация направления» (9.10.2) используют одну опцию **«Включить текущие статусы сотрудников»**; **по умолчанию она выключена** и действует на все три кнопки. Если опция выключена, пакет статусов не содержит, а у получателя статусы остаются без изменений. Отметки экспорта статусов ведутся отдельно от отметок карточек. Отметки статусов продвигаются только когда текущие статусы фактически включены в пакет (опция включена); при выключенной опции они не продвигаются, поэтому следующий экспорт с включённой опцией несёт всё накопленное. Инкрементальный пакет с включённой опцией несёт статусы, изменённые с момента отметки статусов, независимо от изменений карточек. Полный пакет с включённой опцией несёт текущие статусы всех экспортируемых карточек. Отметки статусов сбрасываются при инициализации (7.8.3), при восстановлении (6.7.2) и при смене домашнего филиала (5.4.6) так же, как отметки карточек.

## 7.5. Состояние PENDING

1. После выпуска пакета операция экспорта получает состояние **PENDING**: пакет выпущен (зафиксирован в истории транспорта), но подтверждения человека о его получении и приёме получателем ещё нет. PENDING получают все пакеты цепочки: обычный, обязательный полный, полный экспорт без смены поколения (7.4.6) и пакет инициализации (7.8).
2. Автоматически переводить PENDING в «подтверждено» запрещено. Перезапуск программы, наличие файла пакета, истечение времени и другие косвенные признаки подтверждением не являются.
3. PENDING хранится в базе данных и восстанавливается после перезапуска.

## 7.6. Заморозка направления

1. Пока по направлению существует операция PENDING, **новый выпуск пакета по этому направлению запрещён** для любого вида: инкрементального, полного, обязательного полного, полного экспорта без смены поколения (7.4.6). Единственный пакет, который допускается выпустить при существующем PENDING, — инициализация по решению оператора в 7.7.2, кнопкой «Инициализация направления» на форме «Экспорт» (9.10.2) или Администратором из настроек (7.8.4). Это правило протокола, а не только ограничение интерфейса.
2. Если по направлению есть PENDING, форма «Экспорт» (9.10.2) показывает неподтверждённый пакет (идентификатор, направление, время создания, поколение, последовательность) и предлагает действия 7.7; кнопки «Обычный экспорт» и «Полный экспорт (без смены поколения)» при этом недоступны. Если файл неподтверждённого пакета не был записан (сбой, 7.4.4), программа сообщает об этом и предлагает записать тот же пакет из временной копии до того, как предлагаются действия 7.7. Действия 7.7 («Подтвердить», «Не подтверждено») предлагаются только после того, как файл пакета записан: ответ до записи в этом диалоге невозможен.
3. Заморозка действует только для этого направления и не препятствует обмену по другим.
4. Пока направление находится в **режиме инициализации** (7.7.2), по этому направлению допускается только инициализация; обычный, инкрементальный, обязательный полный и полный экспорт без смены поколения (7.4.6) запрещены (правило протокола); форма «Экспорт» предлагает только кнопку «Инициализация направления» (9.10.2, 7.8). Режим действует только для этого направления.

## 7.7. Завершение PENDING

Оператор (HR или Администратор) выбирает одно из двух явных действий. Автоматически ни одно не выполняется. Эти действия предлагаются только после записи файла пакета (7.6.2).

1. **«Подтвердить»:** получатель получил пакет и принял его (в выборочном сценарии принятой единицей является пакет, а не каждая запись, 7.18.3). Операция получает состояние CONFIRMED (время, пользователь), направление размораживается.
2. **«Не подтверждено»** (пакет не доставлен или не обработан, либо оператор не уверен): операция получает состояние «заменено инициализацией», её PENDING завершается, и направление переходит в устойчивый **режим инициализации** (7.6.4): следующий пакет этого направления выпускается только как инициализация (7.8). Диалог сразу предлагает выпустить инициализацию; отмена выбора места файла режим не снимает. Режим хранится в базе данных, переживает перезапуск и восстановление (6.7.1), снимается только при фиксации самого пакета инициализации (7.4.4) и вручную отменить его нельзя.

Действия «повторить на старых ключах» и «отменить» исходного ТЗ (6.2 и 6.3) исключены. Пока существует PENDING, форма «Экспорт» показывает неподтверждённый пакет и действия 7.7; в **режиме инициализации** вопрос не задаётся: доступна только кнопка «Инициализация направления»; подтвердить пакет можно и в любой момент из формы экспорта.

## 7.8. Инициализация направления

1. Инициализация повышает поколение направления, начинает последовательность с единицы и создаёт новую цепочку ключей. Каждая инициализация начинает новое поколение ключей (число поколений не ограничено). Первый пакет нового поколения **всегда полный** и содержит начальный ключ цепочки. Пакет инициализации также получает PENDING (7.5.1); направление размораживается подтверждением этого пакета (7.7.1) или новой инициализацией.
2. Публичные ключи доверия заново не обмениваются.
3. Отметки экспорта направления (карточек и статусов) сбрасываются.
4. Инициализацию запускают HR и Администратор кнопкой «Инициализация направления» на форме «Экспорт» (9.10.2), в том числе когда PENDING нет; доступа к ключам доверия для этого не требуется. Если у направления есть PENDING, он завершается состоянием «заменено инициализацией», так же как при запуске из Настроек. Инициализация также запускается ответом «Не подтверждено» (7.7.2). В **режиме инициализации** ожидаемую инициализацию выпускает кнопка «Инициализация направления». Администратор может также запустить её из Настроек (раздел 13): существующий PENDING направления завершается состоянием «заменено инициализацией»; если файл этого пакета ещё не записан, временная копия этого пакета удаляется; если режим уже включён, действие выпускает ожидаемую инициализацию.
5. После инициализации пакеты прежнего поколения не применяются.
6. Получатель обрабатывает пакет инициализации по 7.20 без отдельного подтверждения самой инициализации (пользователь применяет пакет обычным порядком, 7.16). До плана показывается модальное уведомление (7.15); оно не подтверждает инициализацию. Отказ принять выпущенный пакет инициализации нарушит связь.

## 7.9. История операций

Операции экспорта не удаляются. В истории сохраняются: `package_id`, направление, поколение, последовательность, ключ, состояние (PENDING, CONFIRMED, «заменено инициализацией»), время формирования, время подтверждения или замены, пользователь, причина (если предусмотрена). Записи никогда не удаляются, и их конечные состояния никогда не переписываются; единственное допустимое изменение записи — однократный переход из PENDING в CONFIRMED или в «заменено инициализацией» (время, пользователь). **Режим инициализации** — состояние направления (не операции), хранится в базе данных вместе с историей и не является состоянием операции. История позволяет восстановить состояние обмена после перезапуска.

## 7.10. Независимость направлений и перезапуск

Заморозка по PENDING и **режим инициализации** действуют только для своего направления. Состояние транспорта и неподтверждённых операций хранится в базе данных; после перезапуска PENDING восстанавливается, заморозка продолжается, и **режим инициализации** также восстанавливается.

## 7.11. Основной принцип

Если программа не знает наверняка, что пакет получен, она не продвигает обмен и не использует ключ этого пакета для другого пакета. **Продвижение обмена** означает признание текущих ключей использованными и разблокировку экспорта; оно происходит только в двух случаях: оператор вручную подтвердил получение (7.7.1), либо оператор выполнил инициализацию направления (7.8; прежние ключи считаются использованными, а экспорт разблокируется подтверждением пакета инициализации, 7.8.1). Отметки экспорта (7.4.5) в продвижение обмена не входят. Неопределённость разрешается только явным действием оператора.

## 7.12. Аудит транспорта

События транспорта записываются в Журнал (раздел 8): формирование пакета, переход в PENDING, подтверждение, ответ «не подтверждено», инициализация, полный экспорт, приём, отклонение, применение, повторная доставка принятого пакета, продвижение состояния, повторная запись пакета из временной копии после сбоя, включение режима инициализации, автоматическая смена типа направления при смене домашнего филиала (5.4.7), ручная смена типа направления, загрузка справочников из пакета (5.3.3). Журнал позволяет установить, какое действие выполнено автоматически, а какое явно подтверждено пользователем.

## 7.13. Приём входящего пакета

1. При поступлении пакета программа сначала выполняет **транспортную проверку, не изменяя рабочую базу**.
2. Проверяются: целостность; возможность расшифровки; направление; поколение; последовательность; идентификатор ключа; соответствие ожидаемому состоянию обмена; отсутствие ранее принятого пакета с тем же `package_id`.
3. **Совместимость версий** (14.2.4).
4. **Отправитель не должен совпадать с получателем:** пакет, подписанный собственным `installation_id` (в том числе копией-клоном), отклоняется.
5. **Домашний филиал отправителя** из заголовка сравнивается с типом направления: при расхождении план импорта предупреждает Администратора, что у направления нужно обновить тип (7.2.3).
6. До успешного завершения проверок рабочая база данных не изменяется.

## 7.14. Содержимое пакета

1. Пакет содержит **только записи домашнего филиала отправителя**; чужие записи не ретранслируются (П2).
2. В пакет входят: карточки сотрудников (действующие и архивные, 4.5.5); справочники домашнего филиала (сам филиал, департаменты, отделы, должности, дополнительные виды занятости и статусы); маркер базового набора; служебные признаки «обезличена» и «требует уточнения»; **текущий статус** каждого сотрудника (код, даты, примечание) только для действующих карточек и только если оператор выбрал опцию «Включить текущие статусы сотрудников» (7.4.7); у архивных карточек текущий статус не передаётся. Признак «требует внимания» вычисляется и не передаётся; локальные числовые идентификаторы не передаются (7.14.5).
3. Направление «**внутри филиала**»: карточки передаются полностью, включая чувствительные поля.
4. Направление «**между филиалами**»: те же карточки без чувствительных полей.
5. Не передаются: учётные записи, настройки и профиль компании, история статусов, Журнал, связи идентичности и пометки «Это разные люди»; переводы и языковые пакеты (9.14.7); локальные числовые идентификаторы; вычисляемый признак «требует внимания».
6. Если пакет содержит статусы, получатель добавляет текущий статус в свою историю с пометкой «из импорта» **без дублей**: запись добавляется, только если статус отличается от текущего (код, даты, примечание). Пакет без статусов статусы получателя не трогает. История остаётся локальной. Сроки (просрочка) отслеживаются только для записей своего филиала. Для архивных карточек статус не передаётся и не применяется; история получателя строится из принятых текущих статусов и не копируется.
7. Получатель никогда не хранит чувствительные поля карточки другого филиала, даже если они пришли в пакете; карточка принадлежит другому филиалу, когда её филиал-владелец отличается от домашнего филиала получателя; такие поля отбрасываются, а план импорта показывает предупреждение (7.16.4).

## 7.15. Классификация входящего пакета

После транспортной проверки пакет получает класс:

- **NEW:** ожидаемое поколение и следующая допустимая последовательность;
- **REPLAY:** пакет уже принят ранее (повторная доставка безопасна, база не меняется);
- **STALE:** устаревшее поколение или последовательность, не соответствующая состоянию;
- **ИНИЦИАЛИЗАЦИЯ:** поколение выше локального, последовательность 1, начальный ключ, подпись доверенного отправителя, вид экспорта «полный» (7.20).

После того как пакету присвоен класс ИНИЦИАЛИЗАЦИЯ и до плана импорта (7.16) показывается модальное уведомление: «Отправитель X выполнил инициализацию направления; принимается пакет поколения N. Отказ принять этот пакет нарушит обмен по направлению». Кнопки «Продолжить» и «Отмена». «Отмена» — закрытие без решения (7.16.6): пакет остаётся непринятым, база не изменяется, файл можно открыть снова. Это уведомление не является подтверждением инициализации (7.8.6, 7.20.1). Окончательный отказ — «Отклонить» в плане (7.20.4).

Некорректный пакет не применяется. Пакет нового поколения, не являющийся полным экспортом, отклоняется.

## 7.16. План импорта

После проверок и до изменения базы пользователь видит **план импорта**:

1. Отправитель (копия, филиал, тип направления), **дата и время создания пакета**, дата и время последнего принятого от этого отправителя пакета, вид экспорта, версии.
2. Сводка справочников (3.7) и, при необходимости, диалог 3.7.5.
3. Количество карточек по классам (EXACT, NEW, LOW, AMBIGUOUS, CONFLICT), переходов «архивная ↔ действующая», изменений статусов; строка «статусы в пакете: есть / нет».
4. Предупреждения: возможная двойная занятость и дубли (4.9), конфликт названия филиала (5.2.6), расхождение типа направления (7.13.5), пакет старше последнего принятого, «чувствительные поля карточек другого филиала отброшены (7.14.7)», «чувствительные поля не применены, так как пакет применяет не HR (7.19.6)».
5. Выбор сценария (7.17 или 7.18) и действия «Применить» и «Отклонить».
6. Пользователь вправе отклонить импорт целиком (П6). До решения пакет остаётся непринятым и базу не изменяет; закрытие формы без решения не принимает пакет, его можно открыть повторно.

## 7.17. Сценарий «Последний импорт побеждает»

1. Записи пакета замещают соответствующие локальные записи филиала-источника без вопросов по отдельным записям.
2. Соответствие по `external_id` (4.10.1); карточка замещается целиком, без слияния по полям; состояние «действующая/архивная» передаётся (4.10.8).
3. Карточка с неизвестным `external_id` создаётся как новая; возможные дубли выводятся отчётом (4.9.8, 4.10.6).
4. Локальные записи, которых нет в пакете, остаются; ничего не удаляется (2.4.1).
5. Затрагиваются только записи филиала-источника; записи других филиалов и собственные записи, не относящиеся к источнику, не меняются.
6. CONFLICT (4.10.2; для обезличенной карточки несовпадение ФИО конфликтом не является) и некорректные ссылки (3.6.4) отклоняют импорт целиком.
7. Сценарий предлагается по умолчанию.

## 7.18. Сценарий «Выборочный импорт»

1. Расшифрованный пакет показывается в форме просмотра содержимого (ФИО, филиал, должность, вид занятости, статус, класс сопоставления, состояние); пользователь вручную отмечает записи, которые будут обработаны.
2. Отмеченные записи проходят **обычную обработку**: проверка по справочникам, разрешение LOW и AMBIGUOUS (4.11), предупреждения о двойной занятости.
3. Неотмеченные записи не применяются. **Пакет при этом считается принятым** и повторно не применяется; недостающие записи и статусы неотмеченных записей доставляются полным экспортом без смены поколения (7.4.6) с включённой опцией «Включить текущие статусы сотрудников». Справочники пакета всегда применяются полностью независимо от отметок карточек; обезличивание найденной в пакете обезличенной карточки обязательно и не зависит от отметки её строки (4.10.2). Известная карточка получателя сопоставляется по `external_id` (4.10.1), повторная передача не создаёт дубликат, отсутствующая карточка создаётся по общим правилам сопоставления (4.10), неоднозначные совпадения разрешаются по общим правилам (4.11), а не автоматически.
4. Ошибки пакета (CONFLICT 4.10.2 с учётом исключения для обезличивания, некорректные ссылки 3.6.4 и 4.10.7, конфликт названия филиала 5.2.6) отклоняют весь пакет в обоих сценариях до выбора записей; выбор доступен только для корректного пакета. **Ошибка отмеченной записи:** (1) нарушение формата или отсутствие обязательных полей; (2) неизвестный код значения справочника; (3) запись, противоречащая неизменяемым атрибутам известной карточки (филиал, ФИО, 2.3.2 и 4.4.3). Неразрешённые LOW и AMBIGUOUS ошибкой не являются: применение просто не выполняется, пока пользователь не решит. Ошибка в отмеченных записях отклоняет всю операцию (П6); пользователь может снять отметки и повторить.

## 7.19. Применение пакета

1. Применение атомарно: в одной транзакции выполняются изменения рабочих данных (справочники и записи), фиксация принятия пакета и продвижение состояния транспорта. Невозможна ситуация, когда данные применены, а транспорт считает пакет непринятым, или наоборот.
2. Перед применением создаётся автокопия (6.2); при её неудаче применение не выполняется.
3. Запись в Журнал выполняется после фиксации транзакции (раздел 8).
4. Транспортное состояние направления продвигается **только** после успешного применения. Формирование, шифрование, сохранение или передача пакета продвижением не являются.
5. REPLAY не изменяет базу и не продвигает состояние; пользователь информируется.
6. Чувствительные поля пакета обрабатываются и сохраняются только пользователем с правами HR; при применении пакета Администратором чувствительные поля не применяются, а план импорта и Журнал это показывают; недостающие данные доставляются полным экспортом без смены поколения (7.4.6), который применяется HR.
7. Настроечная операция «Загрузка справочников из пакета» (5.3.3) пакет не принимает: она загружает только справочники (в одной транзакции); не изменяет состояние входящего направления, поколение, ключи и запись о принятии пакета; не создаёт отметку REPLAY и не запускает инициализацию у получателя (7.20), даже если класс пакета ИНИЦИАЛИЗАЦИЯ; пакет остаётся непринятым (класс NEW), пока HR не применит его; операция не является подтверждением доставки и не влияет на PENDING отправителя (7.5). Применение пакета (7.19.1–7.19.5) не изменяется. Операция записывает собственное событие в Журнал; перед ней создаётся автокопия (6.2). Если название филиала в пакете при нормализованном сравнении (5.2.6) совпадает с названием локального филиала при другом `external_id`, операция отклоняется целиком: ничего не загружается, сообщение называет оба филиала; Администратор переименовывает локальный филиал либо, если копия настроена неверно, переустанавливает копию (5.6). Перед загрузкой выполняются те же транспортные проверки, что при обычном импорте (7.13): целостность, расшифровка, формат и версия, подпись доверенного отправителя; затем показывается сводка справочников (3.7) и запрашивается подтверждение; если проверка не пройдена, операция не выполняется и показывается причина. Операция показывает модальное окно прогресса по 9B.5 (этап и таймер). «Отмена» доступна на этапах проверки, пока запись не началась, и недоступна во время записи. Запись — одна транзакция: при ошибке или сбое ничего не изменяется.

## 7.20. Инициализация у получателя

1. Пакет класса ИНИЦИАЛИЗАЦИЯ принимается без отдельного подтверждения инициализации или ключей доверия (достаточно подписи доверенного отправителя). Этап 1: пакет проверяется, строится план импорта и выбирается сценарий; до подтверждения применения пользователем («Применить», 7.16) рабочие данные, постоянное транспортное состояние, поколение, ключи и запись о принятии пакета не изменяются. Этап 2: после подтверждения атомарно выполняются применение данных, запись о принятии пакета и продвижение входящего транспортного состояния (новое поколение, начальный ключ) (7.19.1). План и сценарии импорта те же, что для пакета класса NEW (7.16–7.18); отличие только в том, что поколение и ключи входящего направления продвигаются вместе с применением. Повторная подготовка того же файла до подтверждения постоянное состояние получателя не изменяет.
2. **Оператор уведомляется** модальным окном до плана импорта (7.15); отдельного подтверждения инициализации нет (7.8.6, 7.20.1; пользователь применяет пакет обычным порядком, 7.16): «Отправитель X выполнил инициализацию направления; принимается пакет поколения N. Отказ принять этот пакет нарушит обмен по направлению». «Продолжить» открывает план; «Отмена» закрывает форму без решения (7.16.6).
3. Принять пакет можно при любом более высоком поколении (поколения могли быть пропущены, если у отправителя несколько неподтверждённых циклов).
4. Решение отклонить импорт по содержимому (по 7.16.6) остаётся за пользователем: приёмник при этом не изменяется, а отправителю потребуется выпустить пакет инициализации снова.

## 7.21. Интерфейс транспорта

Операторские формы описаны в разделе 9. Для PENDING интерфейс показывает идентификатор пакета, направление, время создания, поколение, последовательность и информирует, что выпуск пакетов по направлению заморожен (7.6); доступны действия «Подтвердить» и «Не подтверждено» (7.7) (после записи файла пакета, 7.6.2). В **режиме инициализации** интерфейс показывает, что следующий пакет направления будет инициализацией (7.6.4), и доступна только кнопка «Инициализация направления» (9.10.2); если файл последнего пакета не был записан, интерфейс предлагает записать тот же пакет из его временной копии (7.4.4). Ни одно действие не выполняется автоматически. Форма «Экспорт» (9.10.2) запускает выпуск кнопками «Обычный экспорт», «Полный экспорт (без смены поколения)» и «Инициализация направления»; переключателя вида на форме нет.

# Раздел 8. Журнал

## 8.1. Назначение

1. **Журнал** это единственный документ событий программы. Он заменяет «журнал аудита», «журнал безопасности», «журнал действий пользователей» исходного ТЗ; кнопка «Журнал безопасности» становится кнопкой «Журнал».
2. История транспортных операций (7.9) остаётся данными базы, необходимыми для работы обмена. Её события дублируются в Журнал.
3. История статусов (2.4.2) остаётся отдельной. **Назначение статуса в Журнал не записывается**: история статусов сама неизменяема и содержит автора.

## 8.2. Хранение и защита

1. Журнал хранится **вне базы данных**, в отдельном файле в каталоге данных копии. Он не шифруется (см. 8.4): защита правами файла и цепочкой хэшей.
2. Журнал **не затрагивается** резервным копированием и восстановлением (6.8) и не входит в копии.
3. Запись в Журнал возможна и тогда, когда база данных не открыта (отказ по оборудованию, 2.6).
4. Журнал только дополняется. Записи связаны **цепочкой хэшей**, чтобы вмешательство было обнаружимо. Программа не имеет функции изменения или удаления записей Журнала (1.3, П3).
5. Разбиение на файлы по периодам определяет ADR; программа не удаляет файлы Журнала. При поиске записей (в том числе при повторном применении обезличивания, 15.7.6) читаются все файлы Журнала.

## 8.3. Запись Журнала

Каждая запись содержит: порядковый номер, дату и время, пользователя (логин) и роль, тип события, объект (тип и идентификатор, для сотрудников `external_id`), результат (успех или отказ), краткие подробности, хэш предыдущей записи. В записи запуска программы указываются версии (14.2.6).

## 8.4. Что не записывается

В Журнал **не записываются**: пароли, резервные коды, ключи, значения чувствительных полей, **ФИО и иные персональные данные сотрудников** (раздел 15). Объекты идентифицируются `external_id` и кодами.

## 8.5. События

| Группа | События |
|---|---|
| Безопасность | успешный и неуспешный вход, блокировка после ошибок, выход, блокировка сессии (с типом: вручную или по бездействию) и разблокировка, смена пользователя, создание и деактивация учётной записи, изменение роли, сброс и смена пароля, восстановление доступа по резервному коду, изменение настроек безопасности |
| Оборудование и база | открытие базы, изменение одного признака оборудования (допущено), отказ открыть базу (изменение двух и более), запуск программы с версиями, миграция схемы, отказ по несовместимости версий, отказ запуска второго экземпляра |
| Сотрудники | создание, изменение, изменение чувствительных полей, просмотр полного значения чувствительных полей, архивирование, восстановление, обезличивание (`external_id`, кто и когда, перечень стёртых полей без значений), в том числе реплики, обезличенной импортом, и повторное применение после восстановления или возврата; показ HR предупреждения об экспорте обезличенной карточки (15.7.8) |
| Справочники и филиалы | создание, переименование, скрытие записей; создание филиала; назначение и смена домашнего филиала (с перечнем предупреждений); показ и просмотр списка направлений для проверки типов при смене домашнего филиала (5.4.3) |
| Транспорт | события 7.12 |
| Импорт | внешний и локальный: открытие плана, выбранный сценарий, применение, отклонение; решения 3.7.5 и 4.11; создание и отмена связей идентичности; пометки «Это разные люди»; загрузка справочников из пакета (5.3.3) |
| Резервные копии | создание, удаление, восстановление, возврат к автокопии (6.8) |
| Отчёты и шаблоны | загрузка версии шаблона, архивирование, восстановление, формирование, сохранение в файл и печать, подтверждение выдачи персональных данных (11.7) |
| Настройки и язык | изменение настроек и профиля компании; смена языка, изменения в консоли локализации, загрузка языковых пакетов |
| Журнал | обнаружение нарушения цепочки (8.8); печать и сохранение выборки (8.6.3) |

## 8.6. Просмотр

1. Кнопка «Журнал» на верхней панели видна **только Администратору** (1.7).
2. Просмотр только для чтения, с фильтрами по периоду, типу события, пользователю и результату.
3. Результат текущего фильтра можно **распечатать** (системный диалог печати с предпросмотром) или **сохранить в файл** (CSV). Операция доступна Администратору и записывается в Журнал: кто, какой фильтр, сколько записей. Выгруженный файл целостность Журнала не подтверждает; в нём остаются порядковые номера записей для сверки.

## 8.7. Оповещение о нарушении условий использования

1. Событиями, требующими оповещения, считаются: отказ открыть базу данных, изменение признака оборудования, пакет от самого себя, нарушение цепочки Журнала, отказ запуска второго экземпляра.
2. При отказе открыть базу программа показывает пользователю сообщение без технических подробностей и записывает событие.
3. При **следующем входе Администратора** показывается окно извещения со всеми произошедшими с его последнего входа сбоями и нарушениями (в том числе возникшими, пока работал другой пользователь). Окно остаётся, пока Администратор не отметит события как прочитанные; отметка записывается в Журнал.

## 8.8. Целостность Журнала

1. При запуске проверяется цепочка хэшей.
2. Нарушение цепочки или отсутствие файла записывается в новый Журнал (запись «предыдущий Журнал недоступен или нарушен») и вызывает оповещение (8.7). Программа продолжает работу.

## 8.9. Согласованность с базой

1. Запись о событии, изменяющем данные, выполняется **после** фиксации транзакции (7.19.3).
2. Для **критичных операций** (применение импорта, инициализация направления, восстановление, смена домашнего филиала, управление ключами) записываются два события: «начато» (до фиксации) и «завершено» (после). Незавершённая операция остаётся видимой в Журнале как «начато» без «завершено». Для восстановления запись «завершено» пишется после замены базы данных; если сбой произошёл между заменой и этой записью, при следующем запуске программа по маркеру распознаёт уже восстановленную базу и записывает «завершено» (6.5.1).
3. Список критичных операций определяет ADR.

# Раздел 9. Интерфейс

## 9.1. Верхняя панель

Панель не сворачивается. Содержит: логотип компании; название компании, **за ним название домашнего филиала**; название программы; текущие дату и время; имя текущего пользователя; кнопки:

- «Учётные записи пользователей», «Настройки», **«Журнал»**: только Администратор;
- **«?»**: окно «О программе» (14.2.7), для всех ролей;
- **«Заблокировать»**: ручная блокировка сессии (13.2.4), для всех ролей;
- «Сменить пользователя»;
- «Выход».

## 9.2. Панель работы с базой данных

1. Кнопки: «Добавить сотрудника», «Справочник», **«Внешний импорт»**, **«Локальный импорт»**, «Экспорт», «Отчёты», «Шаблоны», «Архив».
2. Администратору и HR показываются все кнопки; Наблюдателю только «Справочник», «Отчёты», «Шаблоны» (1.7).
3. Форма «Резервные копии» вызывается из форм «Внешний импорт» и «Локальный импорт» (6.4); отдельной кнопки нет.
4. В ненастроенной копии (5.3.3) все кнопки, связанные с записями сотрудников, недоступны. У Администратора кнопка «Справочник» при пустом справочнике филиалов открывает модальное окно выбора (5.3.5).

## 9.3. Панель поиска и информации

1. Поле быстрого поиска по ФИО.
2. Обобщённая информация: общее количество действующих сотрудников и количество по статусам в текущей выборке.
3. Быстрые фильтры (кнопки): **«Требуют уточнения»** (карточки после восстановления, 4.8) и **«Требуют внимания»** (просроченный календарный статус, только записи своего филиала).
4. **Счётчик «Возможное двойное числение (N)»** для Администратора и HR (4.9.5).

## 9.4. Панель отображения и фильтрации

1. Режимы «Desk» и «Таблица».
2. Фильтры записей, в том числе **по филиалу**: по умолчанию показывается домашний филиал; записи других филиалов (Администратору и HR) показываются через фильтр и помечаются «только просмотр». Записи чужих филиалов исправить вручную нельзя, только импортом.
3. Рабочее окно показывает только действующих сотрудников.

## 9.5. Режим «Desk» и режим «Таблица»

«Desk» структурированное графическое отображение; таблица с сортировкой, быстрой фильтрацией по столбцам и переходом к форме «Статус». Признаки «требует уточнения» и «требует внимания» отображаются у карточки. Для чужих записей статус (название, цвет) отображается по переводу или так, как пришёл в пакете (3.8.2).

## 9.6. Форма «Статус»

1. Доступна всем ролям; вызывается мышью из «Desk» или таблицы.
2. Показывает краткие данные сотрудника (ФИО, должность, реквизиты) и элементы управления статусом. **Чувствительные поля в ней не отображаются.**
3. Для записей своего филиала пользователь, имеющий право (1.7), назначает статус; для чужих записей форма только для чтения.
4. Примечание к статусу сопровождается подсказкой «без медицинских сведений»; причина отсутствия не фиксируется (15.2).
5. Администратор и HR могут перейти из формы к форме «Карточка сотрудника». Наблюдатель карточку не открывает; нужная ему информация доступна в форме «Статус».

## 9.7. Форма «Карточка сотрудника»

1. Поля по 4.1. **ФИО и филиал недоступны для правки после создания** (4.4.3, 2.3.2).
2. Чувствительные поля показываются только HR и маскированно; просмотр полного значения отдельное действие, записывается в Журнал. У других ролей этих полей на форме нет (4.1.5).
3. Архивная карточка открывается только для чтения.
4. Из формы выполняется архивирование: выбор вида («уволен», «переведён» с филиалом назначения, «ошибочная запись»); восстановление выполняется только из формы «Архив».

## 9.8. Форма «Архив»

1. Доступна Администратору и HR (Наблюдателю нет). Показывает архивные карточки **домашнего филиала** (4.5.4).
2. Поиск, открытие карточки только для чтения, формирование отчёта о деятельности сотрудника в филиале, **восстановление** (4.8) с выбором вида занятости и признаком «требует уточнения», **обезличивание** (только HR, 15.7).
3. Отдельный фильтр «Ошибочные записи» (4.7).

## 9.9. Форма «Справочник»

Вкладки: «Филиалы», «Департаменты», «Отделы», «Должности», «Виды занятости», «Статусы».

1. Для видов занятости и статусов показывается владелец записи и отметка «системная» для базового набора.
2. Записи других филиалов и базовые только для просмотра.
3. В «Филиалах» Администратор создаёт филиал, **назначает домашний** (5.3) и видит предупреждения о смене (5.4.2).
4. Скрытые записи не предлагаются к выбору (3.5.4).
5. В ненастроенной копии с пустым справочником филиалов форма «Справочник» открывается через модальное окно 5.3.5; после загрузки или создания филиалов форма открывается напрямую (5.3.5).

## 9.10. Формы обмена

1. **«Внешний импорт»:** выбор файла, транспортная проверка, **план импорта** (7.16), сценарий (7.17, 7.18), «Применить» и «Отклонить»; доступ к форме «Резервные копии».
2. **«Экспорт»** (Администратор и HR; у Наблюдателя кнопки «Экспорт» нет, 9.2, и форма ему не показывается). На форме: выбор направления; опция «Включить текущие статусы сотрудников» (по умолчанию выключена; действует на все три кнопки, 7.4.7); выбор места сохранения файла; перечень неподтверждённых пакетов с действиями «Подтвердить» и «Не подтверждено» (7.7; эти действия предлагаются только после записи файла пакета, 7.6.2). Переключателя вида на форме нет. Кнопки: «Обычный экспорт», «Полный экспорт (без смены поколения)», «Инициализация направления». Если файл последнего пакета не был записан, форма предлагает записать тот же пакет из его временной копии (7.4.4, 7.21) и до записи не предлагает действия 7.7. «Обычный экспорт»: программа сама выпускает инкрементальный пакет или, где 7.4.5 делает полный обязательным (первый экспорт по направлению, после инициализации, после смены домашнего филиала, после восстановления), полный пакет; форма показывает, какой и почему, например «будет выпущен полный пакет: первый экспорт по направлению», иначе «будет выпущен инкрементальный пакет»; пользователь вид не выбирает. «Полный экспорт (без смены поколения)»: действие 7.4.6, с подтверждением и записью в Журнал. «Инициализация направления»: доступна HR и Администратору, с предупреждением-подтверждением «новое поколение; получатель должен принять пакет инициализации; пакеты прежнего поколения применяться не будут»; это критичная операция (запись «начато» до фиксации, 8.9.2); если у направления есть PENDING, он закрывается как «заменено инициализацией» (как запуск из Настроек, 7.8.4); запускать можно и без PENDING. «Обычный экспорт» и «Полный экспорт (без смены поколения)» доступны, только когда у направления нет PENDING и оно не в режиме инициализации; «Инициализация направления» доступна всегда (HR, Администратор). У недоступной кнопки форма показывает причину рядом с ней. Для направления в режиме инициализации причина у двух первых кнопок — что следующий пакет направления будет инициализацией (7.6.4, 7.21).
3. **«Локальный импорт»:** подпоток ввода неструктурированных данных (раздел 10).
4. Форма «Резервные копии» (6.4).
5. **«Загрузка справочников из пакета»** (5.3.5): диалог выбора пути к файлу пакета; после успешной загрузки программа открывает справочник филиалов для назначения домашнего филиала.

## 9.11. Окна уведомлений и предупреждений

Окно оповещения Администратора при входе (8.7); уведомление об инициализации направления (7.20); экран «копия не настроена» (5.3.3); предупреждение о возможной двойной занятости (4.9.3); предупреждения при смене домашнего филиала (5.4.2); подтверждение возврата к автокопии (6.6.4).

## 9.12. Блокировка сессии

Экран блокировки предлагает «Разблокировать» (пароль текущего пользователя) и **«Сменить пользователя»**: завершить сессию без пароля предыдущего пользователя и перейти к входу. Данные предыдущего пользователя остаются защищёнными; событие записывается в Журнал (#91).

## 9.13. Общие требования

1. Интерфейс поддерживает локализацию на двух и более языках. Поставляются русский и английский. Язык копии устанавливает Администратор в настройках; он действует для всех пользователей копии. Сообщения об ошибках показываются на выбранном языке; для ошибок импорта дополнительно выводится стабильный код.
2. Кнопки отображаются по роли (1.7). Недоступное не показывается, а не блокируется (исключение: ненастроенная копия).

## 9.14. Локализация

1. **Языки.** Поставляются русский (базовый) и английский. Администратор может добавить другой язык через консоль локализации: задать код и название языка и заполнить значения. Для непереведённых значений показывается русский.
2. **Выбор языка.** Один язык на копию; Администратор устанавливает его в «Настройки → Язык». Язык применяется без перезапуска программы; если для отдельного окна это технически невозможно, применяется при следующем открытии окна.
3. **Что локализуется:** все надписи интерфейса (кнопки, заголовки, подписи полей, подсказки, сообщения, окна «?» и уведомлений); заголовки и подписи стандартных отчётов; **названия записей базового набора справочников** (системные статусы и виды занятости, включая «уволен», «переведён», «ошибочная запись»). Администратор может заменить термин интерфейса (например «филиал» на «branch»).
4. **Что не локализуется:** данные пользователей (ФИО, контакты, примечания), название компании, содержимое шаблонов отчётов. Журнал хранит коды событий, а отображает их на выбранном языке. Названия записей справочников, созданных филиалами (филиалы, департаменты, отделы, должности, дополнительные виды занятости и статусы): это данные, они показываются как введены и не переводятся ни в одной локализации; заголовки отчётов следуют языку интерфейса, данные из карточек остаются на языке ввода.
5. **Ключи.** У каждой переводимой величины есть неизменяемый ключ: для надписей идентификатор строки, для записей базового набора неизменяемый `code`. В базе, пакетах и Журнале хранятся ключи и исходные значения, **не переводы**.
6. **Консоль локализации.** Вызывается из «Настроек», доступна только Администратору. Это таблица «ключ, значения по языкам» с фильтрами (язык, вид: надписи или справочники, только непереведённые). Администратор редактирует значения надписей и названий записей базового набора. Изменения сохраняются отдельной кнопкой, применяются без перезапуска и записываются в Журнал.
7. **Переводы локальны для копии** и в пакеты не передаются (как настройки). Базовый набор справочников поставляется с переводами для поставляемых языков; Администратор может переопределить их у себя. Дополнительные записи справочников, созданные филиалами, остаются данными и показываются как введены (3.8.2).
8. **Нет перевода:** показывается значение базового (русского) языка, в консоли оно отмечено как «не переведено».
9. **Форматы** даты, времени и чисел следуют выбранному языку; формат для каждого языка определяет ADR.
10. **Резервные копии:** переводы входят в полное восстановление (6.5) и не затрагиваются возвратом HR (6.6), как настройки.
11. **Языковой пакет.** Набор переводов и названий терминов для одного языка (или его варианта, например «Русский (заказчик)») оформляется как файл с названием, кодом и значениями. Администратор может загрузить пакет в консоли локализации, выбрать его языком копии и выгрузить пакет из консоли. Формат файла определяет ADR. Через такой пакет заказчик заменяет любые термины (в том числе «департамент» и «отдел»).

# Раздел 9B. Окно входа и технические окна

## 9B.1. Последовательность запуска

1. Проверка единственного экземпляра (5.5).
2. **Проверка оборудования** (2.6) до ввода пароля.
3. Проверка цепочки Журнала (8.8); нарушение не блокирует запуск.
4. Проверка версии схемы базы (14.2.3): база новее программы означает отказ.
5. Проверка целостности базы данных.
6. Если Администратор не создан, запускается **мастер первичной настройки** (9B.3); иначе **окно входа** (9B.2).
7. После входа: фон перехода (9B.4), при необходимости миграция схемы с прогрессом и страховочной копией (6.9.2), главное окно.
8. В ненастроенной копии (5.3.3) работает ограниченный режим.
9. Администратору после входа показывается окно оповещения (8.7).

## 9B.2. Окно входа (#85)

1. Полноэкранная заставка: логотип и название компании, название программы, **версия мелким текстом** (14.2.7), поля логина и пароля, **индикатор текущей раскладки клавиатуры**.
2. Сообщение о неверном входе одинаково для неверного логина и неверного пароля.
3. После ошибок срабатывает задержка (13.2.2): окно показывает **обратный отсчёт**; ввод на это время заблокирован.
4. «Восстановить доступ» (ввод резервного кода) доступно только для Администратора (раздел 13).
5. Окно показывается на языке копии (9B.7.3).

## 9B.3. Мастер первичной настройки

Шаги: (1) учётная запись Администратора; (2) показ **резервного кода**, который показывается один раз, с подтверждением, что код сохранён; (3) выбор сценария («первая» или «не первая» установка в филиале); (4) «первая» установка: создание филиала и назначение домашним; «не первая»: настройка транспорта, «Загрузка справочников из пакета» (7.19.7) и назначение домашнего филиала; данные карточек в мастере не загружаются (их применяет HR обычным импортом после ввода в эксплуатацию); (5) итог. Индикатор «шаг N из M». Прерванный мастер оставляет копию «ненастроенной» и безопасно продолжается заново.

## 9B.4. Фон перехода

Между успешным входом и главным окном показывается **фоновое изображение** (заставка программы) с индикатором «Загрузка…» вместо пустого экрана. Переход охватывает открытие базы, загрузку справочников и начального списка, при необходимости миграцию (9B.5).

## 9B.5. Окна прогресса и таймеров

Операция, длящаяся **дольше 2 секунд**, показывает окно прогресса: **этап, прошедшее время (таймер)**, при известном объёме процент.

| Операция | Блокировка интерфейса | Отмена |
|---|---|---|
| Автокопия, ручная и страховочная копии | модальная | да, копия удаляется; для автокопии перед применением означает отмену применения |
| Полное восстановление, возврат к автокопии | модальная | до замены базы да, после нет |
| Транспортная проверка и расшифровка пакета | модальная | да |
| Загрузка справочников из пакета (этапы: проверка, сводка, запись) | модальная | на этапах проверки да, во время записи нет |
| Применение внешнего импорта (этапы: проверка, автокопия, справочники, записи, фиксация) | модальная | до начала фиксации да, во время неё нет |
| Формирование и запись пакета экспорта | модальная | до фиксации (7.4.4) да |
| Локальный импорт: чтение и проверка файла, пакетное применение | модальная | да; пакетное применение прерывается между строками, применённое остаётся |
| Миграция схемы | модальная | нет (страховочная копия создана заранее) |
| Формирование отчётов, поиск по большой базе | модальная | да |
| Печать и сохранение выборки Журнала | модальная | да |
| Применение языка | краткая | нет |

## 9B.6. Временная блокировка функций

1. Окно операции модально: ввод и кнопки остальных окон на время операции недоступны, повторный запуск операций невозможен.
2. Закрытие программы, «Выход», «Сменить пользователя» и ручная блокировка во время операции блокируются с пояснением «дождитесь завершения».
3. **На время операции блокировка по бездействию не отслеживается**: отсчёт приостанавливается и после завершения операции начинается заново.
4. После завершения показывается итог; при ошибке причина и состояние («данные не изменены» или «возвращено к состоянию до операции»).

## 9B.7. Окна отказа и сообщения

1. Единый вид: заголовок, краткая причина понятным языком, что делать, **код события** для обращения в поддержку, кнопка «Закрыть». Технических подробностей не раскрывается (2.6.5). У окна «не удалась миграция» вместо кнопки «Закрыть» кнопки «Повторить» и «Выйти», Журнал доступен для просмотра (6.9.2).
2. Окна: оборудование (2.6); база новее программы (14.2.3); второй экземпляр (5.5); повреждение или ошибка открытия базы (с рекомендацией восстановления из копии); не удалась миграция («данные возвращены в состояние до обновления»); «копия не настроена» (5.3.3); ошибка записи или нехватка места на диске.
3. **Язык окон, возникающих до открытия базы,** определяется небольшим файлом **настроек запуска вне базы**, в который программа дублирует выбранный язык; при его отсутствии используется русский.
4. Все тексты локализуются (9.14); события записываются в Журнал.

## 9B.8. Общие требования

Единый стиль и клавиатурное управление (Enter подтверждает, Esc закрывает неопасные окна и не отменяет критичную операцию).

# Раздел 10. Локальный импорт

## 10.1. Назначение

Локальный импорт это ввод неструктурированных данных (файлы XLSX и CSV) для заведения **новых** карточек сотрудников домашнего филиала. Он не обновляет существующие карточки и не передаёт данные другим копиям: созданные карточки уходят дальше обычным экспортом. От внешнего импорта (пакеты, раздел 7) отличается источником и правилами. Раздел заменяет ADR-0012 и его адденд.

## 10.2. Доступ

Администратор и HR, кнопка «Локальный импорт» (9.2). Наблюдателю недоступен (1.7).

## 10.3. Источник данных

1. Поддерживаются файлы XLSX и CSV. Первая строка файла содержит заголовки.
2. Учитываются только распознанные заголовки; нераспознанные колонки игнорируются.
3. Обязательным для постановки строки в очередь является только ФИО. Строки без ФИО, а также строки, у которых в файле указан филиал, отличающийся от домашнего, **в очередь не ставятся** и сообщаются отдельно (количество и причина).
4. **Проверка кодировки.** Перед постановкой строк в очередь программа проверяет кодировку файла (прежде всего CSV; XLSX хранит данные в Юникоде). Если кодировка не соответствует кодировке программы (UTF-8), программа предлагает преобразовать данные: определяет вероятную кодировку, показывает **предпросмотр первых строк после преобразования** и позволяет выбрать кодировку вручную. Без подтверждённого преобразования ввод не продолжается. Перечень поддерживаемых кодировок определяет ADR; минимум UTF-8 и Windows-1251.
5. Чувствительные колонки файла (домашний адрес, номер страхования) обрабатываются только если импорт выполняет HR; иначе они игнорируются с предупреждением (раздел 15).

## 10.4. Принадлежность и справочники

1. Все создаваемые карточки принадлежат **домашнему филиалу** (2.3). Локальный импорт работает только с записями домашнего филиала: импортировать данные других филиалов этим способом невозможно.
2. Департамент, отдел, должность и вид занятости сопоставляются по тексту (без учёта регистра) с нескрытыми записями базового набора и справочника домашнего филиала (3.8.1). Локальный импорт справочники не создаёт и не изменяет.

## 10.5. Порядок работы

Очередь строк обрабатывается в два этапа: сначала **пакетное применение готовых строк** (10.7), затем **построчный мастер** для оставшихся (10.6).

## 10.6. Построчный мастер

1. Для строки показывается черновик карточки со значениями из файла; пользователь может исправить любое поле до сохранения (карточка ещё не создана, поэтому ФИО правится, 4.4.3).
2. Действия: «Сохранить» (создать карточку) и «Пропустить». Каждое действие выполняется атомарно.
3. Предупреждения о возможной двойной занятости и дубле ФИО (4.9) показываются и **не блокируют** сохранение: решение за пользователем.

## 10.7. Пакетное применение готовых строк (#124)

1. Перед построчным мастером показывается окно со списком **всех** строк очереди, у каждой флажок.
2. Строка **готова к применению** (флажок включён и отмечен по умолчанию), если одновременно: филиал отсутствует в файле или совпадает с домашним; все справочные значения однозначно сопоставлены; обязательные поля заполнены; нет возможной двойной занятости и дубля ФИО (4.9, в том числе в других филиалах).
3. Все остальные строки **требуют проверки**: флажок недоступен, они обрабатываются в построчном мастере.
4. «Применить отмеченные (N)»: перед применением создаётся автокопия (6.2); строки применяются **независимо**, каждая своей транзакцией; ошибка одной строки не прерывает остальные.
5. После применения показывается сводка (создано, ошибок с причиной) и открывается построчный мастер для оставшихся строк.
6. Массового пропуска нет.

## 10.8. Временные данные

1. Очередь строк хранится временно. Прерванный ввод можно продолжить повторным выбором **того же** файла (то же содержимое) в рамках той же авторизации.
2. При входе, выходе и смене пользователя временные данные удаляются. Восстановление очереди после аварийного завершения не гарантируется.
3. Удаление временных данных очереди не является удалением карточек (2.4.1).

## 10.9. Результат и ограничения

1. Созданные карточки обычные: без статуса, принадлежат домашнему филиалу, подчиняются правилам раздела 4.
2. Локальный импорт не изменяет существующие карточки, не создаёт справочники и не передаёт данные в другие копии.
3. События записываются в Журнал (8.5): начало, завершение, количества созданных, пропущенных и ошибочных строк.

# Раздел 11. Отчёты

## 11.1. Назначение

Раздел «Отчёты» формирует стандартные отчёты по данным программы. Доступ определяется правами (1.7): Администратор, HR и Наблюдатель.

## 11.2. Перечень стандартных отчётов

1. «Сводка «сейчас»»;
2. «Отсутствующие за период»;
3. «Временный персонал»;
4. «История по сотруднику»;
5. **«Требуют внимания»** (прежнее название «Требуют уточнения»): карточки с просроченным календарным статусом; имеет параметр «признак»: «требуют внимания», «требуют уточнения» (восстановленные из архива) или оба (по умолчанию «требуют внимания»);
6. **«Краткая сводка доступности персонала»** (11.3.6).

Расширение набора возможно через шаблоны (раздел 12).

Назначение отчётов 11.3.1–11.3.5:

- 11.3.1. Сводка «сейчас»: кто в каком статусе на сегодня.
- 11.3.2. Отсутствующие за период: кто отсутствует в выбранный период.
- 11.3.3. Временный персонал: сотрудники с видом занятости «Временный» и их статусы.
- 11.3.4. История по сотруднику: все назначения статусов выбранного сотрудника за период.
- 11.3.5. Требуют внимания: карточки с просроченным календарным статусом.

## 11.3. Содержание и параметры

Данные по умолчанию: действующие карточки домашнего филиала; «ошибочные записи» исключены. Стандартные отчёты строятся только по данным домашнего филиала; отчёты по записям других филиалов формируются только по шаблонам (12.5).

Общие правила области данных, вывода, локализации, чувствительных полей и маркеров: 11.4–11.8. Отчёты 11.3.1–11.3.5 описаны ниже по единому каркасу; отчёт 11.3.6 описан по собственной структуре. Для отчётов 11.3.1–11.3.5 строки упорядочены по ФИО (Фамилия, Имя, Отчество); при группировке по департаменту сначала идёт департамент. Для «Требуют внимания» порядок — по «Просрочено дней» по убыванию. Шапка как в 11.3.6: название компании, название филиала, название отчёта, дата формирования, применённые параметры. При пустой выборке отчёт формируется с шапкой и строкой «Нет данных по выбранным параметрам»; это не ошибка.

**11.3.1. «Сводка «сейчас»»:**

1. **Состав данных:** данные по умолчанию раздела 11.3, без «ошибочных записей» (11.4.2).
2. **Параметры:** департамент, отдел, статус, вид занятости, группировка по департаменту.
3. **Правила отбора и расчёта:** итог по статусам в конце.
4. **Столбцы:** ФИО, Должность, Статус, Начало, Окончание, Департамент, Вид занятости.
5. **Отображение и экспорт:** как у остальных отчётов, 11.5.
6. **Ограничения по филиалам и доступу:** 11.4.3.

**11.3.2. «Отсутствующие за период»:**

1. **Параметры:** период, департамент, отдел, статус, вид занятости.
2. **Правила отбора и расчёта:** **Правило «отсутствия»** (отчёт «Отсутствующие за период»): отсутствием считается статус с датой окончания (политика даты окончания не равна 0), поэтому в отчёт попадают и собственные статусы филиала.
3. **Столбцы:** ФИО, Должность, Статус, Начало, Окончание.
4. **Отображение и экспорт:** как у остальных отчётов, 11.5.
5. **Ограничения по филиалам и доступу:** 11.4.3.

**11.3.3. «Временный персонал»:**

1. **Параметры:** департамент, отдел, статус.
2. **Правила отбора:** только карточки с видом занятости «Временный» (`temporary`).
3. **Столбцы:** ФИО, Должность, Статус, Дата приёма.
4. **Отображение и экспорт:** как у остальных отчётов, 11.5.
5. **Ограничения по филиалам и доступу:** 11.4.3.

**11.3.4. «История по сотруднику»:**

1. **Состав данных:** включает архивные карточки своего филиала (11.4.1).
2. **Параметры:** сотрудник, период.
3. **Столбцы:** Статус, Начало, Окончание, Примечание, Кто назначил, Источник (локально или из импорта); в заголовке ФИО, должность, вид занятости.
4. **Отображение и экспорт:** как у остальных отчётов, 11.5.
5. **Ограничения по филиалам и доступу:** формируется только для карточек своего филиала (11.4.5).

**11.3.5. «Требуют внимания»:**

1. **Состав данных:** карточки с просроченным календарным статусом; параметр «признак» (определение — 11.2.5).
2. **Параметры:** департамент, отдел, вид занятости, группировка, признак.
3. **Столбцы:** ФИО, Последний статус, Окончание, Просрочено дней, Должность, Департамент; для признака «требуют уточнения»: ФИО, Должность, Департамент, Вид занятости.
4. **Отображение и экспорт:** как у остальных отчётов, 11.5.
5. **Ограничения по филиалам и доступу:** учитывает только записи своего филиала (11.4.4, 9.3.3).

**11.3.6. «Краткая сводка доступности персонала»:**

1. **Шапка:** название компании (профиль), название филиала, «по состоянию на» (дата, длинный формат на языке копии).
2. **Строки:** департаменты и их отделы (строка департамента содержит сотрудников, закреплённых прямо за ним); строки «Не указано» для сотрудников без департамента или отдела (иерархия необязательна, ADR-0008); итоговая строка суммирует все строки.
3. **Столбцы:** «Плановая численность» (3.9.7); «Принято в штат»: все действующие карточки с любым видом занятости; «Доступны в офисе» = принято в штат минус отсутствующие; «Отсутствуют»; затем пары «число и список ФИО» по **всем статусам справочника, кроме «В офисе»**, в порядке сортировки (собственные статусы филиала добавляются автоматически). «Удалённо» входит в «Отсутствуют».
4. **Параметры:** дата; параметр **«Показывать количество по статусам»**, по умолчанию выключен. При выключенном параметре столбцы с числами скрываются, остаются столбцы со списками ФИО; в .xlsx столбцы скрываются, но не удаляются, поэтому формулы «Отсутствуют», «Доступны в офисе» и итогов работают.
5. **Вывод** как у остальных отчётов (11.5); в файле .xlsx вычисляемые столбцы и итоги сохраняются формулами.
6. ФИО в формате «Фамилия И.О.» (маркер `employee.short_name`, 11.8) с запасным значением полного ФИО, если разобрать невозможно.

## 11.4. Область данных

1. Отчёты строятся по **действующим** карточкам; исключение «История по сотруднику» (включает архивные карточки своего филиала).
2. Карточки с видом «ошибочная запись» **исключаются из всех отчётов** (4.7.2).
3. Стандартные отчёты (11.3) формируются только по записям домашнего филиала для всех ролей. Отчёты по записям других филиалов (только данные импортированных реплик) формируются только по шаблонам (12.5) пользователями, которым доступны чужие записи (1.6). Наблюдатель формирует отчёты только по записям своего филиала (1.5).
4. «Требуют внимания» учитывает только записи своего филиала (9.3.3).
5. **«История по сотруднику» формируется только для карточек своего филиала:** история статусов локальна и для чужих карточек недоступна.

## 11.5. Вывод

1. Результат отображается в окне программы в виде таблицы.
2. Пользователь может сохранить отчёт в файл .xlsx, в файл .pdf или отправить на печать (системный диалог печати). Сохранение в PDF не считается отправкой на печать.
3. Содержимое файла и печати соответствует таблице в окне.

## 11.6. Локализация

Заголовки и подписи отчётов формируются на языке копии (9.14); названия записей базового набора справочников показываются по переводам (9.14.3), названия записей справочников, созданных филиалами, показываются как введены (3.8.2, 9.14.4); данные пользователей не переводятся; формат дат и чисел по языку.

## 11.7. Чувствительные поля

1. По умолчанию отчёты и шаблоны чувствительных полей не содержат.
2. Включить их опцией «Включить чувствительные поля» может **только HR**. Администратору и Наблюдателю опция недоступна.
3. При включении показывается **форма подтверждения**: пользователь подтверждает, что формирует и передаёт документ с персональными данными, защищаемыми законом, и совершает действия с ними (юридическая формулировка в разделе 15). Без подтверждения опция недоступна.
4. Подтверждение записывается в Журнал: кто, когда, отчёт или шаблон, параметры, перечень включённых чувствительных полей, число строк.
5. Сохранение отчёта в файл и печать записываются в Журнал: кто, какой отчёт, параметры, число строк.
6. То же правило действует для отчётов по шаблонам (раздел 12): шаблон с маркерами чувствительных полей формируется только HR с этим подтверждением.
7. **Перспектива:** в дальнейшем работа с чувствительными данными (просмотр, правка, включение в отчёты) потребует дополнительной идентификации пользователя аппаратным средством аутентификации и защиты информации. В ТЗ v2 не входит; отдельный issue.

## 11.8. Единый каталог маркеров

1. Стандартные отчёты и шаблоны опираются на **один каталог маркеров**. Стандартный отчёт это предопределённый набор столбцов из каталога; шаблон это пользовательское размещение тех же значений.
2. Каталог строится по структуре данных так, чтобы **не ограничивать создание шаблонов**. Расширение каталога обратно совместимо (контракт 1.x): существующие шаблоны продолжают работать, прежние алиасы маркеров сохраняются.
3. У каждого маркера есть неизменяемый канонический ключ и алиасы (русские и английские); для добавленных языков (9.14) используются канонические ключи.
4. Группы маркеров:

| Группа | Состав (к прежним ключам добавляется) |
|---|---|
| Отчёт (`report.*`) | заголовок, дата и время формирования, период с и по, название компании, домашний филиал, кто сформировал (логин и роль), текст параметров отбора, число строк, версия программы, язык |
| Сотрудник и структура (`employee.*`) | ФИО, `short_name` («Фамилия И.О.»), филиал, департамент, отдел, должность, вид занятости, дата приёма, контакты, примечание, действующая или архивная, причина архивации, филиал назначения (для «переведён»), признаки «требует уточнения» и «требует внимания»; `department.planned_headcount`, `division.planned_headcount` |
| Статус сотрудника | текущий статус, начало, окончание, примечание, дней до окончания, дней просрочки |
| История статусов (`history.*`) | статус, начало, окончание, примечание, кто назначил, источник (локально или из импорта); только для карточек своего филиала |
| Итоги | всего и отсутствуют по филиалу, департаменту, отделу; число по каждому статусу и каждому виду занятости; списки ФИО по статусу с параметром-кодом (`report.status_employees.<код>`), в том числе для собственных статусов филиала |
| Чувствительные поля | домашний адрес, номер страхования (только по 11.7) |

5. Структурные элементы (повторяющиеся строки, именованные блоки) остаются как в ADR-0005.

# Раздел 12. Шаблоны

## 12.1. Назначение и форматы

Раздел «Шаблоны» работает с библиотекой шаблонов отчётов. Поддерживаются шаблоны **Microsoft Excel (.xlsx, .xlsm)** и **PDF**. Значения подставляются в области и поля, предусмотренные шаблоном, по каталогу маркеров (11.8).

## 12.2. Excel и PDF

1. **Excel:** маркеры вида `{{ключ}}` и повторяющиеся строки `{{#ROW}}` по контракту ADR-0005. Формулы внутри строки-образца копируются с пересчётом ссылок.
2. **.xlsm:** макросы **не исполняются и не сохраняются**; результат всегда сохраняется в формате .xlsx.
3. **PDF:** подстановка в поля формы (AcroForm) либо по файлу областей `regions.json`; результат .pdf.
4. Исходный файл шаблона хранится без изменений (побайтно); формирование отчёта исходный файл не меняет.

## 12.3. Библиотека

1. Для шаблона хранится несколько версий. Пользователь с правом управления загружает новые версии, архивирует шаблоны и восстанавливает их из архива.
2. Формирование отчёта выполняется по выбранной **активной** версии; архивированные шаблоны для новых отчётов не используются.
3. **Управляет библиотекой Администратор**; использовать активные шаблоны могут Администратор, HR и Наблюдатель (1.7).
4. Библиотека **локальна для копии**: пакетами не передаётся (каждый Администратор загружает шаблоны сам); входит в полное восстановление (6.5) и не затрагивается возвратом HR (6.6).

## 12.4. Проверка при загрузке

Загрузка отклоняется, если:

1. шаблон содержит маркер, которого нет в каталоге (с перечнем неизвестных маркеров);
2. маркер записан некорректно (незакрытые или одинарные скобки, #36);
3. нарушены правила блоков `{{#ROW}}` (не более одного неименованного на лист, именованные блоки парные);
4. PDF не читается, защищён паролем, не содержит ни полей формы с известными именами, ни действующего `regions.json`.

Проверка выполняется до записи версии в базу. Сообщения об ошибках на языке копии (9.14).

## 12.5. Формирование отчёта (#39)

1. Пользователь выбирает активный шаблон и в **диалоге параметров** задаёт отбор: филиал (по умолчанию домашний), департамент, отдел, вид занятости, статус, период, сотрудник. Параметры, которые шаблон не использует, игнорируются.
2. Данные берутся по правилам 11.4: действующие карточки, «ошибочные записи» исключены; Наблюдатель только по данным домашнего филиала, Администратор и HR могут выбрать любой филиал.
3. Известный маркер без значения заменяется пустой строкой.
4. Ограничение версии 2.0: шаблонные отчёты по другим филиалам строятся по данным реплик на момент последнего импорта; параметра «дата» нет, история чужих карточек недоступна (11.4.5).

## 12.6. Предпросмотр

1. Перед сохранением или печатью пользователь **обязан** открыть окно предварительного просмотра.
2. Из окна просмотра можно сохранить результат в файл (формат как у шаблона: .xlsx или .pdf) или отправить на печать через системный диалог. Сохранение в PDF не считается печатью.
3. Предпросмотр Excel встроенный, приближённый: показывает сформированные значения и структуру и помечен надписью **«оформление может отличаться»**. Итоговым документом является сохранённый файл. Для PDF-шаблонов предпросмотр показывает заполненный PDF, как позволит ADR.

## 12.7. Чувствительные поля

1. Каталог содержит маркеры чувствительных полей; шаблон с такими маркерами при загрузке **помечается** в библиотеке.
2. Такой шаблон формирует **только HR** и только после формы подтверждения (11.7). Администратор и Наблюдатель формировать его не могут; им показывается пояснение.

## 12.8. Журнал и поставка

1. В Журнал записываются: загрузка версии, архивирование, восстановление, формирование отчёта по шаблону, сохранение, печать, подтверждение выдачи персональных данных (8.5).
2. В составе документации поставляются образцы шаблонов и актуальный каталог маркеров (формируется из кода, не вручную).

# Раздел 13. Настройки и учётные записи

## 13.1. Настройки программы: общие правила

1. Раздел «Настройки» доступен только Администратору (кнопка на верхней панели, 9.1) и только при разблокированной сессии.
2. Группы настроек: **«Безопасность»**, **«Профиль компании»**, **«Транспорт»**, **«Язык»**.
3. Каждая группа сохраняется **своей кнопкой**; несохранённые изменения при закрытии окна не применяются; успешное изменение записывается в Журнал (8.5).
4. Управление учётными записями, Журнал и резервное копирование в «Настройки» не входят (учётные записи вызываются отдельной кнопкой верхней панели).

## 13.2. Безопасность

1. **Автоматическая блокировка сессии:** период бездействия в секундах. **Отключить блокировку нельзя**: допустимый период от 30 до 3600 секунд, по умолчанию 300. Изменение применяется к текущей сессии без перезапуска.
2. **Задержка после неуспешного входа или разблокировки:** длительность в секундах. **Отключить задержку нельзя**: допустимо от 1 до 60 секунд, по умолчанию 3. Применяется при последующих неудачных попытках; во время задержки окно показывает обратный отсчёт (9B.2).
3. **Требования к паролю:** минимальная длина 8 символов, максимальная не менее 64; пароль содержит заглавную и строчную буквы (латиница или кириллица), не менее одной цифры и не менее одного специального символа из набора `! @ # $ % ^ & * ( )`; прочие печатные знаки, кроме пробела, допускаются, но требование не выполняют. Требования проверяются при создании записи, сбросе и самостоятельной смене; при нарушении программа указывает, какое требование не выполнено. Временный пароль также должен отвечать требованиям; программа может предложить сгенерированный временный пароль.
4. **Ручная блокировка.** Пользователь любой роли может заблокировать сессию вручную в любой момент кнопкой «Заблокировать» на верхней панели (9.1) и сочетанием клавиш (сочетание определяет ADR). Ручная блокировка действует как автоматическая (9.12): окно блокировки, разблокировка паролем текущего пользователя, «Сменить пользователя»; после неудачной попытки действует задержка (13.2.2). Во время выполняющейся операции ручная блокировка недоступна (9B.6). В Журнал записывается тип блокировки.

## 13.3. Профиль компании

1. Администратор задаёт название компании и **логотип** (PNG или JPEG).
2. **Логотип хранится в базе данных**, а не как путь к файлу (2.8.2). Профиль локален для копии и пакетами не передаётся.
3. Название выводится в верхней панели, за ним название домашнего филиала (9.1); изменения применяются без перезапуска.

## 13.4. Транспорт (#137)

Группа предназначена для настройки доверия и направлений обмена; доступна только Администратору. Состав:

1. **Локальная идентичность:** `installation_id` и отпечаток собственных ключей (для сверки с абонентами).
2. **Регистрация абонента:** загрузка файла публичных ключей абонента с проверкой отпечатков (сверка по внешнему каналу) и указанием филиала абонента.
3. **Направления:** создание исходящего и входящего направления, **тип** («внутри филиала» или «между филиалами», по филиалу абонента, 7.2.3), просмотр состояния (поколение, последовательность, статус, наличие PENDING, режим инициализации), инициализация направления. При создании направления Администратор вводит удобочитаемое имя; программа предлагает «Филиал отправителя → Филиал получателя». Имя локально, в пакетах не передаётся, Администратор может его изменить, оно уникально в пределах копии и показывается в списках направлений и в предупреждениях (5.4.3, 5.4.7).
4. **Закрытие:** закрыть и скрыть направление или ключ абонента; история обмена остаётся (7.9), физического удаления нет.
5. **Выгрузка собственных публичных ключей и отпечатков** в файл. Резервной копии приватных ключей нет.
6. Все действия записываются в Журнал. HR доступа к группе не имеет.

## 13.5. Язык

Выбор языка копии, консоль локализации и языковые пакеты (9.14.6, 9.14.11).

## 13.6. Учётные записи

**Состав записи:** уникальный логин (не изменяется), пароль, роль, признак активности. Роли: «Администратор», «Сотрудник HR» (в тексте «HR»), «Наблюдатель». Учётные записи локальны для копии (1.1.6).

**Создание:**

1. При первичной настройке создаётся Администратор; пароль вводится с подтверждением; формируется **резервный код**, который показывается однократно и подтверждается пользователем как сохранённый.
2. Администратор создаёт учётные записи «HR» и «Наблюдатель». Вторая активная запись «Администратор» не допускается.

**Управление (только Администратор):** просмотр списка, назначение роли «HR» или «Наблюдатель», деактивация и повторная активация, сброс пароля. Удаление учётных записей и изменение логина не предусмотрены. Последнюю активную запись Администратора деактивировать нельзя.

**Пароль:**

1. Пароль хранится только в защищённом виде.
2. **Пользователь любой роли меняет свой пароль самостоятельно** (с вводом прежнего).
3. **Временный пароль:** пароль, заданный при создании записи или сбросе Администратором, временный. Пользователь **обязан сменить его при первом входе**, поэтому Администратор не знает рабочих паролей пользователей.

**Вход и сессия:** при неверных данных не раскрывается, что именно неверно; деактивированная запись не входит; пользователь может завершить сессию или сменить пользователя (9.12); блокировка по бездействию (13.2.1).

**Восстановление доступа Администратора:** по резервному коду, однократному; после использования код недействителен, формируется новый (показывается однократно); пользователь задаёт новый пароль. Восстановление предусмотрено только для Администратора. Если утеряны и пароль, и код, доступ не восстановить: выполняется новая установка (5.6).

**Журналирование:** события записываются в Журнал (8.5); пароли и резервные коды не записываются.

# Раздел 14. Нефункциональные требования

## 14.1. Платформа и установка

1. Программа работает под управлением **Debian 12** на ноутбуках и компьютерах без подключения к сети Интернет. Поддерживаются и тестируются только Debian 12 и Python 3.11.
2. Дистрибутив (пакет `.deb`) содержит всё необходимое, включая Python, и устанавливается автономно (5.1).
3. Для печати используется системная подсистема печати; для сохранения отчётов, шаблонов и пакетов нужен доступ к файловой системе и съёмным носителям.

## 14.2. Версии и совместимость

**14.2.1. Четыре версионные оси**

| Ось | Что это | Где используется |
|---|---|---|
| Версия программы | Строка вида MAJOR.MINOR.PATCH | Окно «?», Журнал, заголовок пакета, резервные копии |
| Версия схемы БД | Номер последней применённой миграции | Открытие базы, резервные копии |
| Версия протокола обмена | Целое число в каждом пакете | Приём пакета |
| Маркер базового набора | Целое число, только растёт | Приём пакета (3.4, 3.7.1) |

**14.2.2. Принципы**

1. Совместимость определяют версия схемы, версия протокола и маркер базового набора. Строка версии программы информационная: она нужна человеку и сообщениям об ошибках.
2. Любое изменение протокола обмена или базового набора повышает соответствующее число и MINOR-версию программы.
3. Базовый набор только растёт: коды не удаляются и не переименовываются.
4. Запуск более старой программы на базе, созданной более новой, не поддерживается.

**14.2.3. Открытие базы данных**

1. Схема базы новее известной программе: программа отказывается открыть базу и сообщает, что нужна более новая версия.
2. Схема базы старше: выполняется миграция; перед ней создаётся **страховочная копия** (6.1.3, 6.9.2). Если страховочную копию создать нельзя, миграция не выполняется, и пользователю сообщается причина. При неудаче миграции база возвращается к страховочной копии (6.9.2). При следующем запуске программа показывает окно с причиной неудачи; доступны только кнопки «Повторить» и «Выйти»; Журнал при этом можно просматривать; число попыток не ограничено. Результат записывается в Журнал.

**14.2.4. Приём пакета**

1. Заголовок пакета содержит версию программы отправителя, версию протокола и маркер базового набора.
2. Приёмник принимает пакет, если версия протокола находится в диапазоне от минимально поддерживаемой (объявляется в каждом релизе) до собственной, а маркер базового набора **не больше** собственного.
3. Иначе пакет отклоняется целиком (П6) с сообщением вида: «Пакет создан программой версии X (протокол P, набор M). Эта копия: версия Y (протокол Q, набор N). Обновите программу в этой копии.»
4. Следствие: копии можно обновлять поочерёдно, начиная с получателей; отправитель более новой версии получателем старой не принимается до обновления.

**14.2.5. Резервные копии.** Каждая копия хранит версию программы и схемы. Восстановление копии с более новой схемой в более старую программу отклоняется (раздел 6).

**14.2.6. Журнал.** В Журнал записываются версии при запуске, обновления схемы и отказы по несовместимости.

**14.2.7. Окно «О программе»**

1. Кнопка «?» на верхней панели, видна всем ролям. Открывает модальное окно.
2. Содержимое: название, версия программы, дата сборки, версия схемы БД, версия протокола обмена, маркер базового набора, домашний филиал. **`installation_id` показывается только Администратору.**
3. Кнопка «Копировать» помещает эти сведения в буфер обмена для обращения в поддержку.
4. Версия программы также выводится мелким текстом на экране входа.

## 14.3. Релизная сборка (#141)

1. Установленный из `.deb` лаунчер **отклоняет** запуск в демо-режиме (параметр `--demo`, переменная окружения) с понятным сообщением.
2. Демо-режим, отключение привязки к оборудованию (2.6.7) и иные средства разработки доступны только в тестовых сборках и **физически отсутствуют** в релизном артефакте.
3. Для релизного артефакта выполняется автоматический packaging-тест, фиксирующий п. 1 и 2.

## 14.4. Масштаб

Программа не вводит ограничений на число филиалов, копий программы, направлений обмена и карточек. Практические пределы определяются ресурсами оборудования (14.5).

## 14.5. Требования к оборудованию

Минимальные, оптимальные и максимальные требования к оборудованию определяются **по результатам разработки и нагрузочных испытаний** на наборах данных разного размера и включаются в документацию. Операции дольше 2 секунд показывают окно прогресса (9B.5). Максимальными считаются объёмы данных, при которых основные операции остаются приемлемыми на рекомендованном оборудовании.

## 14.6. Надёжность

1. Применение пакета и иные изменения данных атомарны (7.19).
2. Авария питания или завершение процесса не оставляет базу в неработоспособном состоянии; незавершённые операции, кроме восстановления, откатываются. Восстановление при сбое завершается вперёд по маркеру (6.5.1) и не откатывается.
3. Один экземпляр программы на базу (5.5); надёжное восстановление и обновление (6.9).

## 14.7. Безопасность: сводка

Шифрование базы (2.1), привязка к оборудованию (2.6), роли (раздел 1), пароли и блокировка (раздел 13), Журнал (раздел 8), чувствительные данные (раздел 15). **Оборудование, на котором работает программа, не имеет сетевого интерфейса. Программа не устанавливает сетевых соединений** и не содержит сетевых функций (телеметрии, обновлений, проверки лицензии); это проверяется тестом. Данные между копиями передаются только пакетами на съёмных носителях. Свойство среды: системные часы не синхронизируются по сети, время создания пакета и записей Журнала показывается как записано, без коррекции.

## 14.8. Локализация

Требования 9.14; все тексты интерфейса, сообщений и справочников локализуются.

## 14.9. Тестирование и сборка

1. Полный набор автоматических проверок выполняется в среде Debian 12 с Python 3.11 (#139).
2. Допускается тестирование в контейнерах; привязка к оборудованию в тестовых сборках может отключаться (2.6.7), кроме тестов самой привязки.
3. Порядок работы: ТЗ v2 → ADR или адденд → issue → код → pull request → человеческий мерж (0.4).

## 14.10. Документация

Руководства пользователя (HR, Наблюдатель) и администратора пишутся после принятия ADR. Обязательные разделы: транспорт и настройка направлений (#137), «Что делать, если пакет потерян» (#138), резервное копирование и возврат, чувствительные данные, каталог маркеров и образцы шаблонов (12.8).

## 14.11. Эксплуатация и диагностика

Сведения для поддержки доступны в окне «?» (копирование); окна отказа показывают код события (9B.7); Журнал доступен Администратору. Дополнительной диагностики по сети нет.

## 14.12. Среда

Минимальное разрешение экрана 1366×768; поддержка раскладок клавиатуры русской и латинской.

# Раздел 15. Персональные данные

## 15.1. Принципы

1. **Минимизация:** программа хранит только данные, нужные для учёта доступности.
2. **Доступ по ролям:** чувствительные поля только у HR (1.7); остальные данные по матрице прав.
3. **Явность вывода:** данные покидают программу только по явному действию пользователя (экспорт пакета, отчёт, печать); сеть не используется (14.7).
4. **Защита хранения:** база и копии зашифрованы (2.1); Журнал не содержит персональных данных (8.4).
5. **Прослеживаемость:** действия с чувствительными данными фиксируются в Журнале.

## 15.2. Классификация данных

| Категория | Данные | Доступ |
|---|---|---|
| Обычные персональные данные | ФИО, должность, департамент, отдел, вид занятости, дата приёма, контакты, примечание | Администратор и HR (правка в своём филиале); Наблюдатель только просмотр основных сведений в форме «Статус» |
| **Чувствительные** | домашний адрес, номер страхования | **только HR** своего филиала |
| Сведения о доступности | статусы и их история | все роли по матрице; статус «Больничный» не раскрывает медицинских сведений и к чувствительным данным не относится |
| Служебные | логины, роли, пароли (в защищённом виде), Журнал (логины, `external_id`, коды) | Администратор |

Примечание к статусу не должно содержать медицинских сведений (подсказка в форме «Статус», 9.6); причина отсутствия не фиксируется.

## 15.3. Чувствительные поля

1. Никакая роль, кроме HR, **не может вводить, просматривать, редактировать и выводить** их в любом виде. «Вывод» означает предоставление человеку.
2. На форме карточки у других ролей поля отсутствуют (не маскированы).
3. У HR поля по умолчанию маскированы; полное значение показывается отдельным действием; просмотр и правка записываются в Журнал.
4. Локальный импорт обрабатывает чувствительные колонки только когда его выполняет HR (10.3.5).
5. Пакеты и резервные копии содержат поля в зашифрованном виде как технические носители; их содержимое Администратору не раскрывается ни в интерфейсе, ни в отчётах.
6. Чувствительные поля пакета применяются и хранятся только HR (7.19.6); получатель никогда не хранит чувствительные поля карточек другого филиала (7.14.7); после смены домашнего филиала чувствительные поля прежнего домашнего филиала остаются в базе данных в зашифрованном виде, недоступны и не стираются (5.4.9).

## 15.4. Передача между копиями

1. Копиям **того же филиала** карточки передаются полностью, включая чувствительные поля; копиям **других филиалов** без них (7.14).
2. Архивные карточки передаются по общим правилам направления (7.14): копиям того же филиала полностью, копиям других филиалов без чувствительных полей; чужие архивные реплики не показываются ни в одной форме (4.5.4).
3. Текущие статусы передаются только если оператор включил опцию экспорта (по умолчанию выключена, 7.4.7).
4. Что не передаётся, определяет единый перечень в 7.14.5 (включая Журнал, учётные записи и настройки).

## 15.5. Вывод в отчётах и файлах

1. Стандартные отчёты и шаблоны по умолчанию чувствительных полей не содержат.
2. Включить их может **только HR** и только через форму подтверждения: пользователь подтверждает, что формирует документ с персональными данными, защищаемыми законом, и совершает действия с ними. Подтверждение, сохранение и печать записываются в Журнал (11.7).
3. Файлы, сохранённые вне программы (отчёты, пакеты), находятся вне её контроля: ответственность за их хранение несёт пользователь.

## 15.6. Хранение и временные данные

1. База данных и все резервные копии зашифрованы; копии привязаны к установке (2.6.6).
2. Временные данные локального импорта удаляются при входе, выходе и смене пользователя (10.8).
3. Журнал и файл настроек запуска не содержат персональных данных (8.4, 9B.7.3).

## 15.7. Обезличивание данных карточки

Карточки не удаляются (П3), но **данные из карточки удаляются**.

1. **Обезличивание** необратимо заменяет персональные значения карточки служебными. Карточка остаётся (`external_id`, филиал, вид занятости, даты, служебные признаки).
2. Допускается **только для архивных карточек своего филиала**; выполняет **HR**.
3. Стираются: ФИО (заменяется служебным значением вида «обезличено»), контакты, домашний адрес, номер страхования, примечание. История статусов сохраняется (она не содержит идентифицирующих данных).
4. Перед выполнением показывается форма подтверждения с предупреждением о необратимости. В форме есть строка: «Копии базы данных, созданные до обезличивания, содержат прежние данные в зашифрованном виде. Если организации нужно удалить сами копии, сообщите Администратору: ручные и страховочные копии удаляет только он». В Журнал записываются `external_id`, кто и когда, перечень стёртых полей (без значений). Запись делается при каждом обезличивании, применённом в этой копии, в том числе для реплики, обезличенной импортом, и при каждом повторном применении после восстановления (15.7.6).
5. **Распространение:** признак «обезличена» передаётся в пакетах; получатель применяет стирание, а не отклоняет пакет по CONFLICT (исключение из 4.10.2). Чужие реплики обезличиваются тоже. Обезличивание является изменением карточки и попадает в инкрементальный экспорт каждого исходящего направления, которое ещё не получило это состояние (7.4.5); при применении импорта стирание обязательно и не зависит от отметки строки (4.10.2, 7.18); чужие карточки не ретранслируются: чтобы филиал A передал свою карточку филиалу V, должно существовать прямое направление A → V, а направление A → B не даёт B права ретранслировать карточку A.
6. **Факт обезличивания** — это дизъюнкция: запись в Журнале **или** признак «обезличена» в базе данных. Обезличивание имеет приоритет над восстановлением: карточка, обезличенная в текущей базе, не получает прежние персональные данные из копии; если в Журнале есть запись об обезличивании, а карточка в базе не обезличена, она обезличивается. После восстановления Администратором программа повторно применяет обезличивание в базе-кандидате до замены (6.5.1) ко всем карточкам, для которых есть запись или признак; после возврата HR обезличивание применяется повторно по 6.6.8. Копии, созданные до обезличивания, хранят прежние данные до вытеснения (автокопии) или удаления Администратором (ручные и страховочные).
7. Основания и сроки обезличивания определяет организация; ТЗ задаёт механизм.
8. При обезличивании HR показывается предупреждение, что обезличенную карточку нужно вскоре экспортировать во все доступные исходящие направления; факт показа предупреждения записывается в Журнал с пользователем и временем и не является подтверждением доставки (8.5).

## 15.8. Законодательство

1. ТЗ задаёт технические механизмы (доступ по ролям, журналирование, ограничение передачи, обезличивание), но не является юридическим заключением.
2. Текст формы подтверждения (15.5.2), основания обработки, сроки хранения и ответы на запросы субъектов данных подлежат согласованию с юристом или ответственным за персональные данные **до релиза**.

## 15.9. Перспектива

Работа с чувствительными данными в дальнейшем потребует дополнительной идентификации пользователя аппаратным средством аутентификации (11.7.7); регистрация носителей и токенов отдельные issue.

## 15.10. Что перенесено из других разделов

1.7 (матрица), 2.8 (профиль), 4.1.5, 4.4.4, 4.5.4–4.5.5, 7.14, 8.4, 10.8, 11.7, 12.7 действуют как часть данного раздела; при расхождении побеждает раздел 15.

# Приложение E. Открытые вопросы и допущения

**Решения, которые остаются за ADR:** формат и сегментация Журнала; формат языковых пакетов; перечень кодировок CSV; сочетание клавиш ручной блокировки; предельный размер и формат логотипа; форматы даты и чисел по языкам; состав факторов отпечатка оборудования.

**Требует внешнего согласования до релиза:** юридическая проверка (15.8): текст формы подтверждения вывода, основания обработки, сроки хранения, обезличивание.

**Определяется по итогам разработки:** минимальные, оптимальные и максимальные требования к оборудованию (14.5).

**Принято по умолчанию без явного ответа:** двухфазная запись критичных операций в Журнал (8.9.2); в 5.4.2 повтор положения из 5.4.7 оставлен как предупреждение; 7.14.5 отдельно не называет библиотеку шаблонов и логотип (о них сказано в 12.3.4 и 2.8.1); остальные пункты подтверждены явно.

**Для проверки Cursor-ом (инвентаризация перед ADR):**

- состав и статусы всех ADR на `master`, включая ADR-0001, ADR-0004, ADR-0006;
- передаёт ли пакет признак «архивная» и применяет ли импорт переходы архивная↔действующая;
- допускает ли код правку засеянных статусов и видов занятости; реальные параметры пяти существующих отчётов;
- правила пароля в коде; кодировки CSV; реализован ли #124; проверяет ли CONFLICT филиал;
- влияние автоинкрементного `id` у `dismissed`; смержен ли PR #119.

**Открытые пробелы аудита ТЗ v2 (предположениями не заполнены; решаются решением владельца, в ADR или при реализации):**

- **Миграция и восстановление:**
  - перечень проверок на шаге «выполняется проверка» (6.5.1);
  - механика миграции при выборочном возврате HR (6.6; для ADR N9).
- **Транспорт:**
  - хранение и контроль целостности временной копии (решается в ADR);
- **Статусы и виды занятости:**
  - коды новых системных видов занятости («Переведён», «Ошибочная запись»): адденд ADR-0011 ещё не создан и блокирует эпик E1 (Приложение D).

**Допущения:** реальных баз нет (схему можно перестроить); оборудование без сети, обмен только носителями; часы не синхронизируются; одна установка один компьютер.

**Принятые риски:** потеря пароля и кода единственного Администратора; расхождение копий между обменами («последний импорт»); клон образа виртуальной машины обходит привязку; Журнал, ручные копии и страховочные копии не входят в обезличивание задним числом. У HR нет просмотра по направлениям обезличивания, ещё не выпущенного в пакет (состояние уходит автоматически со следующим экспортом; сроки выпуска пакетов — работа HR вне программы); шаблонные отчёты по другим филиалам не имеют параметра «дата» и не имеют истории (12.5).

**Не вошло в ТЗ v2:** #44, #87, #88, #118, #121, #147, резервная копия приватных ключей (отменена), групповое разрешение дублей, «Экспорт статусов» для Наблюдателя, права на уровне полей.
