# ADR-0014 — Резервная копия перед применением импорта/конвертации

Статус: Принято (2026-09-28)
Дата: 2026-09-28
Автор: Claude (архитектурный обзор)
Затронутые EPIC: EPIC-018 (конвертация, вкладка «Конвертация данных»), EPIC-021 (приём transport-пакетов, вкладка «Импорт данных», ADR-0013)
Прецедент: `BackupService.restore_backup` (EPIC-012, ADR-0002) уже делает именно это перед восстановлением — не изобретается заново

## Контекст

`BackupService.restore_backup` уже, без вопроса пользователю, создаёт автоматическую резервную копию текущего состояния БД в `default_backups_dir(db_path.parent)` с именем `pre-restore-{timestamp}`, проверяет её (`verify_database_file`) и логирует через `TechnicalEventRepository`, **до** самой замены базы — и только если это прошло успешно, продолжает восстановление. Пользователь ничего не выбирает и не подтверждает отдельно; это встроенная защита, а не опциональная функция.

Найдено при подготовке: у операций импорта/конвертации (`EmployeeConversionService.save_row`, будущий `save_rows_bulk` из ADR-0012-addendum, `TransportImportApplyService.apply_validated_package`) такой защиты нет вообще — они пишут в БД напрямую, полагаясь только на транзакционный rollback при ошибке, но не на резервную копию для отмены уже успешно закоммиченного, но нежелательного изменения (например, ошибочно применённый transport-пакет или неверно сопоставленная строка конвертации, которые прошли валидацию, но по факту не то, что хотел пользователь).

## Решение

Применяется тот же паттерн, что уже есть в `restore_backup`, а не новый: перед точкой невозврата — автоматическая, молчаливая (без выбора каталога пользователем) резервная копия в `default_backups_dir`, с префиксом по операции (`pre-import-…` для transport-приёма, `pre-conversion-…` для batch-применения конвертации), проверка и запись в журнал технических событий **тем же кодом**, что уже использует `restore_backup._copy_live_to`/`verify_database_file` — переиспользуется существующий приватный метод `BackupService._copy_live_to`, либо он становится защищённым/публичным для переиспользования (минимальное изменение видимости, не логики). Если резервная копия или её проверка не удались — операция импорта/конвертации **не выполняется**, ошибка показывается пользователю как есть (без попытки продолжить без копии).

Причина выбрать автоматический, а не запрашиваемый вариант (Johan просил «предлагать» — здесь предлагается альтернатива на решение): ручной запрос каталога и подтверждения на **каждое** сохранение строки конвертации или пакета сделал бы рутинную работу навязчивой (см. открытый вопрос 1 — про частоту). Автоматический вариант без диалога уже есть в проекте как прецедент для восстановления и воспринимается человеком одинаково — «это просто происходит», а не как ещё один клик.

## Явно вне рамок

- Ручное управление местом хранения такой авто-копии — используется тот же `default_backups_dir`, что и для восстановления, без отдельной настройки.
- Автоматическая очистка/ротация старых авто-копий — сейчас её нет и для `pre-restore-*`, значит и здесь не добавляется отдельно; если копится мусор — это отдельная будущая задача, общая для обоих префиксов, не специфичная для этой ADR.

## Решения по открытым вопросам (2026-09-28)

1. **Частота — раз на сессию конвертации + всегда перед приёмом transport-пакета.** Для конвертации: авто-копия создаётся один раз, перед первым `save_row`/`save_rows_bulk` этой сессии импорта (флаг «копия уже сделана для этой сессии» хранится в состоянии сессии/диалога, не в БД — переживать перезапуск приложения ему не нужно, при повторном заходе в тот же файл сессии копия делается заново). Для transport-приёма: копия обязательна перед **каждым** `apply_validated_package`, без исключений — приём чужого пакета не «рутинная построчная работа», а единичное дискретное событие.
2. **Видимость пользователю — как у `restore_backup`, отдельного статус-виджета нет.** Факт создания копии не выводится отдельной строкой (как `BackupOperationsWidget._status`); вместо этого — упоминание в тексте перед самой операцией, тем же стилем, что и confirm-диалог `restore_backup` («Перед заменой будет создана автоматическая копия текущего состояния»). Для конвертации — одна строка в начале сессии («Резервная копия сессии создана»), для transport-приёма — аналогичная строка в сводке экрана подтверждения ADR-0013 перед кнопкой «Применить пакет».
3. **Без отдельного permission-чека.** Как и `restore_backup` не проверяет `Permission.CREATE_BACKUP` (только `RESTORE_BACKUP`), так и здесь: авто-копия — часть операции импорта/конвертации, а не самостоятельное действие пользователя, отдельная проверка прав не добавляется поверх уже существующих `IMPORT_EXPORT`/`MANAGE_EMPLOYEES`.
