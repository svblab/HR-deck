# ADR-0007: Протокол доверенного обмена данными с филиалами (v2)

Статус: Предложено
Дата: 2026-09-07 (пересмотр v2)
Автор: Claude (переработано по итогам архитектурного ревью; см. история
решений в конце документа)
Затронутый EPIC: EPIC-019, EPIC-020

## Контекст

Первая версия этой ADR описывала только конфиденциальность пакета
(шифрование публичным ключом получателя, `SealedBox`). Ревью показало, что
для EPIC-020 («истина в филиале», автоматическое применение без построчного
подтверждения) конфиденциальности недостаточно: нужен полноценный протокол
с четырьмя свойствами.

**Переопределение задачи ADR:** это не «как зашифровать пакет», а «какими
свойствами обладает протокол обмена данными между независимыми копиями
приложения»:

1. **Confidentiality** — посторонний не может прочитать пакет.
2. **Integrity** — пакет нельзя незаметно изменить в пути.
3. **Authenticity** — центр криптографически знает, от какого филиала пакет,
   а не только что «кто-то, у кого есть публичный ключ центра».
4. **Freshness** — более старый пакет не может случайно затереть более
   свежие данные того же филиала.

## Рассмотренные варианты (обновлено)

1. `SealedBox` (анонимное шифрование публичным ключом получателя) —
   **отклонено**. Даёт (1), не даёт (3): любой обладатель публичного ключа
   центра (а он по определению не секрет, рассылается всем филиалам) может
   сформировать пакет, который центр успешно расшифрует, приняв за
   легитимный.
2. Шифрование + отдельная подпись (отдельная пара ключей на аутентичность,
   отдельная — на шифрование) — технически решает задачу, но удваивает
   количество ключевого материала и шагов проверки без выигрыша в
   безопасности по сравнению с вариантом 3.
3. **`nacl.public.Box`** (аутентифицированное шифрование между двумя
   известными сторонами, X25519 + XSalsa20-Poly1305) — выбрано. Для
   вычисления shared secret требуются одновременно приватный ключ
   отправителя и публичный ключ получателя; получатель проверяет тем же
   shared secret (свой приватный + публичный отправителя). Успешная
   расшифровка **криптографически доказывает**, что пакет создан именно
   держателем конкретного приватного ключа отправителя — закрывает (1),
   (2) и (3) одним примитивом, без отдельной подписи.

**Выбор:** вариант 3.

## Модель ключей (пересмотрено)

- **Каждая установка — и центр, и каждый филиал — генерирует собственную
  пару ключей X25519.** Это отличие от v1: раньше только центр имел пару,
  филиалы только импортировали чужой публичный ключ. Теперь симметрично:
  для `Box` обеим сторонам нужна собственная пара.
- Каждой сгенерированной паре присваивается **идентификатор ключа**
  (`key_id`, формат `K-<installation-label>-<YYYY-MM>`, например
  `K-center-2026-09` или `K-tula-2026-09`) — не для секретности, а для
  однозначного выбора нужного ключа при расшифровке, включая архивные после
  ротации (см. ниже).
- Перед генерацией новой пары (первой или при ротации) — обязательное
  предупреждение с объяснением последствий и явным подтверждением
  (без изменений от v1).
- Приватный ключ: **не экспортируется через UI/API/файл и не отображается
  пользователю**; может существовать в оперативной памяти процесса и внутри
  защищённого хранилища `keys.enc` — это единственные два состояния,
  формулировка «никогда не покидает установку» из v1 заменена на эту, более
  проверяемую.
- Публичный ключ — экспортируется в файл, передаётся любым каналом на
  усмотрение пользователя.
- **Модель доверия при импорте чужого публичного ключа — явно фиксируется,
  не подразумевается:** система не проверяет, что импортированный публичный
  ключ действительно принадлежит заявленному филиалу — это ответственность
  администратора, который сверяет ключ по отдельному, не входящему в эту
  систему каналу (телефон, личная встреча, независимо переданный
  контрольный отпечаток ключа). Метка «Филиал Тула» — это **удобное имя
  для человека**, не элемент криптографической проверки. Система для
  внутренней логики использует не изменяемый после создания `branch_key_id`
  (см. формат пакета), метка — только для отображения и может быть
  переименована в любой момент без последствий для протокола.
- **Ротация:** при генерации новой пары старая помечается архивной,
  сохраняется бессрочно по умолчанию. Архивный ключ используется **только**
  для расшифровки уже полученных пакетов, зашифрованных под него —
  выбирается однозначно по `recipient_key_id` в заголовке пакета (см. ниже),
  без перебора. Явное ручное удаление архивного ключа администратором
  возможно; система обязана предупредить: «После удаления пакеты,
  зашифрованные под ключ K-…, станут нечитаемыми, если у вас нет их
  незашифрованных копий или более старой резервной копии `keys.enc`».

## Хранилище ключей и восстановление (пересмотрено)

- `keys.enc` — рядом с `personnel.db`, оборачивается **той же самой**
  процедурой keywrap, что и `personnel.db.keywrap` (тот же код, тот же
  механизм разворачивания паролем учётки/резервным кодом — не новый,
  параллельный механизм).
- **Recovery invariant (явно фиксируется):** восстановление
  `personnel.db` + `personnel.db.keywrap` + `keys.enc` на новой машине
  автоматически восстанавливает и доступ к базе, и способность
  расшифровывать/проверять архивные транспортные пакеты — поскольку это
  один и тот же keywrap-путь, отдельной recovery-процедуры для ключей
  шифрования пакетов не требуется. `BackupService` обязан копировать
  `keys.enc` в каждую резервную копию наравне с `.db`/`.keywrap`.

## Формат транспортного пакета (новое в v2)

Пакет — это два слоя: **незашифрованный заголовок маршрутизации** (нужен,
чтобы получатель нашёл нужный ключ до попытки расшифровки) и
**зашифрованное тело** (полезная нагрузка + подтверждаемые метаданные).

```
TransportPackage (файл на диске)
├── header (открытый текст, JSON)
│   ├── protocol_version: int
│   ├── package_id: UUID4
│   ├── claimed_sender_branch_key_id: str   # "K-tula-2026-09"
│   ├── recipient_key_id: str               # "K-center-2026-09"
│   └── created_at: str (UTC ISO-8601)
└── ciphertext (nacl.public.Box, base64)
    └── (после расшифровки) payload
        ├── sender_branch_key_id: str        # дублируется внутри шифротекста —
        │                                      совпадение с header.claimed_*
        │                                      после успешной расшифровки и
        │                                      есть доказательство подлинности
        ├── source_sequence: int             # монотонный счётчик отправителя
        ├── data_scope: {"all"} | {"period", "from", "to"}
        ├── employees: [ { ... } ]           # см. «Владение полями» ниже
        └── statuses: [ { ... } ]
```

**Процедура приёма:**
1. Прочитать `header` (открытый текст).
2. По `recipient_key_id` найти свой (текущий или архивный) приватный ключ.
   Не найден → отказ с понятной причиной «пакет зашифрован для ключа
   K-…, которого нет в этой установке», без попытки перебора.
3. По `header.claimed_sender_branch_key_id` найти импортированный публичный
   ключ этого филиала. Не найден → отказ, «публичный ключ отправителя не
   импортирован».
4. Попытаться `Box.open()`. Неудача (не тот ключ, повреждён, подделан) →
   отказ, «не удалось подтвердить подлинность пакета», **никаких попыток
   подобрать другой ключ**.
5. Успех — сверить `payload.sender_branch_key_id` (из уже расшифрованного,
   то есть проверенного тела) с `header.claimed_sender_branch_key_id`.
   Совпадение обязательно; несовпадение — отказ (защита от переклеенного
   заголовка).
6. Только после пп. 1–5 — переходить к бизнес-валидации содержимого.

## Идентичность филиала и защита от устаревших пакетов (новое в v2)

- У каждой установки (и центра, и филиала) — стабильный, не меняющийся
  `branch_key_id` (это и есть `key_id` собственной пары шифрования,
  переиспользуется как идентичность источника — заводить отдельный
  identity-идентификатор не требуется).
- `external_id` сотрудника остаётся глобальным UUID4 без составного ключа
  с филиалом — независимая генерация без координации, как и решено в
  ADR-0006 (коллизия статистически пренебрежима). Дополнительно: центр
  хранит для каждого `external_id` **последний филиал, от которого он был
  успешно принят** (не как ограничение доступа, а как сверка): если
  очередной пакет с тем же `external_id` приходит от **другого**
  `branch_key_id`, чем в прошлый раз — не блокировать автоматически, но
  явно отметить в отчёте импорта как предупреждение «сотрудник ранее
  импортировался из другого филиала» для внимания HR.
- **Freshness:** каждая установка ведёт собственный монотонный счётчик
  `source_sequence` (инкремент на каждом экспорте, хранится локально,
  переживает ротацию ключей). Центр хранит по каждому `branch_key_id`
  максимальный успешно применённый `source_sequence`. Входящий пакет с
  `source_sequence` **меньше или равным** уже применённому максимуму для
  этого филиала — расценивается как устаревший и отклоняется целиком, за
  одним исключением: если это **точно тот же** `package_id`, что уже был
  применён — это не «устаревший», а «повтор» (см. идемпотентность ниже),
  обрабатывается иначе, чем просто отказ.

## Идемпотентность и атомарность (новое в v2)

- **Один пакет — одна транзакция БД.** Порядок: расшифровать → проверить
  подлинность → провалидировать содержимое пакета целиком (все строки,
  бизнес-правила: `external_id`+ФИО конфликт и т.д., freshness) → если
  проверка пройдена — одна транзакция, в которой одновременно: применяются
  все принятые строки, записывается факт применения `package_id` и
  `source_sequence`, пишется запись в журнал действий. Всё это — одна
  атомарная единица: либо всё закоммитилось, либо (при сбое/крахе) не
  закоммитилось ничего, и повторный запуск того же импорта проходит с чистого
  листа безопасно.
- **Повторный импорт того же `package_id` (после того как он уже успешно
  закоммичен ранее) — не заблокирован, разрешён явно** (легитимный сценарий
  восстановления после сбоя хоста, как и решено ранее), но должен быть
  **идемпотентным по построению**, а не просто «разрешённым повторением
  того же кода с тем же результатом второй раз»:
  - Создание/обновление сотрудника по `external_id` — естественно
    идемпотентно (то же значение полей просто перезаписывается тем же
    значением).
  - Назначение статуса — **обязано** идти через существующий
    `StatusHistoryService.propose_assign_status`/`assign_status`, не через
    прямую запись — тогда повторное назначение того же периода того же
    статуса естественно не создаёт вторую запись истории (уже
    гарантируется существующей бизнес-логикой сервиса).
  - Запись в журнал действий на повторный импорт — отдельная запись с тем
    же `package_id` и явной пометкой «повторное применение», не
    маскируется под первый раз.
- Строки, отклонённые бизнес-валидацией (конфликт `external_id`+ФИО) — не
  считаются сбоем операции, не блокируют коммит остальных строк пакета,
  фиксируются в отчёте импорта с причиной по каждой.

## Владение полями — whitelist (новое в v2)

Импорт из филиала обновляет **только** перечисленные поля существующей
карточки (при совпадении `external_id`+ФИО). Всё остальное — не трогается:

**Filial-owned (заменяются данными филиала):** ФИО, должность, филиал,
департамент, отдел, тип занятости, контакты, домашний адрес, номер
страхования, текущий статус доступности (через `StatusHistoryService`,
см. выше).

**Local-only (никогда не изменяются импортом):** `id` (локальный
первичный ключ), `external_id` (устанавливается один раз при первом
создании записи, далее неизменяем), `created_at`, `is_archived`
(изменяется только косвенно — через назначение статуса «Уволен/неактивен»,
не прямой записью флага), любые будущие поля-заметки, специфичные для
центра, вся служебная audit-метадата.

Статус «в архиве» **не** передаётся напрямую полем — только как следствие
получения статуса «Уволен/неактивен» через штатный механизм статусов,
который уже автоматически архивирует сотрудника (see Фаза 5 `TESTING.md`).

## Права (без изменений от v1)

- `Permission.MANAGE_ENCRYPTION_KEYS` (новое) — генерация/ротация
  собственной пары, импорт чужих публичных ключей, ручное удаление
  архивных ключей. Только Администратор.
- `Permission.IMPORT_EXPORT` (существующее) — подготовка и приём пакетов
  (использование уже готовых ключей), доступно HR.

## Журнал действий (уточнено)

Каждый экспорт и каждый импорт — отдельная запись. Состав (без самих
персональных данных, только метаданные операции): временная метка,
пользователь, тип операции (экспорт/импорт/повторный импорт),
`package_id`, `sender_branch_key_id`/`recipient_key_id`,
`source_sequence`, результат (успех/отказ и причина), число строк
принято/отклонено.

## Что сознательно остаётся вне рамок этой ADR

- Обратный поток (центр → филиал) — не рассматривается, поток строго
  однонаправленный, как решено ранее.
- Многосторонний конфликт («два филиала одновременно правят одного и того
  же сотрудника») — не решается специально: freshness-механизм (счётчик
  `source_sequence` на филиал) защищает от применения старых данных **того
  же** филиала поверх новых, но не арбитрирует между двумя **разными**
  филиалами, утверждающими разные данные для одного `external_id` —
  это было бы полноценным multi-master merge, явно исключённым
  `ANCHOR_CORE.md` §6. Предупреждение «сотрудник ранее импортировался из
  другого филиала» (см. выше) — это весь объём защиты от этого сценария,
  осознанно неполный.
