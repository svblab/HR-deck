## Контекст

ADR-0010 закрепил `external_id` организационных справочников и сотрудника и оставил справочники значений вне обмена. ТЗ v2 это исключение снимает (3.2.2; Приложение A, строка 9; Приложение B, строка ADR-0010). Ссылка в пакете — пара «владелец плюс `code`»; у базового набора владельца нет (3.6.1). Локальный `id` в пакет не входит (3.6.2).

Принятый аддендум ADR-0011 §5 оставил этому файлу: обмен справочников значений, ссылку «владелец плюс код», статус в пакете и архивные реплики, уникальность названий филиала, формат кода дополнительной записи (3.5.2), issue #155. Там же названы имя поля, порядок «справочники до сотрудников» (3.7), старый пакет с целым id (14.2.2), отказ при отсутствии кода (3.6.4), филиал назначения как `external_id` (4.10.7) и отдельное поле «архивная» (4.10.8).

## 1. Что в ADR-0010 перестаёт действовать

При расхождении с ТЗ v2 действует раздел ТЗ. Старая формулировка нормой не остаётся.

| Было в ADR-0010 | Действует |
|---|---|
| Справочники значений вне набора обмена (часть 3; комментарий `directory_sync.py:155-161`; `SYNCED_TABLES`) | 3.2.2: виды занятости и статусы передаются как данные филиала-владельца |
| Ссылка на вид — сырое `employment_type_id` | 3.6 и Приложение A, строка 10: код; локальный id не передаётся. Issue #155 закрывает та же норма |
| Имя филиала не создаёт конфликта (часть 2 распространяла «имя не идентичность» на справочники; пример «Секретарь» — про должность) | Для филиала имя уникально (3.9.6, 5.2.6). Пример «Секретарь» для должностей разных филиалов остаётся |
| Состояние карточки можно было бы вывести из вида | 4.1.4 и 4.10.8: состояние передаётся отдельно. Канон архива — `is_archived` (аддендум ADR-0011 §3) |

Остаётся в силе, этот файл это не переписывает:

- часть 1 ADR-0010 (должность принадлежит филиалу);
- `external_id` филиала, департамента, отдела, должности и сотрудника;
- сопоставление организационных справочников по `external_id` (3.6.3);
- часть 4, пункты 3–4 (предпросмотр требований должности и отказ пакета, если пострадал бы активный сотрудник) — для организационных справочников. К справочникам значений они не применяются. Отношение к 3.7.4–3.7.5 — решение Maintainer 2026-10-27, пункт 2.

## 2. Что входит в пакет

Две группы (3.2).

**Организационные** строки по-прежнему сопоставляются по `external_id`. Этот файл их состав не расширяет плановой численностью (3.9.7 остаётся у E1-11 и аддендума ADR-0005).

**Справочники значений** — таблицы пакета `employment_types` и `availability_statuses`. В них только дополнительные записи домашнего филиала отправителя (3.5, 7.14.1, 7.14.2, П2). Базовые строки в таблицы не кладутся и пакетом не изменяются (3.4, 3.7.3). Совместимость базового набора — маркер в заголовке (7.4.2, 14.2.1, 14.2.4). Число маркера назначает ADR N4, не этот файл.

Строка справочника значений не содержит локальный `id` (3.6.2, 7.14.5).

Ключ таблицы, которой в пакете нет, ничего в этом справочнике не меняет. Пустой список тоже не скрывает и не удаляет локальные строки: скрытие — только признак в пришедшей строке (3.5.4, 3.7.5, 2.4.3). Как таблица отбирается в пакет (водяной знак части 3 ADR-0010 или отметки 7.4), этот файл не меняет: отметки экспорта остаются у аддендума ADR-0007 (Приложение B).

Поле порядка не задаётся: столбец вводит E1-08, здесь он не проектируется. Пока столбца нет, строка вида поле порядка не содержит.

## 3. Формат кода дополнительной записи (3.5.2)

Решение Maintainer от 2026-10-25: формат задаёт этот аддендум. Один формат у видов и у статусов: оба справочника уже приводят код через strip и нижний регистр (`src/services/directories.py:518-521`, `src/services/availability_statuses.py:183-186`).

После strip и перевода в нижний регистр код — один токен `^[a-z][a-z0-9_]*$`. Пустая строка отвергается. Буквы только латинские, как ряд 3.4 и коды `transferred`, `erroneous` аддендума ADR-0011. Верхний регистр на входе приводится к нижнему; сравнение резерва — casefold, как `is_system_employment_type_code` (`src/domain/employment_types.py:21-22`).

Резерв вида (дополнительной записи с таким кодом нет ни у какого владельца):

```text
staff, temporary, contractor, dismissed, transferred, erroneous
```

Шесть имён — аддендум ADR-0011 §2. В коде множество пока из четырёх (`src/domain/employment_types.py:9`); этот файл состав не сужает.

Резерв статуса:

```text
office, remote, trip, sick, vacation, day_off
```

`inactive` удалён (`src/data/migrations/0016_remove_inactive_status.sql:4`) и в 3.4 его нет: ни резерв, ни базовая строка.

Резерв свой у каждого справочника. Код `staff` как статус резервом вида не занят: ссылка всегда знает справочник.

Уникальность дополнительной записи — пара «владелец плюс код» (3.5.2), не глобальный `code`. Два филиала могут иметь один и тот же дополнительный код. Глобальный `UNIQUE` (`0001_initial_schema.sql:64`, `:74`) этому противоречит и подлежит замене. Карточка схемы — не этот файл.

## 4. Владелец в базе

Базовый набор никому не принадлежит (3.4, 3.6.1). Дополнительная запись принадлежит одному филиалу (3.5.1).

Столбец `owner_branch_id INTEGER NULL REFERENCES branches(id)` в `employment_types` и в `availability_statuses`. NULL — базовая строка. У дополнительной строки значение обязательно.

В SQLite NULL в одном UNIQUE не равен другому NULL. Поэтому два частичных уникальных индекса на каждую таблицу:

- `code` при `owner_branch_id IS NULL` — базовые коды уникальны;
- `(owner_branch_id, code)` при `owner_branch_id IS NOT NULL` — код уникален у владельца.

Миграцию этот файл не содержит и не проектирует. Внешние ключи не отключаются (2.4.5). `ON DELETE` не добавляется: в `0001` его нет, запись со ссылками не удаляется (2.4.3).

Снятие столбцового `UNIQUE` у `code` (`0001_initial_schema.sql:64` и `:74`) в SQLite требует перестройки таблицы. `PRAGMA foreign_keys=OFF` не применяется (2.4.5). Карточка схемы должна доказать безопасный способ. `PRAGMA defer_foreign_keys` внутри транзакции — кандидат, здесь не выбран.

Поиск базовой строки — `code` и `owner_branch_id IS NULL`. Поиск дополнительной — пара. Поиск только по `code`, как `get_by_code` сейчас (`src/data/directories.py:427-430`), пару не различает.

## 5. Имена полей ссылки на строке сотрудника

Плоские ключи, как у уже существующих `branch_external_id` и `position_external_id`.

| Ключ | Правило |
|---|---|
| `employment_type_code` | обязателен |
| `employment_type_owner` | `external_id` филиала. Для базового набора ключ отсутствует (3.6.1). JSON null равносилен отсутствию |
| `transfer_target_branch_external_id` | филиал назначения. Нет локального значения — ключ отсутствует или null |
| `is_archived` | обязателен. JSON true — архивная, false — действующая |
| `status_code` | только вместе с блоком статуса, §7 |
| `status_owner` | как `employment_type_owner`, для статуса |
| `status_start_date`, `status_end_date`, `status_note` | даты и примечание текущего статуса. Конец и примечание могут быть null |

Запрещены и отклоняют пакет, даже если код рядом указан: `employment_type_id`, `transfer_target_branch_id`, `status_id`. Локальный id между копиями не сопоставляется (2.2.1, 3.6.2, 4.14). Issue #155 — про первый из этих ключей.

Сериализация пакета — JSON (`src/services/transport_operator.py:104`). Признак архива в выгрузке — JSON true/false, потому что в записи это `bool` (`src/data/employees.py:27`).

`transfer_target_branch_id` в базе задаёт аддендум ADR-0011 §3.2. В пакете то же значение — `external_id` филиала (4.10.7, 4.14). Поле справочное (4.6.5, 4.12): получатель разрешает его в локальный id и сохраняет. Карточку в другом филиале оно не создаёт и не восстанавливает.

По 4.10.7 неизвестный `transfer_target_branch_external_id` отклоняет пакет целиком. Карточка «переведён», чей филиал назначения у получателя нет ни в пакете, ни локально, останавливает весь пакет. Это следствие 4.10.7, не новое правило.

## 6. Справочники до сотрудников (3.7)

Порядок в одной транзакции применения (3.7, 7.19.1). Родители раньше детей, как план сейчас (`src/services/directory_sync_import.py:166-173`), затем справочники значений, затем сотрудники. Код уже применяет организационные строки раньше сотрудников и фиксирует оба плана одним сохранением (`src/services/directory_sync_import.py:196-223`). Справочники значений встают в этот же порядок, после должностей и до сотрудников: владелец строки — филиал, филиал уже сопоставлен.

1. Совместимость версий — 14.2.4. Несовместимый пакет отклоняется целиком, до записи (3.7.1).
2. Сводка по записям вне базового набора: добавлено, изменено, скрыто; у изменённых — «локально» и «в пакете» (3.7.2).
3. Базовый набор не меняется (3.7.3).
4. Новые строки и обновления справочника другого филиала применяются без вопросов, сводка есть (3.7.4). «Другой» — `owner_external_id` не равен `external_id` домашнего филиала этой копии. До этого пункта строка справочника значений доходит, только если её владелец равен домашнему филиалу отправителя из метаданных (решение 4, §11). Иной владелец пакет отклоняет; то, что такой филиал есть локально, строку не проводит.
5. Диалог 3.7.5 — если у существующей строки домашнего филиала содержание в пакете иное. Выбор: заменить (добавить, обновить или скрыть по паре «владелец плюс код»; локальных строк, которых в пакете нет, не скрывать, 2.4.3) либо отклонить импорт целиком (П6). Новая строка домашнего филиала сама по себе диалог не открывает: она входит в сводку «добавлено». Отклонить весь импорт пользователь может всегда (7.16.6).
6. Решение диалога пишется в план импорта и в Журнал (3.7.6). Имя события Журнала этот файл не назначает.

Содержание вида — `name` и `is_archived`. Содержание статуса — `name`, `end_date_policy`, `color_hex`, `sort_order`, `is_archived`. Код и владелец — идентичность, не обновление. Смена кода в пакете не выражается: другая пара — другая строка.

Операция «Загрузка справочников из пакета» (5.3.3, 7.19.7) загружает и эти две таблицы: это справочники. Строки сотрудников она не применяет. Пакет не принимается. Домашний филиал ещё не назначен, поэтому диалог 3.7.5 на этой операции не возникает; подтверждение операции — то, которое уже описано в 7.19.7. Конфликт названия филиала отклоняет операцию целиком (7.19.7).

## 7. Текущий статус в пакете

Каталог дополнительных статусов (§2.2) едет как справочник всегда. Текущий статус карточки едет только если включена опция «Включить текущие статусы сотрудников» (7.4.7). По умолчанию опция выключена: ключей статуса на строках нет, статусы получателя не меняются (7.4.7, 7.14.6).

Опция включена:

- у архивной карточки ключей статуса нет (7.14.2). Ключ статуса на архивной строке отклоняет пакет;
- у действующей карточки, для которой текущий статус есть, строка несёт код, владельца (если запись не базовая), даты и примечание (7.14.2). Текущий статус в коде — период, покрывающий дату (`src/domain/status_assignment.py:265-277`);
- у действующей карточки без такого периода ключей статуса нет. Получатель историю этой карточки не дополняет и не стирает (2.4.2).

История отправителя не копируется (7.14.5, 7.14.6). Получатель добавляет одну запись своей истории, если код (пара «владелец плюс код»), даты и примечание отличаются от текущего. Совпадают — запись не добавляется (7.14.6).

Пометка «из импорта» (7.14.6) хранится на этой новой строке истории. Столбца сейчас нет (`src/data/migrations/0001_initial_schema.sql:102-111`). Предлагаемый столбец: `status_history.from_import INTEGER NOT NULL DEFAULT 0` со значениями 0 и 1. Локальное назначение пишет 0. Импорт пишет 1. Имя входит в предложение; карточек этот файл не создаёт.

Какие карточки попадают в инкрементальный пакет, решает 7.4.7. Таблицу отметок этот файл не вводит.

Скрытый статус, уже стоящий на карточке источника, в пакете разрешается и применяется. Запрет 3.5.4 — про новый выбор в интерфейсе, не про реплику.

## 8. Архивная реплика и отдельное поле

`is_archived` обязателен на каждой строке сотрудника (4.10.8). Отсутствие ключа — некорректный пакет (7.18.4), не значение «действующая». Нынешнее чтение подставляет false (`src/services/employee_sync_import.py:675`); нормой это не остаётся.

Состояние применяется к реплике с тем же `external_id`: архив источника делает реплику архивной, восстановление — действующей (4.10.8). Архив из кода вида не выводится (4.1.4; аддендум ADR-0011 §1 и §3).

Входящая архивная карточка с неизвестным `external_id` принимается как архивная реплика. Подбор по ФИО для неё не выполняется (4.10.9). Сейчас классификатор после промаха по `external_id` всегда ищет кандидатов по имени (`src/services/employee_reconciliation.py:61-71`), среди действующих (`:95`). Это расхождение с 4.10.9; норма — 4.10.9.

CONFLICT по ФИО и филиалу (4.10.2, 15.7.5) остаётся в аддендуме ADR-0011. Этот файл его не сдвигает.

## 9. Старый пакет с целым id (14.2.2)

Смена состава пакета — изменение протокола (14.2.2.2). Число протокола и число маркера назначает ADR N4 / E5 (решение Maintainer 2026-10-25, пункт 4; аддендум ADR-0011 §6). Этот файл `TRANSPORT_PROTOCOL_VERSION` не меняет. Маркер базового набора и версия протокола — разные оси (14.2.1): дополнительные записи маркер не увеличивают.

Пакет, который проверка 14.2.4 пропустила, всё равно отклоняется целиком, если строка сотрудника несёт `employment_type_id` или не несёт `employment_type_code` (3.6.2, 3.6.4, П6). Таблицы «целое id → код» нет. Совпадение id 1–3 в посеве (`0001_initial_schema.sql:167-170`) правилом приёма не является: id дополнительной строки и id посева `dismissed` (`0017_employment_type_archive_semantics.sql:6-8`) между копиями общим идентификатором не являются. Рабочих баз нет (2.9.1). Переходный разбор целого id не вводится.

Сообщение о несовместимости версий (14.2.4.3) остаётся за диапазоном протокола и маркера. Отказ из-за целого id — отказ по ссылке (3.6.4), не подмена текста 14.2.4.3.

## 10. Уникальность названия филиала

Название филиала уникально (3.9.6, 5.2.6), в том числе у скрытого (5.2.7). Запрещены создание с занятым названием, переименование на занятое название и приход по импорту филиала с занятым названием при другом `external_id` (3.9.6, 5.2.6). Импорт и операция 7.19.7 в этом случае отклоняются целиком (П6); сообщение называет оба филиала (7.19.7). Тот же `external_id` может переименоваться на свободное название. Совпадение названия у того же `external_id` конфликтом не является.

Сравнение названия филиала — отдельная функция. Её использует E1-10 (решение Maintainer 2026-10-27, пункт 1). `normalize_name_for_match` (`src/domain/employee.py:100-102`) и правило ФИО (4.9.1) не меняются. Форм нормализации Unicode сверх шагов ниже нет.

Шаги, по порядку:

- strip;
- casefold;
- «ё» заменяется на «е» (после casefold «Ё» уже «ё»);
- каждый подряд идущий отрезок пробельных символов Unicode внутри названия, включая NBSP и табуляцию, схлопывается в один пробел.

«А Б» и «АБ» — разные названия. План импорта сейчас сравнивает название посимвольно (`src/services/directory_sync_import.py:276`); это факт, не это правило.

## 11. Когда пакет отклоняется целиком

П6, 3.6.4, 4.10.7, 7.17.6, 7.18.4. Отказ до записи. Частичного применения нет.

Справочник значений:

- нет обязательного поля §2;
- код не проходит §3;
- дополнительный код равен резерву своего справочника;
- у строки нет `owner_external_id`, либо `owner_external_id` не равен `external_id` филиала, названного домашним филиалом отправителя в метаданных пакета (7.4.2, 7.14.1 п.1, П2, решение 4). Филиал, который есть локально или строкой в этом пакете, но не является этим домашним филиалом, строку не делает действительной;
- одна и та же пара «владелец плюс код» в таблице пакета дважды;
- в строке есть `id` или `archives_record`;
- пара есть у получателя как базовая, а пакет несёт её как дополнительную, или наоборот.

Ссылка карточки:

- нет `employment_type_code` или нет `is_archived`;
- есть запрещённый целый ключ §5;
- пара вида или статуса не находится ни в пакете, ни в базовом наборе, ни локально;
- у базового кода указан владелец;
- у дополнительного кода владелец не указан (совпадение голого кода с чужой дополнительной строкой ссылкой не является);
- `employment_type_owner` или `status_owner` указан и не равен `external_id` домашнего филиала отправителя из метаданных (решение 5). Нет владельца — базовый набор, это не отказ. Иной владелец отклоняет пакет целиком, даже если запись с этим владельцем есть локально (4.10.7, 3.6.4, П6). Это чтение Maintainer 3.8.1, 7.14.1 п.1 и 4.10.7, не правка ТЗ: ТЗ «противоречивый объект» не определяет;
- `transfer_target_branch_external_id` указан и филиал не находится ни в пакете, ни локально;
- у архивной строки есть ключ статуса;
- опция статусов выключена (ни на одной строке нет ключей статуса), а на строке ключ статуса есть. Признак «статусы в пакете: есть / нет» (7.16.3) выводится из наличия ключей, отдельное поле заголовка этот файл не вводит.

Название филиала — §10.

Строка полезной нагрузки, которая не является объектом JSON, делает пакет некорректным (7.15). Сейчас разбор оставляет только объекты и прочие элементы списка отбрасывает (`src/services/transport_import_validation.py:186`). Норма — отказ целиком, не пропуск строки.

## 12. Граница

Этот файл не меняет коды, посев, три архивирующих вида, неизменяемость ФИО и филиала, CONFLICT 4.10.2 / 15.7.5 и столбец `transfer_target_branch_id`. Ссылка базового набора — код без владельца (3.6.1). Это уже принято аддендумом ADR-0011.

Не входит, и в этом файле нормой не становится:

- дата окончания и цвет вида занятости (открытый пункт аддендума ADR-0011; 3.8.2 для вида здесь не закрывается);
- столбец порядка видов (E1-08);
- плановая численность (E1-11);
- число маркера и число протокола (N4, E5);
- отметки экспорта и водяные знаки (аддендум ADR-0007);
- правка `ANCHOR_CORE.md`, issue Приложения C, карточка E0-02, `VERIFIER.md`, одобрение CI для E0-02;
- правка Приложения D. Аддендум ADR-0011 не был молчаливой правкой Приложения D; этот файл тоже не правит ТЗ. Строка «Блокер E1» меняется только человеком, версией ТЗ 2.1.

Файлы карточек E1-01…E1-11 не создаются. Выполнение E1 ждёт принятия этого аддендума (Приложение D; решение Maintainer 2026-10-25). Список карточек в аддендуме ADR-0011 §7 не переписывается. Принятие этого файла снимает блокер нормы для уже названных там E1-08, E1-09 и E1-10; статус `ready` ставится отдельным docs-PR после принятия, не этим файлом.

Локальный `id` в строках организационных справочников и сотрудника сейчас выгружается (`src/services/directory_sync.py:85`, `:106`, `:121`, `:148`). Норма — 7.14.5: локальные числовые идентификаторы в пакет не передаются. Этот файл код не меняет. Снятие ключа `id` у этих строк — карточка формата пакета и номера протокола (ADR N4 / E5), вместе со сменой версии протокола, не E1. Предусловие той карточки — решение Maintainer 2026-10-27, пункт 3. Целые ключи §5 этот файл по-прежнему запрещает, и `id` у справочников значений в пакет не входит.

## Рассмотренные варианты

1. Оставить целое `employment_type_id` для посева 1–3. Нет: 3.6.2, Приложение A строка 10, #155. Id расходятся, как только появляется дополнительная строка или посев без фиксированного id (`0017`).
2. Глобально уникальный `code`. Нет: 3.5.2 требует уникальность в пределах владельца.
3. Пустая строка вместо NULL как «нет владельца». Нет: 3.6.1 — владелец не указывается; NULL это выражает. Пустая строка выглядела бы как владелец и сломала бы частичный индекс базовых кодов.
4. Выводить архив из кода вида. Нет: 4.1.4, 4.10.8.
5. Класть базовые строки в пакет. Нет: 3.7.3. Их заменяет маркер.
6. Принимать старый пакет, переводя id 1–3 в код. Нет: §9.

## Решения Maintainer

Дата: 2026-10-27.

1. Сравнение названия филиала (3.9.6, 5.2.6) задаёт отдельная функция. Её использует E1-10. `normalize_name_for_match` (`src/domain/employee.py:100-102`) и правило ФИО (4.9.1) не меняются. Шаги: strip; casefold; «ё» заменяется на «е»; каждый подряд идущий отрезок пробельных символов Unicode внутри названия, включая NBSP и табуляцию, схлопывается в один пробел. «А Б» и «АБ» — разные названия. Форм нормализации Unicode сверх этого нет.
2. Часть 4, пункты 3–4 ADR-0010 остаются в силе для организационных справочников. Это не противоречит ТЗ 3.7.4–3.7.5: те пункты про вопросы пользователю, а часть 4 — про действительность пакета (отказ по П6); предпросмотр требований должности информативен и входит в сводку 3.7.2, это не вопрос.
3. Норма ключей локального `id` в строках организационных справочников и сотрудника — ТЗ 7.14.5: локальные числовые идентификаторы в пакет не передаются. Этот аддендум код не меняет. Снятие ключа делает карточка формата пакета и номера протокола (ADR N4 / E5) вместе со сменой версии протокола, не E1. Предусловие той карточки, на `509675f70f5807d3e8d98921fc0fae4b3cd3b4ba`: поиск по `src` шаблонов `["id"]`, `['id']`, `get("id")` и `get('id')` не нашёл чтения ключа `id` из строки пакета, в том числе в импорте сотрудников. В файлах синхронизации строка `"id"` есть только в выгрузке (`src/services/directory_sync.py:85`, `:106`, `:121`, `:148`). Карточка E5, прежде чем снимать ключ `id`, повторяет этот поиск на тогдашнем текущем коммите.
4. Каждая строка `employment_types` и `availability_statuses` в пакете принадлежит домашнему филиалу отправителя: её `owner_external_id` равен `external_id` филиала, названного домашним филиалом отправителя в метаданных пакета (7.4.2, 7.14.1 п.1, П2). Нарушение отклоняет пакет целиком (П6). Как метаданные называют этот филиал — имя поля и тип значения — здесь не задаётся: это аддендум протокола и заголовка (N4/E5) и работа по идентичности установки. Поле заголовка этот пункт не вводит. Организационные записи идентифицируются по `external_id` (3.2.1, 3.6.3), поэтому сравнение — по `external_id`. Проверка «владелец — строка филиала, присутствующая в том же пакете» не применяется: инкрементальный пакет может не содержать строку филиала. Филиал, который есть локально, но не является этим домашним филиалом отправителя, строку не делает действительной.
5. Ссылка карточки (`employment_type_owner`, `status_owner`) действительна, только если владелец отсутствует (базовый набор) либо равен домашнему филиалу отправителя, названному в метаданных, как в пункте 4. Иной владелец делает пакет некорректным и отклоняет его целиком (4.10.7, 3.6.4, П6). Это чтение Maintainer разделов ТЗ 3.8.1, 7.14.1 п.1 и 4.10.7. ТЗ не определяет «противоречивый объект». Это не изменение ТЗ.

## Последствия

До слияния docs-PR код не меняется. После принятия обмен видов и статусов, ссылка по коду, обязательный `is_archived`, филиал назначения через `external_id` и уникальность названия филиала имеют норму. E1 по-прежнему не начинается, пока человек не примет этот файл. Приложение D само не обновляется.

Целое `employment_type_id` нормой обмена больше не является, со ссылкой на 3.6.2. Часть 2 ADR-0010 про название филиала нормой больше не является, со ссылкой на 3.9.6.

Перестройка таблицы при снятии столбцового `UNIQUE` (`0001_initial_schema.sql:64`, `:74`) остаётся риском карточки схемы: внешние ключи включены, способ не выбран (§4). Неизвестный филиал назначения останавливает весь пакет как следствие 4.10.7 (§5).

Проверка владельца строки справочника значений и ссылки карточки (решения 4 и 5) не может исполняться, пока не приземлится карточка, которая вводит поле заголовка (N4/E5). Карточки E1 это поле не выдумывают. Между E1 и той карточкой получатель не применяет 7.14.1 к этим строкам.

## Как проверяется

При принятии текста поведение программы не меняется. Проверки появятся в карточках после отдельного перевода их в `ready`. Области, не команды:

- формат кода и резерв; два владельца с одним дополнительным кодом; отказ на резервный код;
- частичные уникальные индексы и NULL у базовой строки;
- пакет без `employment_type_id`, с `employment_type_code`; базовый код без владельца; отказ на целое id;
- таблицы значений применяются до сотрудников; чужая строка без диалога; иное содержание домашнего — диалог 3.7.5; отсутствующая таблица ничего не скрывает;
- опция статусов выключена — история получателя прежняя; включена — одна запись с `from_import = 1`, без дубля по коду, датам и примечанию; архивная строка без статуса;
- неизвестный `external_id` и `is_archived` true — новая архивная реплика, без класса LOW по ФИО;
- название филиала после strip, casefold, «ё»→«е» и схлопывания пробельного отрезка Unicode совпало при другом `external_id` — отказ целиком, включая скрытый филиал и операцию 7.19.7; «А Б» и «АБ» отказом не являются;
- строка вида или статуса, владелец которой есть локально, но не является домашним филиалом отправителя из метаданных, отклоняет пакет;
- ссылка карточки, у которой `employment_type_owner` или `status_owner` не равен этому домашнему филиалу, отклоняет пакет; отсутствие владельца отказом не является.
