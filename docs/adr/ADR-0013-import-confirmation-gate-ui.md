# ADR-0013 — Confirmation-Gate UI для приёма transport-пакетов

Статус: Принято
Ревизия: 3 (2026-09-28) — включает решение по `external_id` при `ATTACH_EXISTING` (не переписывается); заменяет все более ранние копии
Дата: 2026-09-28
Автор: Claude (архитектурный обзор), утверждено Johan
Затронутый EPIC: EPIC-021 (вкладка «Импорт данных» в `DatabaseOperationsDialog`)
Зависит от: ADR-0007 v3 (принято), ADR-0007 addendum — generation/epoch (принято 2026-09-28, PR #115/`ae0ee1c`), EPIC-020 020-A..F (весь backend смержен и независимо перепроверен)
Не входит в объём: ADR-0012 addendum (групповое применение при конвертации XLSX/CSV, п.5) — отдельное решение, не принято; ADR-0014 (backup-prompt перед деструктивными операциями, п.6) — отдельное решение, не принято
Открытые вопросы предыдущей версии закрыты 2026-09-28: предпросмотр — отдельное полноэкранное модальное окно; `CONFLICT` осознанно остаётся без пути подтверждения (обоснование см. ниже)

## Контекст

`DatabaseOperationsDialog` (EPIC-021, PR #113) уже несёт вкладку «Импорт данных» как честную заглушку: backend приёма transport-пакетов (EPIC-020, слайсы A–F) полностью реализован и независимо проверен, но нет UI, который проведёт HR/админа от выбора файла пакета до его применения.

Существующий backend уже задаёт три диспозиции после валидации (`TransportImportValidationService.validate_package`):

- `READY_FOR_APPLY` — можно применять сразу;
- `PENDING_CONFIRMATION` — есть строки сотрудников со статусом `LOW`/`AMBIGUOUS` (нет совпадения по `external_id`, но есть 1 или несколько кандидатов по ФИО+орг.юниту);
- `REJECTED` — жёсткий отказ (`CONFLICT`: `external_id` совпал, ФИО — нет; либо structural/validation ошибки).

**Найденный при подготовке этой ADR разрыв**: `TransportImportApplyService.apply_validated_package` и `EmployeeSyncImportService.apply_employee_plan` сейчас **не умеют** принимать пакет, если в нём есть хоть одна запись `LOW`/`AMBIGUOUS` — `_BLOCKING = {CONFLICT, LOW, AMBIGUOUS}` в `employee_sync_import.py` блокирует apply целиком, а `apply_validated_package` требует строго `READY_FOR_APPLY`. То есть сегодня confirmation-gate физически некуда подключить — нужен новый, явно спроектированный механизм передачи решения человека в apply. Это не сторонний баг, а центральная часть того, что проектирует эта ADR.

## Решение

### 1. Сводка + предпросмотр по желанию — отдельное полноэкранное модальное окно

После `validate_package` UI показывает компактную сводку (кол-во справочных записей, сотрудников по операциям create/update, направление обмена, generation/sequence пакета) прямо на вкладке «Импорт данных». Кнопка «Показать подробности» открывает **отдельное полноэкранное модальное окно** (не inline-раскрытие внутри вкладки) с построчным диффом по `DirectoryPlan`/`EmployeePlan`; закрытие окна возвращает на экран сводки без потери состояния. Предпросмотр не обязателен — применение возможно сразу со сводки, если нет `confirmable`-записей.

### 2. Dedup-guard — по одной записи, без группового решения

Новый механизм на уровне сервисов (не на уровне UI-костыля):

- В `domain/employee_reconciliation.py` добавляется:
  ```python
  class EmployeeMatchResolution(StrEnum):
      ATTACH_EXISTING = "attach_existing"  # подтверждено: тот же человек
      CREATE_NEW = "create_new"            # подтверждено: другой человек

  @dataclass(frozen=True)
  class EmployeeMatchResolutionChoice:
      action: EmployeeMatchResolution
      attach_employee_id: int | None = None  # обязателен для ATTACH_EXISTING при AMBIGUOUS
  ```
- В `services/employee_sync_import.py`:
  - `EmployeePlan` получает новое поле `confirmable: list[_EmployeePlanItem]` (статусы `LOW`/`AMBIGUOUS`), отдельное от `conflicts` (остаётся только `CONFLICT` — жёсткий отказ, решения не предусмотрено: `external_id` совпал, но ФИО — нет, это признак повреждённых данных, а не идентичности, и не должен превращаться в UI-тумблер).
  - `build_employee_plan` разносит `_classify`-результаты по трём корзинам вместо одной `_BLOCKING`.
  - `apply_employee_plan(plan, resolutions: dict[str, EmployeeMatchResolutionChoice] | None = None, *, commit: bool = True)`:
    - если `plan.confirmable` непусто и для какого-то `external_id` нет записи в `resolutions` — отказ с явным списком, какие `external_id` не разрешены;
    - `ATTACH_EXISTING` → трактуется как `EXACT`-обновление на `attach_employee_id` (для `LOW` это единственный `matched_employee_id`; для `AMBIGUOUS` — id, который явно выбрал человек из `candidate_employee_ids`, обязан входить в этот кортеж). **Уточнение 2026-09-28:** `external_id` при этом **не переписывается** — `external_id` в проекте write-once при создании (UUID4) и нигде не мутируется; это канонический якорь идентичности, общий для всех направлений обмена данного сотрудника, а не поле одной пары обмена. Молчаливая перезапись сломала бы уже установленные связи с другими партнёрами, которые продолжат ссылаться на старое значение. Практически это означает: обновляются только поля карточки, а сама привязка идентичности не запоминается — при следующем импорте от того же отправителя запись снова покажется как `LOW`/`AMBIGUOUS`. Постоянный ребиндинг `external_id` (и правила для случая нескольких направлений обмена одного сотрудника) — отдельный будущий архитектурный вопрос, не решается в этой ADR;
    - `CREATE_NEW` → трактуется как `NEW`-создание, кандидат игнорируется.
  - `apply_validated_package` (`transport_import_apply.py`) принимает `resolutions` и пробрасывает в `apply_employee_plan`; guard `_guard_ready` расширяется, чтобы принимать `READY_FOR_APPLY` **и** `PENDING_CONFIRMATION` при условии, что все confirmable-записи разрешены.
- UI: экран «Требуется подтверждение» показывает confirmable-записи по одной; для `LOW` — выбор «Это тот же человек» / «Это новый человек»; для `AMBIGUOUS` — список кандидатов (радио-выбор одного) плюс «Это новый человек». Кнопка применения неактивна, пока не разрешена каждая запись.
- Групповое разрешение («принять все как новых» и т.п.) сознательно не делается сейчас — заводится `[Backlog]` issue в `svblab/HR-deck`, привязанный к EPIC-021/EPIC-020, отдельно от конвертации XLSX/CSV.

### 3. Таблица кодов ошибок

- В `transport_import_validation.py` и `employee_sync_import.py` (`_ensure_unique_external_ids`, `_resolve_row` и др.) свободный текст `reject_reasons`/`validation_errors` заменяется на пары `(code, raw_message)` — вводится `domain/import_errors.py` с `class ImportErrorCode(StrEnum)` (`IMP-001`…), стабильный код на каждую ветку отказа.
- UI показывает код + сырое сообщение одной строкой, например: `IMP-014: employee 42 (Петров И.С.) would become invalid`.
- Расшифровка кода, включая примеры, — только в `docs/import-error-codes.md`, не в рантайме.

### 4. Зависимость от ADR-0007 addendum (generation/epoch) — снята

ADR-0007 addendum принят (2026-09-28, `ae0ee1c`). `FreshnessClass`/`ValidationDisposition` в `transport_import_validation.py` уже используют `generation`, доп. работы для этой ADR не требуется — только убедиться, что сводка на шаге 1 показывает generation пакета отдельно от sequence, чтобы reinit-сценарий был виден человеку до применения.

### Явно вне рамок этой ADR

- Постоянная привязка (rebind) `external_id` при `ATTACH_EXISTING` — требует отдельного решения о поведении при нескольких направлениях обмена одного сотрудника (что происходит с партнёрами, уже знающими старое значение); в этой версии `ATTACH_EXISTING` обновляет только карточку, не идентичность (см. п.2 выше).
- П.5 (чекбоксы + групповое «применить одной кнопкой» для конвертации XLSX/CSV, ADR-0012/EPIC-018) — другая вкладка, другой уже закрытый эпик; требует своего ADR-0012-addendum. Не реализуется в рамках задачи по этой ADR.
- П.6 (предложение бэкапа перед импортом/конвертацией) — сквозная тема, затрагивающая обе вкладки; выносится в отдельную ADR-0014.

## Последствия

- UI становится единственным официальным путём запускать приём transport-пакетов; ручной вызов backend для этого больше не нужен.
- Dedup-guard (LOW/AMBIGUOUS) получает первый в проекте механизм передачи решения человека в apply — прецедент, на который можно будет опереться при проектировании ADR-0012-addendum, если п.5 будет принят позже.
- Диапазон изменений выходит за пределы одной вкладки UI: затрагивает `domain/employee_reconciliation.py`, `services/employee_sync_import.py`, `services/transport_import_validation.py`, `services/transport_import_apply.py`, `domain/import_errors.py` (новый), `src/ui/database_operations_dialog.py` (расширяется, не переписывается), `docs/import-error-codes.md` (новый). Это отражено в задаче для Cursor как отдельные чекпойнты, а не один коммит.

## Почему `CONFLICT` остаётся без пути подтверждения (решено 2026-09-28)

Это не пробел в проектировании, а сознательное продолжение уже принятого архитектурного решения ADR-0010, а не что-то новое, придуманное для ADR-0013.

**Что такое `CONFLICT` технически:** локально уже есть сотрудник с таким `external_id`, но ФИО во входящем пакете не совпадает с локальным ФИО того же `external_id` (`services/employee_reconciliation.py::_classify`).

**Ключевая асимметрия, уже зафиксированная и протестированная в ADR-0010** (не изобретается сейчас):

| Сущность | Переименование под тем же `external_id` |
|---|---|
| Справочники (филиал/департамент/отдел/должность) | Автоматически применяется, не конфликт (`test_adr0010_directory_reconcile_by_external_id_updates_name`) |
| Сотрудник | Флагуется как `CONFLICT`, не применяется автоматически (`test_adr0010_employee_reconcile_external_id_name_mismatch_flags_conflict`) |

То есть архитекторы уже осознанно разделили эти два случая: для справочников риск ошибки при автопереименовании низкий (это не персональные данные конкретного человека), а для сотрудников — сознательно строже.

**Почему это не место для UI-подтверждения (в отличие от `LOW`/`AMBIGUOUS`):** у `LOW`/`AMBIGUOUS` совпадения по `external_id` вообще нет — система ничего не знает, и человек лишь помогает установить связь с нуля (риск ошибки: свяжет не того человека, но никого не переименует под чужим существующим ID). У `CONFLICT` связь по `external_id` уже "существует" со стороны отправителя — и если это результат ошибки на стороне отправителя (опечатка, повторно использованный ID, слияние двух разных людей под одним ID), то UI-кнопка «да, это тот же человек, переименовать» тихо перезапишет ФИО **чужого, уже существующего локального сотрудника** — это качественно более опасная ошибка, чем неверная привязка новой записи. `docs/adr/ADR-0010-addendum-020d-plan-apply-split.md` явно фиксирует это как решение уровня человека-архитектора: «no auto conflict resolve, whole-package reject/pend» — то есть весь пакет должен быть отклонён или отложен целиком, без частичного авто-разрешения конфликта.

**Итоговое решение ADR-0013:** `CONFLICT` остаётся хард-реджектом всего пакета, без UI-подтверждения. Путь исправления — вне sync-потока: либо источник поправляет данные и переэкспортирует, либо HR/админ вручную проверяет и правит локальную запись (или её `external_id`) до повторного импорта. Это уже соответствует текущей реализации `_HARD_BLOCKING = {CONFLICT}` в ADR-0013 — дополнительных изменений в код не требуется, только явная фиксация обоснования здесь, в ADR.
