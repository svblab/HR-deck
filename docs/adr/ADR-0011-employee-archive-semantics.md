# ADR-0011: Семантика архива сотрудника и типов занятости

Статус: Предложено
Дата: 2026-09-20
Автор: Cursor (по результатам architecture audit, §1 `docs/ARCHITECTURE_AUDIT.md`)
Затронутый EPIC: EPIC-014 (архивирование сотрудников), EPIC-004 (справочники),
EPIC-026 (синхронизация — follow-up, вне скоупа этого ADR)
Связанные документы: ADR-0010, `docs/ARCHITECTURE_AUDIT.md` §1, ТЗ §3.1 / §3.9

## Контекст

Аудит архитектуры (2026-09-20) подтвердил расхождение между моделью данных,
реализацией и документацией вокруг архивирования сотрудников:

1. **`employees.is_archived`** уже является фактическим источником истины для
   видимости сотрудника в штатном списке, поиске и отчётах.
2. Переработка архива (PR #84, migration `0016`) перенесла «увольнение» с
   availability status `inactive` на employment type `dismissed`, но **не
   засеяла** тип `dismissed` в схеме.
3. `archive_employee()` ищет `employment_types.code = 'dismissed'`; при
   отсутствии строки архивирование **всё равно выполняется** (`is_archived := 1`),
   но метаданные типа занятости не обновляются.
4. Типы занятости — обычные записи справочника с `INTEGER PRIMARY KEY`;
   `name` редактируемо и не является семантическим идентификатором; `code`
   стабилен после создания, но для `dismissed` не гарантирован на свежей БД.
5. Выбор типа занятости в карточке сотрудника **не влияет** на `is_archived`.
6. Импорт/экспорт и синхронизация (ADR-0010) не переносят справочник типов
   занятости; в sync-пакетах уходит сырой `employment_type_id`.

До принятия этого ADR реализация PR #84 считается **промежуточной**: направление
верное (`is_archived` + метаданные типа), но контракт не зафиксирован, а
гарантии свежей БД и расширяемость не обеспечены.

Лабораторный этап: production-данных нет; миграции могут пересоздавать базу.
Это ADR **только фиксирует модель** — без изменения кода, схемы и поведения.

## 1. Что такое архивный сотрудник?

### Определение

**Архивный сотрудник** — запись в `employees`, у которой
`employees.is_archived = 1`.

Это единственный канонический признак lifecycle-состояния «в архиве».

### Что следует из определения

| Аспект | Правило |
| --- | --- |
| Видимость в штатном списке | Архивный сотрудник **скрыт по умолчанию** |
| История статусов | **Сохраняется** без изменений при архивировании |
| Поиск по ФИО (active-only) | Архивные **исключаются** |
| Отчёты «текущий состав» | Архивные **исключаются**, если явно не запрошен архив |
| Availability status | **Не является** механизмом архива (status `inactive` удалён, migration 0016) |

### Роль типа занятости при архиве

Тип занятости с семантикой увольнения/завершения отношений (например,
`code = dismissed`) — **метаданные**, описывающие *причину/категорию*
перевода в архив, а **не** сам факт архива.

Инвариант:

```text
employee.is_archived = 1   ⟹  сотрудник в архиве (канон)
employee.employment_type_id = <archiving-type>   ⟹  метаданные (желательно, но не обязательно для факта архива)
```

Обратное **не** выполняется:

```text
employee.employment_type_id = <archiving-type>   ⟹̸  employee.is_archived = 1
```

Выбор «увольняющего» типа занятости в карточке **не архивирует** сотрудника
автоматически. Архив — **явное действие** (кнопка «В архив», диалог архива).

## 2. Роль типа занятости

Тип занятости отвечает за **таксономию** отношений сотрудника с организацией
(штатный, временный, подрядчик, уволен, на пенсии, …). Это ортогонально
lifecycle-архиву.

Три независимых слоя:

| Слой | Поле / механизм | Назначение |
| --- | --- | --- |
| **Taxonomy** | `employment_type_id` | Категория занятости / завершения отношений |
| **Lifecycle** | `is_archived` | Активен в штатных списках или в архиве |
| **Presentation** | roster filters, Archive dialog, `needs_org_review` | Что видит пользователь и какие действия требуются |

### Нужно ли поле `archives_record`?

**Да, в целевой модели** (см. решение ниже). Семантика «этот тип занятости
описывает завершённые отношения и подходит как метаданные при архивировании»
должна храниться **явно** в справочнике, а не выводиться из русского `name` или
из захардкоженного `code` в прикладном коде.

`archives_record` **не означает** «выбрать этот тип → сотрудник в архиве».
Оно означает: «при **явном** архивировании этот тип может/должен быть
назначен как метаданные».

### Управление администратором

| Действие | Политика |
| --- | --- |
| Создание произвольных типов | Разрешено (`code` + `name`) |
| Переименование `name` | Разрешено |
| Установка `archives_record = 1` | Разрешено с предупреждением; не влияет на уже архивных сотрудников задним числом |
| Снятие `archives_record` с системного типа | **Запрещено** для зарезервированных системных `code` (см. §7) |
| Архивирование записи справочника (`employment_types.is_archived`) | Скрывает из новых назначений; **не** архивирует сотрудников |

### Опасные последствия смены `archives_record`

Смена флага у существующего типа **не меняет** `employees.is_archived` у уже
архивных сотрудников. Риск: HR назначит тип, который перестал быть
«архивирующим», новому сотруднику вручную — это допустимая путаница таксономии,
не нарушение lifecycle. Защита: UI не предлагает archiving-типы для **новых**
активных сотрудников (только при явном архивировании или редактировании
архивной карточки).

Циклической зависимости с `is_archived` нет: lifecycle-флаг каноничен,
`archives_record` — подсказка для метаданных при операции архива.

## 3. Вариант A vs Вариант B

### Вариант A — засеять `dismissed`

```text
employment_types (seed)
---------------------
1  staff
2  temporary
3  contractor
4  dismissed      ← новый seed, code фиксирован, name по умолчанию локализуем
```

| Критерий | Оценка |
| --- | --- |
| Корректность | Улучшает метаданные при архиве, но оставляет магическую строку `'dismissed'` в коде |
| Детерминизм свежей БД | ✓ Тип существует на каждой новой БД |
| Настраиваемость администратором | `name` редактируем; `code` системный |
| Расширяемость (`retired`, `contract_ended`) | ✗ Каждый новый тип → новый hard-coded `code` или дублирование логики |
| Импорт/экспорт | Частично: import знает `code`, export — только `name` |
| Синхронизация | Не решает перенос `employment_type_id` между инсталляциями |
| Аудируемость | Archive audit пишет факт; тип — по косвенным данным |
| Простота UI | Высокая — один «уволенный» тип |
| Совместимость с текущим кодом | Максимальная (минимальный diff) |
| Дублирование правил | `'dismissed'` в сервисе + seed в миграции |

### Вариант B — явная семантика `archives_record`

```text
employment_types
----------------
id
code
name
archives_record   INTEGER NOT NULL DEFAULT 0
is_archived
...
```

| Критерий | Оценка |
| --- | --- |
| Корректность | Разделяет taxonomy и lifecycle; единая точка для «архивирующих» типов |
| Детерминизм свежей БД | ✓ **только если** одновременно засеять системный тип с `archives_record = 1` |
| Настраиваемость | Администратор может добавить `retired`, `contract_ended` без изменения кода |
| Расширяемость | ✓ Lookup `WHERE archives_record = 1` вместо scatter `if code == ...` |
| Импорт/экспорт | Требует передачи `code` (или отдельного столбца) — follow-up |
| Синхронизация | Требует синхронизации справочника или маппинга по `code` — follow-up |
| Аудируемость | Можно логировать выбранный archiving-type id/code |
| Простота UI | Нужен выбор причины архива при нескольких archiving-типах (можно отложить: default) |
| Совместимость | Средняя: миграция + смена lookup в `archive_employee()` |
| Дублирование правил | Одно правило: default archiving type = системный seed с `archives_record = 1` |

### Сравнительный вывод

Вариант A — быстрый патч, не масштабируется на несколько archiving-типов.
Вариант B — правильное место для семантики в справочнике, но **сам по себе**
не гарантирует свежую БД без обязательного system seed.

## 4. Решение (каноническая модель)

### Принятая модель

```text
employees.is_archived          = каноническое lifecycle-состояние архива
employees.employment_type_id   = независимые метаданные таксономии
employment_types.archives_record = семантика «тип для метаданных при архивировании»
```

**Рекомендация: Вариант B + обязательный system seed (гибрид B+A).**

Не реализовывать ни A, ни B до принятия ADR. После принятия — реализовать **оба
элемента вместе**: колонка `archives_record` **и** seed системного типа
`code = 'dismissed'`, `archives_record = 1`, с локализуемым `name` по умолчанию.

Причины выбора гибрида B+A:

1. **Корректность:** lifecycle (`is_archived`) отделён от taxonomy
   (`employment_type_id`) и от семантики справочника (`archives_record`).
2. **Детерминизм свежей БД:** system seed гарантирует наличие default
   archiving-типа без опоры на display name.
3. **Расширяемость:** `retired`, `contract_ended` добавляются в справочник с
   `archives_record = 1` без новых hard-coded проверок.
4. **Избежание дублирования:** `archive_employee()` ищет default archiving type
   по `code = 'dismissed'` среди строк с `archives_record = 1`, а не по имени
   «Уволен».
5. **Совместимость с PR #84:** сохраняет направление «архив + тип увольнения»,
   устраняя архитектурный пробел (отсутствие seed и магическая строка без
   схемной опоры).

### Жизненный цикл (инварианты)

#### Archive (явное действие пользователя)

```text
Предусловие: employee.is_archived = 0

1. employee.is_archived := 1
2. employee.employment_type_id := id системного типа
     WHERE code = 'dismissed' AND archives_record = 1 AND is_archived = 0
   (если такой тип отсутствует — шаг 2 пропускается; шаг 1 обязателен)
3. status_history — без изменений
4. user_action_log: employee.archive
```

Будущее расширение (не в первом коммите реализации): при нескольких
archiving-типах UI может запрашивать причину; по умолчанию — системный
`dismissed`.

#### Restore (явное действие пользователя)

```text
Предусловие: employee.is_archived = 1

1. employee.is_archived := 0
2. employee.needs_org_review := 1
3. employee.employment_type_id — НЕ восстанавливается к значению «до архива»
4. Пользователь при необходимости вручную выбирает новый не-archiving тип
   занятости и актуальный статус («Требует уточнения» / назначение статуса)
5. status_history — без автоматических изменений
6. user_action_log: employee.restore
```

**Запрещено:** автоматическое восстановление предыдущего `employment_type_id`
при restore.

#### Редактирование карточки (обычный save)

```text
Смена employment_type_id НЕ меняет is_archived.
Назначение archiving-типа активному сотруднику через карточку допустимо
как правка метаданных, но НЕ переводит в архив (защита от случайной потери
видимости в списке).
```

## 5. Несколько будущих archiving-типов

Допускается несколько записей с `archives_record = 1`:

```text
dismissed        archives_record=1   (system default)
retired          archives_record=1   (admin-created)
contract_ended   archives_record=1   (admin-created)
staff            archives_record=0
```

Правила:

| Вопрос | Ответ |
| --- | --- |
| Где проверять archiving-семантику? | **Только** в операции Archive (и UI выбора причины), через `archives_record`, не через scatter `if code == ...` по кодовой базе |
| Какой тип назначать по умолчанию? | Системный `code = 'dismissed'` |
| Влияет ли `archives_record` на `is_archived`? | **Нет** — только подсказка при архивировании |
| Может ли archiving-тип сосуществовать с активным сотрудником? | Да, как метаданные без архива (редкий edge case; UI может предупреждать) |

## 6. Идентичность типа занятости

Четыре разных понятия — **не смешивать**:

| Понятие | Поле | Назначение | Допустимо в бизнес-логике? |
| --- | --- | --- | --- |
| Database-local identity | `id` | FK внутри одной БД | Только внутри инсталляции |
| Machine identity | `code` | Стабильный код после создания | **Да**, для system seeds и import/sync (follow-up) |
| Display | `name` | Подпись в UI и XLSX export | **Нет** |
| Archive semantics | `archives_record` | Метаданные при архивировании | **Да**, в операции Archive |

Запреты:

- Не использовать `name` «Уволен» / «Уволенный» как идентификатор.
- Не вводить hard-coded numeric id (в т.ч. «всегда id=4») в прикладной логике;
  seed-миграция может фиксировать id для детерминизма **только на уровне SQL**,
  код обращается по `code` + `archives_record`.
- Не полагаться на существование `dismissed` без seed или эквивалентного
  механизма.

## 7. Гарантия на свежей базе

**Требование:** на каждой свежей БД после миграций должен существовать ровно
один **системный** archiving-тип по умолчанию:

```text
code            = 'dismissed'
archives_record = 1
name            = локализуемое значение по умолчанию (не идентификатор)
is_archived     = 0
```

Системные `code` (`staff`, `temporary`, `contractor`, `dismissed`) считаются
зарезервированными: администратор может менять `name`, но не может удалить
запись или снять `archives_record` с `dismissed` (реализация — в сервисе
справочников, follow-up).

Архив **возможен** и без строки `dismissed` (только `is_archived := 1`), но
это **деградированный режим**; целевая инсталляция обязана иметь system seed.

## 8. Импорт/экспорт и синхронизация

### Совместимость выбранной модели

| Канал | Совместимость | Комментарий |
| --- | --- | --- |
| Archive / Restore в UI | ✓ Полная | Не зависит от sync |
| XLSX import | △ Частичная | Разрешение по `name`/`code`; archiving-тип можно импортировать как обычный столбец |
| XLSX export | △ Частичная | Пишет только `name`; round-trip теряет `code` |
| ADR-0010 sync | ✗ Несовместима с сырым `employment_type_id` | Типы не синхронизируются; id 1–3 совпадают только на идентичных seed-БД |

### Можно ли безопасно переносить `employment_type_id` между инсталляциями?

**Нет.** Integer FK локален. Безопасный перенос требует отдельного решения
(follow-up, **вне скоупа PR #84 и этого ADR**):

- включить `employment_types` в sync-пакет с reconcile по `code`, **или**
- в employee sync row передавать `employment_type_code` вместо/вместе с id.

До follow-up sync **не должен** полагаться на совпадение `employment_type_id`
между отправителем и получателем, кроме случая идентичных seed-only баз.

### Запись в ADR

Несовместимость sync с employment types — **открытая архитектурная задача**
(предлагаемый EPIC/ADR-0012 или расширение EPIC-026). Принятие ADR-0011 **не
блокирует** текущий sync, но фиксирует известный риск.

## PR #84 — что остаётся архитектурно неразрешённым

| Пробел | Почему важно |
| --- | --- |
| `dismissed` не засеян | Метаданные при архиве отсутствуют на свежей БД |
| Lookup только `get_by_code("dismissed")` без `archives_record` | Не масштабируется; семантика только в коде |
| Нет `archives_record` в схеме | Нельзя выразить `retired` / `contract_ended` |
| Sync переносит сырой `employment_type_id` | ADR-0010 assumption ложна для admin-типов |
| Import/export не переносят `code` | Round-trip и кросс-инсталляционная идентичность слабы |
| `docs/manual/user-guide.md`, `ROADMAP` EPIC-014 | Всё ещё описывают архив через status `inactive` |
| Мёртвый код `INACTIVE_STATUS_CODE` в `status_history.py` | Технический долг после 0016 |

PR #84 **не должен мержиться как финальная архитектура** без follow-up по
этому ADR (как минимум: принятие ADR + seed/semantics migration).
