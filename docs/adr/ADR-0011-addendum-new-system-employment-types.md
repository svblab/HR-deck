ADR-0011 оставил архив на `employees.is_archived`, вид — метаданные (`archives_record`) и код `dismissed`. ТЗ v2 добавляет два архивирующих вида и откладывает коды сюда (3.4; Приложение E). Приложение B добавляет постоянное ФИО и неизменяемый филиал. E1 ждёт этот адденд и адденд ADR-0010 (Приложение D, «Блокер E1»). Issue #155 (вид уходит числом) закрывает 3.6 и адденд ADR-0010, не посев.

## 1. Коды, названия, флаг и посев

| code | name | archives_record | is_archived | владелец |
|---|---|---|---|---|
| `transferred` | Переведён | 1 | 0 | нет |
| `erroneous` | Ошибочная запись | 1 | 0 | нет |

Коды продолжают ряд 3.4: латиница, один токен. Вместе с `dismissed` это

### 1.1. Посев и столкновение контракта

`0001` и `0017` не редактировать. Новая миграция после `0019`. Новая база
проходит те же миграции; `0001` по-прежнему вставляет id 1–3
(`src/data/migrations/0001_initial_schema.sql:167-170`). `id` не задаются
и между копиями не сопоставляются (2.2.1, 3.6.2, ADR-0011 §6). Уже
существующие карточки новый код не получают.

Прогон — только SQL, одна транзакция на файл. `apply_pending_migrations`
делает `BEGIN`, выполняет скрипт statement за statement и при любой
ошибке делает `ROLLBACK`
(`src/data/migrations.py:259-261`, `:287-289`). Разбор скрипта не содержит
ветвления по данным (`src/data/sql_script.py:82-85`). Запись версии в
`schema_migrations` стоит после скрипта, в том же `BEGIN`
(`src/data/migrations.py:276-286`).

`RAISE(ABORT, …)` стоит только внутри триггера
(`src/data/migrations/0011_optional_department_for_employees.sql:60-61`,
`src/data/migrations/0013_position_branch.sql:39-40`). Миграция `0013`
прерывается вставкой, которую отвергает NOT NULL
(`src/data/migrations/0013_position_branch.sql:18-27`). Посеву нужен свой
текст, поэтому чужой контракт ловит временный `BEFORE INSERT`-триггер на
временной таблице: `RAISE(ABORT, 'employment type seed contract mismatch')`,
если `code` уже есть и не совпали `name`, `archives_record` или
`is_archived`. Две вставки кодов во временную таблицу запускают проверку.
Если прерывания не было — `INSERT … WHERE NOT EXISTS` без `id`, как
`src/data/migrations/0017_employment_type_archive_semantics.sql:6-8`.
Триггер затем удаляется. Внешние ключи не отключаются (2.4.5). Миграцию
этот файл не содержит.

Ключ поиска — точный `code`. Совпадение строки — одновременно `name`
каноническое, `archives_record = 1`, `is_archived = 0`. `id` и метки
времени в контракт не входят.

| До миграции | Результат | После |
|---|---|---|
| Нет строки с этим `code` | INSERT | Строка контракта; COMMIT |
| Есть строка, три поля совпали | пропуск | Строка прежняя; COMMIT |
| Есть строка, иное `name`, `archives_record` или `is_archived` | RAISE, затем ROLLBACK | База как до миграции; версии в `schema_migrations` нет |
| Один код совпал, второй нет | то же прерывание всего файла | База как до миграции |

Частичного изменения нет: ошибка любого statement откатывает и посев, и
штамп версии (`src/data/migrations.py:287-289`).

### 1.2. Что заменено, что сохранено, что берётся из ТЗ

Три запрета не смешивать:

1. Закрытый базовый набор кодов: шесть имён из раздела 2. Другой системный
   код не добавляется без нового аддендума.
2. Системное `name` не переименовывается в справочнике.
3. Дополнительный вид не архивирует карточку. Своих архивирующих кодов нет.

Заменено в ADR-0011: §5 (администратор заводит `retired` и подобные) —
это запрещает 3.5.5; §7 (системное `name` можно менять) — это запрещают
3.4 и строка 11 матрицы 1.7. Из ТЗ, не из старого ADR: сами коды и флаг
«архивирует» (3.4), резерв кодов (3.4, 3.5.2), три архивирующих вида
(3.5.5). Сохранено без изменения: поиск по `code`, не по числу
(ADR-0011 §6); `archives_record` не есть сам архив (ADR-0011 §1).

Ключ локализации записи базового набора — неизменяемый `code`; в базе
лежит исходное значение, не перевод (9.14.3, 9.14.5). Механизма
локализации этот адденд не добавляет.

Сейчас переименование системный код не проверяет

## 3. Выбор вида, карточка, история, восстановление

Канон ADR-0011 остаётся: архив — `is_archived = 1` (4.1.4, 4.10.8). Код
без флага архивом не является.

### 3.1. Где какой вид предлагается

Решение Maintainer (4.5.1, 9.7.4): три архивирующих вида выбираются только
действием «В архив», в порядке таблицы 3.4. В обычном списке действующей
карточки их нет: там `staff`, `temporary`, `contractor` и нескрытые
дополнительные виды домашнего филиала. Для `transferred` обязателен филиал
назначения. Чужие карточки вид не выбирают (3.8.2). Базовые строки
справочника только для просмотра (9.9.1, 9.9.2).

Сейчас список — все активные виды (`src/ui/employee_card_form.py:220-224`),
архив без выбора (`src/ui/employee_card_form.py:387-388`,
`src/services/employees.py:189-204`), диалог вид не показывает
(`src/ui/archive_dialog.py:73-75`). Заменено в ADR-0011 §4: тихий
`dismissed` (`src/domain/employment_types.py:25-46`) и архив без вида.
Нет системной строки — архив не выполняется. Сохранено: история не
правится (2.4.2, A9); прежний вид сам не возвращается (4.8.3). Из ТЗ:
явный выбор (9.7.4), справочный филиал назначения (4.6.5), фильтр
ошибочных записей (4.7.2).

### 3.2. Филиал назначения и восстановление

Колонка `employees.transfer_target_branch_id`, пустая, внешний ключ на
`branches`. Пишется только архивом с кодом `transferred`: филиал есть, не
скрыт (9.9.4; решение 6) и не равен `branch_id` карточки (2.3.2, 4.6.1).
`branch_id` не меняется. Поле справочное (4.6.5, 4.12): карточка в другом
филиале не создаётся. Повторный перевод перезаписывает поле. Увольнение
и ошибочная запись его не очищают. Восстановление тоже не очищает
(решение 5, 4.13).

Любой архив: карточка не удаляется (2.4.1), `external_id` тот же (4.13),
карточка только для чтения (4.4.1, 9.7.3). `erroneous` не входит в отчёты
и счётчики и виден отдельным фильтром (4.7.2). Критерий — код `erroneous`
при `is_archived = 1`. Отчёты — E12. Список архива по умолчанию без этого
кода. Ограничение списков домашним филиалом (4.5.4) — эпик E4, не E1
(решение 7).

Восстановление только из «Архива» (9.8.2), с выбором неархивирующего вида
в той же операции. Ставится «требует уточнения» (4.8.4). Проверяется
возможная двойная занятость (4.8.6). Сейчас восстановление только снимает
флаг (`src/services/employees.py:213-228`).

## 4. Неизменяемость ФИО и филиала

После создания не меняются ФИО (4.4.3, 4.15.16, 9.7.1) и филиал карточки
(2.3.2, 4.4.2). Исключение для ФИО — обезличивание (15.7.3). Филиал не
исключается (4.10.2, 15.7.5). Кода обезличивания в `src/` нет.

| Путь | Строки | Факт |
|---|---|---|
| Создание | `src/services/employees.py:90-94` | первая запись законна |
| Правка | `src/services/employees.py:115-132` | оба поля пишутся без сравнения |
| Форма | `src/ui/employee_card_form.py:86-89` | поля доступны после создания |
| Архив | `src/services/employees.py:193-203` | передаёт уже сохранённые значения |
| Импорт | `src/services/employee_sync_import.py:571-578` | пакет перезаписывает оба поля |
| Класс | `src/services/employee_reconciliation.py:56-60` | CONFLICT только по ФИО |

### 4.1. Где стоит запрет

Запрет обычной смены — в `EmployeeService.update_employee`: другое ФИО
или другой `branch_id` отвергаются до записи. Форма после создания гасит
поля (9.7.1); это подсказка. E1-03 по решению Maintainer содержит сервис
и форму. Импорт того же `external_id` — отдельный слой, карточка E1-04:
другое нормализованное ФИО или другой филиал — CONFLICT, пакет
отклоняется до записи (4.10.2, П6). EXACT с теми же значениями может
записать их снова. Классификатор филиал сейчас не сравнивает
(`src/services/employee_reconciliation.py:56-60`).

Репозиторий (`update`, `apply_sync_row`) политики не получает и пишет
переданные значения: архив уже передаёт прежние, EXACT — те же. Триггер
базы на эти столбцы не добавляется: постоянный `RAISE` на любое изменение
ФИО закрыл бы обезличивание (15.7.3, 15.7.5). Запрет репозитория «иное
значение — ошибка» закрыл бы и EXACT, и будущую замену в
`apply_sync_row`. Обезличивание — E10 и ADR N6, отдельный вызов, не
`update_employee`. Пока его нет, другое ФИО на импорте — CONFLICT (2.9.1).

| Сценарий | full_name | branch_id |
|---|---|---|
| Создание | записывается | записывается |
| Обычная правка | отказ, если иное | отказ, если иной |
| Импорт EXACT | те же значения записать можно | те же значения записать можно |
| Импорт с расхождением | CONFLICT, записи нет | CONFLICT, записи нет |
| Импорт обезличивания (E10) | замена служебным значением, если филиал совпал | совпадение обязательно, иначе CONFLICT |
| Архив | без изменения | без изменения |
| Восстановление | без изменения | без изменения |

## Альтернативы

1. Коды кириллицей, из двух токенов, с фиксированным id или правкой `0001` — нет: ряд 3.4, ADR-0011 §6, A11.
2. Молча принять чужую строку — нет: флаг может быть 0.
3. Прервать посев повторной вставкой в UNIQUE — нет: текст будет про индекс, не про контракт. Голый `SELECT RAISE` вне триггера в этой схеме не встречается.
4. Триггер базы или запрет репозитория на любую перезапись ФИО — нет: закроет 15.7.3, 15.7.5 и EXACT с теми же значениями.
5. Тихий архив кодом `dismissed` или архив без флага — нет: 9.7.4, 4.1.4. Закрытие #155 — адденд ADR-0010 (Приложение B).

## Решения Maintainer

1. Три архивирующих вида выбираются только действием «В архив» (4.5.1, 9.7.4), не обычным списком карточки.
2. Формат кода дополнительной записи (3.5.2) решает адденд ADR-0010.
3. Порядок сортировки видов нужен (3.5.3, 3.8.3). Колонку вводит E1-08, не этот адденд.
4. Посев базового набора — в E1. Число маркера — в ADR N4 / E5.
5. Филиал назначения после восстановления не очищается.
6. Скрытый филиал нельзя выбрать назначением (9.9.4).
7. Фильтр архива по домашнему филиалу (4.5.4) — E4, не E1.
8. Плановая численность остаётся карточкой E1-11. Маркер — адденд ADR-0005.

## Открытые вопросы

«Дата окончания» и «цвет» из 3.5.3 для видов занятости этим ответом не
закрыты. Колонку порядка вводит E1-08; дату и цвет вида адденд не вводит.

## Последствия

Посев откатывает чужой контракт. Правка не меняет ФИО и филиал. EXACT
пишет те же значения; расхождение — CONFLICT. Триггера на эти столбцы и
правки пакета нет. `ANCHOR_CORE` и ТЗ не редактируются.

## Как проверяется

При приёмке поведение не меняется. После карточек раздела 7 проверяются
области раздела 6. Обмен новыми кодами ждёт адденд ADR-0010 и E1-09.
