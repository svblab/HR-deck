## Контекст

ADR-0011 оставил архив на `employees.is_archived`, вид занятости — метаданные
(`archives_record`) и один архивирующий код `dismissed`. ТЗ v2 добавляет
два архивирующих вида и откладывает их коды сюда (3.4; Приложение E).
Приложение B добавляет сюда постоянное ФИО и неизменяемый филиал карточки.
E1 не начинается, пока не приняты этот адденд и адденд ADR-0010
(Приложение D, «Блокер E1»).

Issue #155, по тексту задания и Приложению C: локальный вид уходит в пакете
числом. Это закрывает 3.6 и адденд ADR-0010, не посев кодов.

## 1. Коды, названия, флаг и посев

| code | name | archives_record | is_archived | владелец |
|---|---|---|---|---|
| `transferred` | Переведён | 1 | 0 | нет |
| `erroneous` | Ошибочная запись | 1 | 0 | нет |

Коды продолжают ряд 3.4 (`staff`, `temporary`, `contractor`, `dismissed`):
латиница, один токен. `name` — русское исходное значение; перевод отдельно
и в пакеты не входит (9.14.3, 9.14.5). Вместе с `dismissed` это три
архивирующих вида (3.5.5).

Посев:

- `0001` и `0017` не редактировать. Новая миграция после `0019`, как
  `0017` (`src/data/migrations/0017_employment_type_archive_semantics.sql:6-8`):
  `INSERT` без `id`, если `code` ещё нет.
- Новая база проходит те же миграции. `0001` по-прежнему вставляет id 1–3
  (`src/data/migrations/0001_initial_schema.sql:167-170`).
- Повтор безопасен. Строка с тем же `code` и тем же контрактом
  (`name`, `archives_record = 1`, `is_archived = 0`) пропускается. Иной
  контракт останавливает миграцию и откатывает её (A11, 14.2.3, 2.4.5).
  Чужую строку под этот код не переписывать.
- `id` не задаются и между копиями не сопоставляются (2.2.1, 3.6.2, ADR-0011 §6).
  Код ищет вид по `code`. Существующие карточки новый код не получают.

Отменяется ADR-0011 §5 (свои архивирующие коды вроде `retired`): это
запрещает 3.5.5. Отменяется ADR-0011 §7 (правка системного `name`):
базовый набор не меняется и не скрывается (3.4, матрица 1.7 строка 11).
Перевод названия — консоль 9.14, не справочник.

## 2. Зарезервированные коды и запреты

```text
staff, temporary, contractor, dismissed, transferred, erroneous
```

Сравнение без регистра, как `is_system_employment_type_code`
(`src/domain/employment_types.py:21-22`). Набор
`SYSTEM_EMPLOYMENT_TYPE_CODES` (`src/domain/employment_types.py:9`)
включает два новых кода. `archives_record` трёх неархивирующих кодов
остаётся 0; у трёх архивирующих его пишет только миграция.

| Действие | Базовый набор | Дополнительная запись |
|---|---|---|
| Переименовать `name` | запрещено (3.4, 9.9.2) | можно владельцу (3.5.3) |
| Изменить `code` | запрещено | запрещено (3.5.2) |
| Скрыть (`is_archived = 1`) | запрещено (3.4) | можно (3.5.4) |
| Удалить | API нет (2.4.3) | то же |
| Менять `archives_record` | нельзя | нельзя, всегда 0 (3.5.5) |
| Создать с зарезервированным `code` | отказ | отказ |

Сейчас переименование системный код не проверяет
(`src/services/directories.py:407-419`). Скрытие проверяет четыре кода и
только направление «в архив» (`src/services/directories.py:431-432`).
Создание ловит занятый код, не резерв как класс
(`src/services/directories.py:391-396`). Вставка не задаёт
`archives_record` и оставляет 0 (`src/data/directories.py:435-438`) — это
совпадает с 3.5.5 и сохраняется. Метода менять флаг для ролей не заводить.
Глобальная уникальность `code`
(`src/data/migrations/0001_initial_schema.sql:64`) сужается до пары
«владелец плюс код» в аддендуме ADR-0010, не здесь.

## 3. Выбор вида, карточка, история, восстановление

Канон ADR-0011 остаётся: архив — `is_archived = 1` (4.1.4, 4.10.8). Код
без флага архивом не является. Отменяется тихий архив без вида и тихий
выбор `dismissed` (`src/domain/employment_types.py:25-46`): если системной
строки нет, операция не выполняется. Пользователь называет один из трёх
кодов (9.7.4).

### 3.1. Где какой вид предлагается

Предложенное чтение 3.8 и 9.7 (вопрос 1):

1. Обычный список действующей карточки своего филиала: `staff`,
   `temporary`, `contractor` и нескрытые дополнительные виды домашнего
   филиала. Трёх архивирующих видов там нет: иначе сохранение карточки
   либо не архивирует, либо архивирует без филиала назначения (4.6.2).
2. «В архив» (9.7.4) предлагает три вида в порядке таблицы 3.4. Для
   `transferred` обязателен филиал назначения. Для двух других — нет.
3. Чужие карточки вид не выбирают (3.8.2). Базовые строки справочника
   только для просмотра, с отметкой «системная» (9.9.1, 9.9.2).

Сейчас карточка показывает все активные виды
(`src/ui/employee_card_form.py:220-224`) и архивирует без выбора
(`src/ui/employee_card_form.py:387-388`). Сервис сам берёт вид по
умолчанию (`src/services/employees.py:189-204`). Диалог архива вид не
показывает (`src/ui/archive_dialog.py:73-75`) и восстанавливает без нового
вида (`src/ui/archive_dialog.py:180-189`). Создание вида спрашивает
свободные код и имя (`src/ui/directories_dialog.py:385-393`).

### 3.2. Филиал назначения

Колонка `employees.transfer_target_branch_id`, пустая, внешний ключ на
`branches`. Пишется только архивом с кодом `transferred`: филиал есть,
не скрыт и не равен `branch_id` карточки (2.3.2, 4.6.1, 4.6.2, 9.9.4).
`branch_id` не меняется. Поле справочное (4.6.5, 4.12, 4.15.6–8): карточка
в другом филиале не создаётся и не связывается. Повторный перевод
перезаписывает поле. Увольнение, ошибочная запись и восстановление его
не очищают (4.13).

### 3.3. Следствия двух видов

Любой архив: карточка не удаляется (2.4.1, 4.15.17), `external_id` тот же
(4.2, 4.13), история статусов не правится (2.4.2, A9), данные работы в
филиале остаются (4.5.2), карточка только для чтения (4.4.1, 9.7.3).

`transferred` — флаг, этот код и филиал назначения. Импорт не команда
создать карточку в другом филиале (4.12).

`erroneous` — флаг и этот код. Карточки не входят в отчёты и счётчики и
видны в «Архиве» отдельным фильтром (4.7.2, 9.8.3). Критерий фильтра —
код `erroneous` при `is_archived = 1`. Отчёты — E12, не E1. В двойной
занятости архив не участвует (4.9.7); поиск по ФИО архив уже исключает
(`src/data/employees.py:71-76`). Восстановление обычное (4.7.4). На копии
уходит реплика по `external_id` (4.7.3, 4.10.8).

Список архива по умолчанию без `erroneous`; фильтр показывает только их.
Ограничение обоих списков домашним филиалом (4.5.4) ждёт E4 (N3): в E1
поля домашнего филиала нет, карточка его не добавляет.

### 3.4. Восстановление

Только из «Архива» (9.7.4, 9.8.2). В той же операции пользователь выбирает
неархивирующий вид (3.1.1). Прежний вид сам не возвращается (4.8.3).
`id`, `external_id` и история сохраняются (4.8.2). Ставится «требует
уточнения»; снимает его сохранение уже с неархивирующим видом (4.8.4).
Проверяется возможная двойная занятость (4.8.6, 4.9.2). Сейчас
восстановление только снимает флаг и ставит `needs_org_review`
(`src/services/employees.py:213-228`).

## 4. Неизменяемость ФИО и филиала

После создания не меняются ФИО (4.4.3, 4.15.16, 9.7.1) и филиал карточки
(2.3.2, 4.4.2, 4.15.1). Запись при создании — не правка. Единственное
исключение для ФИО — обезличивание (15.7.3). Филиал не исключается даже
тогда (4.10.2, 15.7.5). Кода обезличивания в `src/` нет.

Пишут или могут писать сохранённые `full_name` и `branch_id`:

| Путь | Строки | Факт |
|---|---|---|
| Создание | `src/services/employees.py:90-94`, `src/data/employees.py:99-104` | законная первая запись |
| Правка | `src/services/employees.py:115-132`, `src/data/employees.py:140-142` | оба поля пишутся из формы без сравнения |
| Форма | `src/ui/employee_card_form.py:86-89`, `452-462` | поля доступны и уходят в `update_employee` |
| Архив | `src/services/employees.py:193-203` | передаёт уже сохранённые значения |
| Импорт | `src/services/employee_sync_import.py:571-578`, `src/data/employees.py:179-183` | пакет перезаписывает оба поля |
| Класс | `src/services/employee_reconciliation.py:56-60` | CONFLICT только по ФИО, филиал не сравнивается |
| Новые карточки | `src/services/employee_import.py:94`, `src/services/employee_conversion.py:80` | создание, не правка |

`restore_employee`, `update_sensitive` и сброс оргпривязки эти поля не пишут.

Нужно: `update_employee` отказывается менять ФИО или `branch_id`; форма
после создания делает их недоступными (9.7.1). Тот же `external_id` с
другим нормализованным ФИО или другим филиалом — CONFLICT, пакет
отклоняется целиком (4.10.2, П6). Совпадение обоих — EXACT. Исключение
15.7.5: входящая карточка обезличена, `external_id` и филиал совпали —
другое ФИО не CONFLICT, локальная карточка обезличивается, старые
персональные данные не возвращаются. Другой филиал остаётся CONFLICT.
Обезличивание — E10 и ADR N6, не E1. Запрет обычной правки ФИО не должен
закрыть эту будущую операцию: единственный будущий писатель нового ФИО —
обезличивание. Пока его нет, другое ФИО остаётся CONFLICT (2.9.1).

## 6. Совместимость, инварианты, области проверок

Рабочих баз нет (2.9.1), миграция для уже открытых схем нужна (14.2.3).
Риски: занятый `transferred` или `erroneous` останавливает миграцию;
разные id одного кода ломают нынешний обмен целым id; смена ФИО или
филиала, которая сегодня сохраняется, получит отказ; тот же `external_id`
с другим филиалом перестанет быть EXACT.

Держать: A8 (ключ не текст имени); A9; A11 и 2.4.5; П3; П4; П5 (перевод
не создаёт карточку молча); П6; отдельность `is_archived` от вида (4.1.4).
Маркер базового набора растёт при изменении набора (14.2.2.2). Число
маркера — ADR N4 и E5; посев строк от маркера не зависит.

Области проверок, без текстов тестов: посев на пустой и непустой базе;
повтор миграции; отказ при чужой строке с тем же `code`; запрет
переименования, скрытия и создания с резервным кодом; дополнительный вид
не архивирует; архив тремя кодами и обязательный филиал назначения;
восстановление с новым видом без возврата старого; отказ смены ФИО и
филиала; недоступность полей после создания; CONFLICT по ФИО и по филиалу;
история статусов не меняется; фильтр ошибочных записей.

## Последствия

Миграция посева и отдельная миграция колонки назначения. Архив получает явный код. Правка и реплика не меняют ФИО и филиал; другой филиал реплики — CONFLICT. Состав пакета не меняется. `ANCHOR_CORE` и ТЗ не редактируются. A8 верен, если между копиями ключ базового вида — `code`. Вопрос 1 закрывает чтение 3.8.1.

## Как проверяется

При приёмке аддендума поведение не меняется. После карточек раздела 7
проверяются области раздела 6. Обмен новыми кодами не проверен, пока нет
