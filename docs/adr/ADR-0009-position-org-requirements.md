# ADR-0009: Настраиваемая по должности обязательность департамента/отдела

Статус: Принято
Дата: 2026-09-14
Автор: Claude (черновик по инициативе пользователя), принято пользователем 2026-09-14
Затронутый EPIC: EPIC-025

## Контекст

ADR-0008 сделала департамент и отдел опциональными на уровне схемы и
карточки сотрудника — HR/администратор теперь сам решает при вводе
конкретного сотрудника, нужен ли департамент/отдел. Пользователь указал на
следующий шаг: для многих должностей это решение на самом деле не должно
приниматься каждый раз заново вручную — оно известно заранее и зависит от
должности («Секретарь» всегда без департамента, «Бухгалтер» всегда с
департаментом). Решение: хранить обязательность департамента/отдела как
свойство должности (справочник «Должности»), с чекбоксами для
администратора/HR, и учитывать это при вводе сотрудника.

Изначальное опасение о «нелегальных комбинациях» снято: переключателя
фактически два («департамент обязателен», «отдел обязателен»), а не три —
филиал обязателен всегда и чекбоксом не является. Уже реализованная
(Phase 1 EPIC-024) фильтрация отдела по выбранному департаменту сама по
себе не допускает противоречивого состояния: если департамент обязателен и
заполнен, в списке отделов показываются только отделы этого департамента;
если департамент не обязателен и не заполнен, в списке — только отделы
филиала напрямую. Дополнительной защиты от «нелегальных» сочетаний
чекбоксов не требуется.

## Решение

### Хранение требований

`positions` получает два новых столбца (`ALTER TABLE ADD COLUMN` — рядовое
добавление, без перестройки таблицы, в отличие от 0010/0011):

```sql
ALTER TABLE positions ADD COLUMN department_required INTEGER NOT NULL DEFAULT 0
    CHECK (department_required IN (0, 1));
ALTER TABLE positions ADD COLUMN division_required INTEGER NOT NULL DEFAULT 0
    CHECK (division_required IN (0, 1));
```

Значение по умолчанию — `0` (не обязательно) для обоих столбцов: у всех
уже существующих должностей поведение не меняется автоматически,
ужесточение — осознанное действие администратора для конкретной должности.

### Проверка при вводе/редактировании сотрудника

`EmployeeService.create_employee`/`update_employee` (не только карточка —
иначе импорт обходил бы это правило) при известной должности сотрудника
подгружают её `department_required`/`division_required` и требуют
соответствующие поля так же, как сейчас требуется `branch_id`/`full_name` —
той же ошибкой валидации, не отдельным механизмом. Карточка сотрудника
делает то же самое на UI-уровне.

Если у выбранного департамента нет ни одного отдела, а должность требует
отдел — это тупиковая, но не системная ошибка: HR увидит обычное «отдел
обязателен» и не сможет сохранить, пока не заведёт отдел или не сменит
департамент. Ожидаемое поведение, не баг.

### Безопасное редактирование требований должности

`DirectoryService` получает два метода вместо одного «сохранить»:

```python
def preview_position_requirement_change(
    self, position_id: int, *, department_required: bool, division_required: bool
) -> list[EmployeeRef]:
    """Активные сотрудники этой должности, которые перестанут
    соответствовать новым требованиям. Пустой список — ужесточения нет
    или никто не пострадает, применять можно сразу."""

def apply_position_requirement_change(
    self, position_id: int, *, department_required: bool, division_required: bool,
    reset_violations: bool = False,
) -> None:
    """Если preview_position_requirement_change() непуст и
    reset_violations=False — бросает исключение с числом затронутых
    сотрудников. Если reset_violations=True — одной транзакцией:
      1. каждому затронутому активному сотруднику department_id и/или
         division_id, которые перестали удовлетворять новым требованиям,
         сбрасываются в NULL (только те, что реально стали нарушением);
      2. каждому такому сотруднику needs_org_review = 1;
      3. запись в user_action_log на каждого сотрудника
         (action_type="employee.org_review_reset", entity_type=ENTITY_EMPLOYEE,
         entity_id=employee.id, details — какие поля сброшены и из-за
         какой должности);
      4. только затем обновляются department_required/division_required
         самой должности.
    Ослабление требований violators не порождает никогда.
    """
```

`branch_id` и `position_id` сотрудника этим механизмом никогда не
затрагиваются — обнуляются только `department_id`/`division_id`.
Только активные сотрудники (`is_archived = 0`) учитываются и в preview, и
в apply.

### Признак «требует внимания»

Новый столбец `employees.needs_org_review INTEGER NOT NULL DEFAULT 0
CHECK (needs_org_review IN (0, 1))`. Не путать с `needs_clarification` из
ростера — тот вычисляется на лету по статусу доступности.

Устанавливается только автоматическим сбросом из
`apply_position_requirement_change`. Снимается автоматически при следующем
успешном сохранении карточки этого сотрудника.

Отображение: в ростере — колонка/бейдж «Требует внимания» и фильтр
`RosterFilters.only_needing_org_review`, по аналогии с `only_needing_clarification`;
в карточке сотрудника — предупреждение при открытии, если флаг установлен.

### UI

Вкладка «Должности» — два чекбокса («Департамент обязателен», «Отдел
обязателен») в форме создания/редактирования должности. При сохранении
изменений у существующей должности сначала вызывается
`preview_position_requirement_change`; если список не пуст — модальное
окно с количеством и списком затронутых сотрудников и явным
предупреждением; только после подтверждения —
`apply_position_requirement_change(..., reset_violations=True)`.

## Последствия

- Миграция простая (`ADD COLUMN` ×3), без table rebuild.
- Требования проверяются на уровне сервиса, а не только UI — импорт тоже
  обязан соблюдать требования должности. Решено отдельно в ADR-0010:
  нарушение требований должности при импорте — ошибка строки, не тихое
  создание с пометкой (см. ADR-0010, Часть 4).
- Массовый сброс данных сотрудников как побочный эффект правки справочника
  сделан заметным (модалка с подтверждением) и аудируемым, а не тихим.
- Явно НЕ вводится: ограничение «нельзя обязать отдел без обязательного
  департамента» — не нужно, комбинация безопасна сама по себе.
