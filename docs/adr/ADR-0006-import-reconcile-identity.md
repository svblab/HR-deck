# ADR-0006: Идентификация записей и режимы обработки расхождений при импорте (сверка «файл ↔ база»)

Статус: Предложено
Дата: 2026-09-05
Автор: Claude (черновик по инициативе пользователя, требует ревью и принятия)
Затронутый EPIC: не назначен — новая функциональность вне скоупа EPIC-016 и уже
закрытых эпиков; кандидат на отдельный EPIC после принятия ADR

## Контекст

Текущий импорт (`EmployeeImportService.confirm()`) — чисто аддитивный: каждая
готовая строка файла становится **новой** карточкой сотрудника; ничего не
обновляется и не удаляется. Отсутствие в файле записи, которая есть в текущей
базе, сейчас никак не анализируется — программа о разнице вообще не знает.

Целевой сценарий использования: несколько филиалов ведут **независимые копии**
базы (каждая — отдельная установка приложения, `ANCHOR_CORE.md` §6 явно
исключает сетевой/серверный многопользовательский режим), периодически
выгружают своих сотрудников в файл и передают в центральный офис для сверки.

Прямое следствие: сотрудники, добавленные независимо в разных копиях, не
координируются между собой при создании — что создаёт риск идентификации
(см. ниже) и является причиной, а не просто фоном для этой ADR.

Пользователь предложил рассмотреть три режима обработки расхождений между
файлом и базой при импорте:

1. истина в импортируемом файле (отсутствующие в файле — удалить/архивировать);
2. истина в текущей базе (ничего не трогать — де-факто уже так);
3. ручной режим — таблица совмещения, чекбоксы «оставить/архивировать».

Прежде чем проектировать любой из режимов, есть блокирующая проблема:
**надёжная идентификация записи между файлом и базой**, причём в сценарии
«несколько независимых копий» она приобретает дополнительное измерение —
не только сопоставление существующих записей, но и различение **новых**
записей, независимо созданных в разных копиях.

- `EmployeeExportService.export_xlsx` выгружает только `EXPORT_HEADERS`
  (ФИО, Должность, Филиал, Департамент, Отдел, Тип занятости) —
  **без ID сотрудника**.
- ФИО намеренно не является уникальным идентификатором в модели данных
  (`TESTING.md` §2.6: «два сотрудника с одинаковым ФИО, разными ID — операции
  над каждым не задевают другого»).
- `employees.id` (`0001_initial_schema.sql`) — обычный `INTEGER PRIMARY KEY`,
  локальный автоинкремент. В сценарии независимых копий два **разных**,
  ранее не существовавших сотрудника, добавленные в разных филиалах, с
  высокой вероятностью получат **один и тот же** `id` — локальный
  автоинкремент никак не координируется между копиями. Использовать его
  напрямую как ключ сопоставления небезопасно даже при точном совпадении.
- `ANCHOR_CORE.md` §3: «Программа фиксирует факты, но не принимает кадровых
  решений за пользователя»; «Любая корректировка… только через предложенный
  вариант + обязательное подтверждение… Никогда не выполняется автоматически
  и молча». Автоматическое удаление/архивация по неточному совпадению прямо
  противоречит этому пункту — по `ANCHOR_PROTOCOL.md` §4 п.6 это требует ADR.

Пункт 2 предложенных режимов уже является текущим поведением по умолчанию и
не требует изменений — обсуждение ниже касается идентификации записей и того,
что делать с расхождениями (пункты 1 и 3).

## Рассмотренные варианты

### Идентификация записи файл↔база

1. **Использовать внутренний `employees.id` напрямую в экспорте.** Отклонено:
   не координируется между независимыми копиями (см. Контекст) — гарантированно
   даст коллизии между новыми записями разных филиалов при достаточном объёме
   добавлений, независимо от качества остальной логики сопоставления.
2. **Сопоставление только по ФИО + подразделение**, как сейчас у warning'ов
   о дублях. Плюсы: не требует изменения формата экспорта. Минусы: ФИО не
   идентификатор — непригодно как основание для удаления/архивации.
3. **Отдельный глобально уникальный идентификатор (`external_id`, UUID4),
   генерируемый локально при создании записи, независимо от координации с
   другими копиями.** Вероятность коллизии двух независимо сгенерированных
   UUID4 где угодно и когда угодно — величина порядка 10⁻³⁸, то есть проблема
   снимается математически, без сетевого/серверного согласования (которое
   и так вне рамок проекта). Внутренний `INTEGER PRIMARY KEY` остаётся как
   есть — используется только для FK внутри одной БД, наружу (экспорт/сверка)
   не идёт.

**Выбор:** вариант 3 (UUID4, `external_id`), с уточнениями:

- **Защита от подмены/конфликта.** Совпадение по `external_id` засчитывается,
  только если он существует среди активных сотрудников **и** ФИО из файла
  совпадает с ФИО этой записи (хотя бы частично/нечётко). Если `external_id`
  найден в базе, но принадлежит записи с полностью другим ФИО — статус
  **«Конфликт идентификатора»**: автоматическое доверие запрещено, строка
  уходит в fallback ниже с явным предупреждением (защита от загрузки файла
  из чужого/тестового контура).
- **Устойчивость к формату ячейки.** `external_id` — строка (UUID как текст),
  не число — проблема экспоненциальной записи/разделителей тысяч Excel
  (актуальная для числовых ID) на UUID не распространяется. Любое значение,
  не проходящее валидацию формата UUID после чтения через `cell_text()`,
  трактуется как **невалидный ID**, не как исключение — штатный повод уйти
  в fallback.
- **Два уровня уверенности для fallback**, когда `external_id` отсутствует
  или невалиден:
  - **LOW** — ровно один кандидат в базе по ФИО+подразделению;
  - **AMBIGUOUS** — более одного кандидата (легитимный кейс: два сотрудника
    с одинаковым ФИО и подразделением, `TESTING.md` §2.6, у каждого свой
    `external_id`). Для `AMBIGUOUS` чекбокс принять/отклонить не показывается —
    пользователь обязан явно выбрать конкретного сотрудника из списка
    кандидатов; автоматический выбор запрещён.

### Обработка записей, отсутствующих в файле

1. **Истина в файле — автоудаление/архивация отсутствующих.** Отклонено:
   даже с `external_id`-сопоставлением остаётся кейс `LOW`/`AMBIGUOUS` и
   «Конфликт идентификатора», и любое автоматическое действие по такому
   совпадению нарушает `ANCHOR_CORE.md` §3. Полностью автоматический режим
   для операции такого типа не рассматривается ни в каком виде.
2. **Истина в базе — ничего не трогать.** Уже текущее поведение
   (`confirm()` только создаёт). Фиксируется как единственный
   **автоматический** режим импорта по умолчанию.
3. **Ручной режим — отдельная функция «Сверка с базой».** Таблица
   совмещения (найдено по `external_id` / найдено по имени с пометкой
   уверенности LOW/AMBIGUOUS / конфликт идентификатора / есть в файле, нет в
   базе / есть в базе, нет в файле), чекбоксы по каждой однозначной позиции
   и явный выбор из списка кандидатов для `AMBIGUOUS`; ничего не применяется
   без явного подтверждения.

**Выбор:** вариант 2 остаётся единственным поведением обычного импорта;
вариант 3 реализуется как **отдельная** функция, не как часть текущего
`run_import_flow`/`ImportPreviewDialog`.

## Решение

- Обычный импорт (кнопка «Импорт») **не меняется по семантике**: всегда
  только создаёт новые карточки.
- Схема: миграция добавляет `employees.external_id TEXT UNIQUE`. Генерация —
  `uuid4()` в момент `EmployeeService.create_employee()`; backfill для уже
  существующих строк — один раз, в теле той же миграции (сгенерировать
  каждой существующей записи свой UUID).
- `EmployeeExportService.export_xlsx` получает дополнительный служебный
  столбец `external_id` (например заголовок `ID (служебное поле, не
  редактировать)`), не заменяющий текущие бизнес-колонки.
- Новая, отдельная от импорта функция **«Сверка с базой»**: отдельный пункт
  меню, отдельный сервис поверх `EmployeeService`/`DirectoryService`, не
  переиспользует `EmployeeImportService.confirm()`. Строит таблицу
  совмещения по правилам идентификации выше. Расхождения «есть в базе, нет
  в файле» предлагаются к архивации через существующий
  `archive_employee`/`is_archived` — batch-механизм см. ниже.
- Никакого понятия «жёсткое удаление» не вводится — расхождения закрываются
  через уже существующую архивацию, обратимую операцию.
- Право на выполнение сверки — существующее `MANAGE_EMPLOYEES`; новых
  permission не вводится; проверяется один раз на всю операцию.
- **Массовая архивация** — один `UPDATE … WHERE id IN (...)` на уровне
  данных плюс один batch-insert (`executemany` в одной транзакции) в журнал
  действий, по одной строке `entity_type=employee` на каждого сотрудника.
  `UserActionLogRepository` — простой append-only без хеш-цепочки между
  записями, batch-insert архитектурно ничего не ломает. Целевой объём —
  «несколько сотен сотрудников» (`TESTING.md` §2.8), батчинг — дешёвая
  инженерная гигиена независимо от масштаба.

## Последствия

- **Требуется миграция схемы БД** — единственный пункт этой ADR, реально
  меняющий схему (`ALTER TABLE employees ADD COLUMN external_id TEXT UNIQUE`
  + backfill). Тест на непустой БД обязателен (`TESTING.md` §4).
- Требует: (а) генерацию `external_id` в `EmployeeService.create_employee()`;
  (б) правку `EmployeeExportService`/`EXPORT_HEADERS`; (в) новый сервис
  сопоставления (reconcile), отдельный от `EmployeeImportService`, со
  статусами «по external_id» / «конфликт идентификатора» / LOW / AMBIGUOUS;
  (г) новый UI-диалог таблицы совмещения; (д) batch-метод массовой
  архивации на уровне данных.
- Журнал действий: массовая архивация пишет по одной записи на сотрудника
  единым batch-insert — новый тип batch-события не вводится.
- Существующее поведение обычного импорта и все текущие тесты
  (`tests/*employee_import*`) — не меняются этой ADR.
- Явно фиксируется отказ от автоматического режима 1 и от решения задачи
  слияния конфликтующих правок **одной и той же** записи между копиями
  (это уже полноценный multi-master merge — прямо попадает под «сетевой/
  многопользовательский режим», `ANCHOR_CORE.md` §6, вне рамок этой ADR).
- После принятия: завести отдельный EPIC (кандидат EPIC-018+) и ветку;
  до принятия — **не реализовывать**. Issue #39 (параметры шаблонов) к этой
  ADR не относится и остаётся отдельным backlog.
