# ADR-0005: Контракт маркеров Excel и привязки полей PDF (EPIC-011)

Статус: Предложено
Дата: 2026-08-29
Автор: Cursor (EPIC-011 Step 0)
Затронутый EPIC: EPIC-011

## Контекст

EPIC-011 вводит движок пользовательских Excel/PDF-шаблонов (ТЗ §3.8.2).
Заказчик готовит шаблоны **независимо** от релизов приложения; смена синтаксиса
маркеров или правил PDF ломает уже загруженные файлы. `ANCHOR_PROTOCOL.md` §4
п.4 требует зафиксировать контракт в ADR **до** реализации движка.

Существующее:

- `openpyxl` — импорт/экспорт и будущие Excel-шаблоны (ADR-0001, EPIC-009).
- `reportlab` — **генерация** табличных PDF с нуля для стандартных отчётов
  (ADR-0001, EPIC-010); не заполняет PDF заказчика.
- Таблицы `report_templates` / `report_template_versions` (migration `0001`) —
  хранение версий; детали привязки и сгенерированных отчётов — в Step 3.
- Права `USE_ACTIVE_REPORT_TEMPLATES` / `MANAGE_REPORT_TEMPLATES` уже в
  `domain/permissions.py` (ТЗ §4.1) — новых permission не требуется.
- Журнал действий: `entity_type = report_template` (EPIC-013).

## Рассмотренные варианты

### Excel: синтаксис маркеров

1. **`{{ИМЯ}}` (Mustache-подобный)** — совпадает с примерами ТЗ (`{{ФИО}}`),
   читаем для HR, однозначно отделяется от текста.
2. `%ИМЯ%` — риск коллизии с формулами Excel и процентным форматированием.
3. Именованные диапазоны Excel — не переносимы между редакторами, сложнее
   валидировать программно.

**Выбор:** вариант 1.

### Excel: неизвестный маркер

1. **Отказ при загрузке шаблона** — ошибка до попадания в библиотеку.
2. Оставить литерал `{{…}}` в отчёте — скрывает опечатки.
3. Пустая строка при генерации — скрывает опечатки, если п.1 пропущен.

**Выбор:** п.1 для имён вне каталога; при генерации известный маркер без
значения → пустая строка (частично заполненные строки допустимы).

### Excel: повторяющаяся строка

1. Маркер **`{{#ROW}}`** в любой ячейке строки-образца — строка копируется
   на каждую запись данных.
2. Отдельный лист «данные» + формулы INDEX — хрупко для заказчика.
3. Только именованный диапазон — плохая переносимость.

**Выбор:** вариант 1; для нескольких таблиц на листе — `{{#ROW:имя}}` /
`{{/ROW:имя}}` (см. ниже).

### PDF: способ подстановки

1. **AcroForm** (именованные поля формы) — основной путь для PDF из Word/LibreOffice.
2. **Координатные области** (manifest JSON) — запасной путь для «плоского» PDF.
3. Только reportlab «с нуля» — не шаблон заказчика; остаётся за EPIC-010.

**Выбор:** 1 + 2; оба описаны в одном контракте; при загрузке нужен хотя бы один.

### PDF: библиотека заполнения

1. **pypdf** — чтение/запись AcroForm, чистый Python, офлайн.
2. reportlab — уже есть; overlay текста по координатам поверх существующей
   страницы (не заменяет pypdf для полей формы).
3. WeasyPrint / pdfrw — избыточны или устарели для form-fill.

**Выбор:** pypdf для AcroForm + reportlab только для overlay по координатам
из manifest (переиспользуем EPIC-010, не второй стек «с нуля»).

## Решение

### Версия контракта

- Идентификатор: **`1.0`** (строка semver-lite).
- Каждая запись `report_template_versions` при загрузке **закрепляет**
  `contract_version = '1.0'`. Генерация всегда использует правила той версии
  контракта, с которой файл прошёл валидацию.
- Смена контракта (например `2.0`) — **новая ADR**; версии `1.0` остаются
  валидными и обслуживаются движком `1.0` без перезагрузки файла.

### Каталог полей (contract 1.0)

Маркер — подстрока ячейки или поля PDF: `{{` + *имя* + `}}`.

- *имя* — регистрозависимое; символы: буквы (Latin/Cyrillic), цифры, `_`, `.`.
- Пробелы внутри `{{ }}` запрещены.
- Вложенные `{{` в одной ячейке не поддерживаются.

**Канонические ключи и алиасы (оба принимаются при валидации):**

| Ключ | Алиасы | Описание |
|------|--------|----------|
| `report.title` | `заголовок` | Заголовок отчёта (параметр) |
| `report.date` | `дата` | Дата формирования |
| `report.period_from` | `период_с` | Начало периода (параметр) |
| `report.period_to` | `период_по` | Конец периода (параметр) |
| `employee.full_name` | `ФИО` | ФИО сотрудника |
| `employee.position` | `должность` | Должность |
| `employee.branch` | `филиал` | Филиал |
| `employee.department` | `департамент` | Департамент |
| `employee.division` | `отдел` | Отдел |
| `employee.status` | `статус` | Текущий статус |
| `employee.status_from` | `статус_с` | Дата начала статуса |
| `employee.status_to` | `статус_по` | Дата окончания статуса |
| `employee.employment_type` | `тип_занятости` | Тип занятости |

Расширение каталога в рамках `1.0` — допустимо в коде без смены синтаксиса;
**удаление** ключа — только с новой версией контракта.

**Служебные маркеры** (не из каталога данных):

| Маркер | Назначение |
|--------|------------|
| `{{#ROW}}` | Начало блока повторяющейся строки (одна таблица на лист) |
| `{{/ROW}}` | Конец блока (опционально, если после блока идут строки с формулами) |
| `{{#ROW:имя}}` / `{{/ROW:имя}}` | Именованный блок (несколько таблиц на листе) |

`имя` блока: `[A-Za-z][A-Za-z0-9_]*`.

### Excel: подстановка и повтор строк

1. **Загрузка:** исходный `.xlsx` сохраняется **байт-в-байт** (отдельный файл
   на диске); рабочая копия для генерации — производная.
2. **Валидация при загрузке:**
   - обход всех ячеек всех листов (значение и текст формулы);
   - извлечение всех `{{…}}`;
   - каждый маркер данных должен быть в каталоге (ключ или алиас);
   - служебные `#ROW` / `/ROW` — по правилам выше;
   - **иначе — отказ загрузки** с перечислением неизвестных маркеров;
   - не более одного неименованного `{{#ROW}}` на лист; именованные блоки
     должны быть парными.
3. **Генерация:**
   - скалярные маркеры вне `#ROW` подставляются один раз на весь лист;
   - для каждой записи набора данных блок `#ROW` копируется: стили ячеек
     образца сохраняются (`openpyxl` copy style);
   - формулы **внутри** строки-образца копируются с пересчётом относительных
     ссылок на номер вставленной строки;
   - формулы **вне** блока не переписываются, кроме автоматического сдвига
     строк при вставке (поведение Excel);
   - известный маркер без значения → **`""`**;
   - исходный файл в хранилище **не изменяется**.

### PDF: валидация при загрузке (не при генерации)

PDF считается **непригодным** и **отклоняется на загрузке**, если:

1. Файл не читается как PDF или защищён паролем/open-action.
2. **Нет ни одного** из:
   - AcroForm с ≥1 полем, имя которого (после нормализации) совпадает с ключом
     или алиасом каталога; **или**
   - сопроводительного **`*.regions.json`** (UTF-8) с тем же базовым именем,
     прошедшего JSON-schema контракта 1.0 (см. ниже).
3. `regions.json` есть, но невалиден или `contract_version` ≠ поддерживаемой.
4. Поля AcroForm есть, но **ни одно** имя не из каталога **и** manifest отсутствует
   — отказ («PDF не поддерживает подстановку» по смыслу ТЗ §3.8.2).

Проверка выполняется **до** записи версии в БД. Ошибки генерации из-за
«неподдерживаемого PDF» недопустимы — это баг валидации.

**AcroForm:** имена полей сопоставляются с каталогом регистрозависимо; значения
записываются через **pypdf** (`update_page_form_field_values` или эквивалент).

**Координатный manifest (`regions.json`):**

```json
{
  "contract_version": "1.0",
  "binding_mode": "regions",
  "regions": [
    {
      "field": "employee.full_name",
      "page": 1,
      "x_pt": 72.0,
      "y_pt": 700.0,
      "width_pt": 200.0,
      "height_pt": 14.0,
      "font_size_pt": 10
    }
  ]
}
```

- Координаты в **points**, начало координат — **нижний левый угол** страницы
  (PDF-конvention).
- `page` — 1-based.
- `field` — ключ каталога (алиасы в manifest не используются).
- Текст рисуется overlay через **reportlab** поверх исходной страницы; исходный
  PDF байт-в-байт в архиве версии не перезаписывается до выдачи результата.

Manifest сохраняется в метаданных версии (Step 3: колонка или sidecar-path в
`report_template_versions`); на Step 0 схема **не меняется**.

### reportlab vs pypdf (EPIC-010 vs EPIC-011)

| Задача | Библиотека | EPIC |
|--------|------------|------|
| Табличный PDF с нуля | reportlab | EPIC-010 |
| Заполнение AcroForm чужого PDF | **pypdf** | EPIC-011 |
| Текст в координаты чужого PDF | reportlab overlay | EPIC-011 |

reportlab **не** используется для парсинга/изменения полей формы чужого PDF.

### Права и аудит (зафиксировано для Step 4–5)

- HR / Наблюдатель: `USE_ACTIVE_REPORT_TEMPLATES` — генерация по активным
  шаблонам.
- Администратор: `MANAGE_REPORT_TEMPLATES` — загрузка, версии, архив/восстановление.
- Каждая операция upload / archive / restore / generate →
  `UserActionLogRepository.record()`, `entity_type = report_template`,
  `entity_id = report_templates.id`, `details` содержит `version_number`.

## Последствия

- Step 1 (Excel): `openpyxl` only; тесты ссылаются на **ADR-0005 §Excel**.
- Step 2 (PDF): добавить **`pypdf`** в `pyproject.toml` отдельным коммитом;
  тест upload-reject — **ADR-0005 §PDF validation**.
- Step 3: вероятна миграция (`contract_version`, `binding_spec_json`,
  таблица сгенерированных отчётов) — отдельное решение в PR Step 3 или
  addendum к этой ADR, если схема простая.
- Документация Step 6 и `templates_samples/` должны использовать **только**
  синтаксис этой ADR.
- ADR-0001: дополнение EPIC-010 про reportlab **не отменяется**; заполнение
  шаблонов заказчика регулируется **этой ADR**.
