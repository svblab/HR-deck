# ADR-0003: Жизненный цикл мастер-ключа SQLCipher

Статус: Принято
Дата: 2026-08-26
Автор: Cursor (EPIC-003)
Затронутый EPIC: EPIC-002 (инфраструктура), EPIC-003 (решение), EPIC-012 (наследует)

## Контекст

ADR-0002 фиксирует модель: отдельный мастер-ключ шифрования БД, не равный
паролю учётной записи; резервный код восстановления для роли Администратор.
В EPIC-002 реализованы генерация 32-байтного ключа, SQLCipher 4, проверка
целостности и отказ при неверном ключе. Нужно зафиксировать, **где и как
хранить мастер-ключ между запусками** и как связать его с паролями учёток и
резервным кодом, не ослабляя SQLCipher и не храня ключ в открытом виде.

Требования ТЗ §4.2–4.3 и ANCHOR_CORE A7: вход по логину/паролю для любой из
трёх ролей; мастер-ключ не равен паролю; восстановление доступа Администратора
через одноразовый резервный код.

## Рассмотренные варианты

1. **Ключ в sidecar-файле рядом с БД**, обёрнутый (wrap) секретом каждой
   активной учётной записи и отдельно резервным кодом (KDF + AEAD). Плюс:
   полный офлайн-контроль; любой пользователь может открыть БД своим паролем;
   смена пароля рядовой учётки не требует перешифровки файла БД. Минус: нужна
   аккуратная ротация wrap-записей.
2. **Ключ только в памяти после ввода** (каждый запуск — отдельный секрет
   расшифровки). Плюс: меньше следов на диске. Минус: UX и конфликт с входом
   ролей HR/Observer без отдельного «мастер-пароля».
3. **OS keyring / libsecret** на Linux. Плюс: удобство. Минус: привязка к
   окружению ноутбука; перенос БД на другой ПК усложняется.

## Решение

**Вариант 1.** Рядом с файлом БД хранится sidecar `*.keywrap` (JSON):

- plaintext мастер-ключа на диске нет;
- для каждой учётной записи — AEAD-обёртка мастер-ключа под ключом, выведенным
  Argon2id из пароля этой учётки (соль уникальна);
- отдельная обёртка под резервный код восстановления;
- параметры KDF — единый источник в коде (`domain.password_kdf`), не
  разбросаны по вызовам.

Жизненный цикл:

- первичная настройка: генерация мастер-ключа → создание БД → учётка
  Администратора → wrap по паролю и по резервному коду;
- вход: по логину найти wrap → unwrap паролем → открыть SQLCipher → проверить
  хэш пароля и `is_active` в БД;
- смена/сброс пароля: при наличии мастер-ключа в памяти перезаписать wrap
  учётки;
- создание учётки: добавить wrap для нового пароля;
- восстановление: unwrap по резерву → сброс пароля Администратора →
  инвалидация использованного кода → выпуск нового кода (показ один раз).

## Последствия

- Нельзя коммитить plaintext мастер-ключ рядом с БД.
- Перенос каталога данных требует копировать и `.db`, и `.keywrap`.
- EPIC-012: бэкап должен включать согласованную пару БД + keywrap (или
  эквивалентную процедуру).
- UI онбординга и recovery разблокированы этой ADR.

## Как проверяется

`TESTING.md` §2.1: вход с верным/неверным паролем; восстановление по коду;
неверный ключ/отсутствие keywrap не даёт читаемых данных; integration-тесты
