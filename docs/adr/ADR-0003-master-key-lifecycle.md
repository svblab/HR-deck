# ADR-0003: Жизненный цикл мастер-ключа SQLCipher (открытый вопрос)

Статус: Предложено
Дата: 2026-08-26
Автор: Cursor (EPIC-002 hardening)
Затронутый EPIC: EPIC-002 (инфраструктура), EPIC-003 / EPIC-012 (решение)

## Контекст

ADR-0002 фиксирует модель: отдельный мастер-ключ шифрования БД, не равный
паролю учётной записи; резервный код восстановления для роли Администратор.
В EPIC-002 реализованы генерация 32-байтного ключа, SQLCipher 4, проверка
целостности и отказ при неверном ключе. **Где и как хранить мастер-ключ между
запусками** и как связать его с резервным кодом при онбординге — в ADR-0002
не детализировано на уровне файловой раскладки / UX.

По `ANCHOR_PROTOCOL.md` п.4.5 изменение модели ключей требует ADR. Здесь
фиксируется **нерешённый** жизненный цикл, чтобы EPIC-003 не изобретал его
молча в коде.

## Рассмотренные варианты (пока без выбора)

1. **Ключ в защищённом файле рядом с БД**, обёрнутый секретом Администратора /
   резервным кодом (KDF). Плюс: полный офлайн-контроль. Минус: нужна аккуратная
   процедура первого запуска и восстановления.
2. **Ключ только в памяти после ввода** (каждый запуск — ввод секрета,
   расшифровывающего мастер-ключ). Плюс: меньше следов на диске. Минус: UX.
3. **OS keyring / libsecret** на Linux. Плюс: удобство. Минус: привязка к
   окружению ноутбука; перенос БД на другой ПК усложняется.

## Решение

**Пока не выбрано.** EPIC-002 предоставляет только API
`generate_master_key` / `create_database` / `connect` и передачу ключа
вызывающим кодом (тесты, будущий bootstrap). UI ввода/хранения ключа в
EPIC-002 **не** реализуется.

Выбор варианта и реализация — в EPIC-003 (первичный Администратор + резервный
код) с дополнением в EPIC-012 (бэкап наследует то же шифрование). До
утверждения этой ADR (или её преемника) нельзя коммитить в `main` хранение
мастер-ключа в открытом виде рядом с БД.

## Последствия

- Тесты EPIC-002 передают ключ явно — это допустимо.
- Онбординг и recovery UI блокируются отсутствием утверждённого решения.
- Не затрагивает матрицу ролей и схему доменных таблиц.

## Как проверяется

Пока: `tests/integration/test_encryption.py` (неверный ключ, corruption,
reopen). После выбора варианта в EPIC-003 — отдельные integration-тесты
хранения/восстановления по `TESTING.md` §2.1.
