# ADR-0010: Стабильная идентичность и синхронизация справочников между инсталляциями

Статус: Принято
Дата: 2026-09-14
Автор: Claude (черновик по инициативе пользователя), принято пользователем 2026-09-14
Затронутый EPIC: EPIC-026
Отменяет: ADR-0006 (Предложено, не реализована) — содержание полностью
поглощено этим документом.

## Контекст

Возник в ходе обсуждения ADR-0009 (обязательность департамента/отдела по
должности): импорт сотрудников (`employee_import.py`) сопоставляет
департамент/отдел/должность **по имени** с уже существующими локальными
справочниками. Если сотрудник импортируется из файла, подготовленного в
другой инсталляции (другом филиале, со своей отдельной базой), и там
используются названия, которых ещё нет в локальной базе, — импорт падает с
«unknown department»/«unknown position». Такие ошибки недопустимы:
справочники отправителя должны приезжать вместе с пакетом и подключаться
раньше, чем начнётся обработка сотрудников.

По ходу выяснилось два самостоятельных факта:

1. Механизм для этого уже частично спроектирован, но не принят и не
   реализован — ADR-0006 вводит `employees.external_id` (UUID4) именно для
   того, чтобы отличать «эта же запись под другим именем» от «новая
   запись». Делать для справочников отдельный, второй с нуля придуманный
   механизм — дублирование. ADR-0006 отменяется как самостоятельная,
   содержание входит в этот документ.
2. `positions` сейчас **не привязаны к филиалу** (`positions(id, name,
   is_archived, created_at, updated_at)` — без `branch_id`). У каждого
   филиала физически своя система должностей, и сотрудник, переходя из
   филиала в филиал, всегда меняет должность. Это отдельный локальный
   структурный факт, не зависящий от импорта, и закрепляется в схеме
   независимо от темы синхронизации.

Названия (филиалов, департаментов, отделов, должностей) остаются свободно
редактируемыми — потребуется локализация (узбекский, таджикский, турецкий),
поэтому имя не может быть идентичностью записи ни локально, ни тем более
между инсталляциями. Идентичность — только стабильный ID.

Модель развёртывания: каждая копия программы — отдельная база со своими
справочниками, которыми копии делятся друг с другом только через
экспорт/импорт пакетов (транспорт — уже принятая ADR-0007).
Централизованного реестра ID нет — каждая инсталляция сама минтит
`external_id` для своих же записей.

## Решение

### Часть 1 — должности привязываются к филиалу (независимо от импорта)

`positions` получает `branch_id INTEGER NOT NULL REFERENCES branches(id)`.
Миграция — table rebuild (как 0010/0011 в ADR-0008); база пересоздаётся с
нуля вместе с этой миграцией, реальных данных нет.

Новый инвариант (триггер по образцу 0004): `employee.position_id` должен
принадлежать `employee.branch_id` — должность из другого филиала у
сотрудника запрещена, симметрично проверке департамента.

UI: `employee_card_form.py` — список должностей фильтруется по выбранному
филиалу и обновляется при его смене (`_on_branch_changed`), как уже
сделано для департамента/отдела. Смена филиала у сохранённого сотрудника
сбрасывает выбранную должность — автоматически перенести старую должность
в новый филиал невозможно, там её нет.

`directories_dialog.py`, вкладка «Должности» — становится филиал-зависимой
по образцу вкладки «Отделы» (`extra_parent` = филиал, список и создание
скопированы под текущий филиал).

### Часть 2 — стабильная идентичность (`external_id`)

`external_id TEXT UNIQUE` (UUID4, генерируется в `create_*` соответствующего
сервиса) добавляется на: `employees` (из ADR-0006, без изменений в
подходе), `branches`, `departments`, `divisions`, `positions`.

Для справочников имя — не сигнал идентичности и не участвует в разрешении
конфликтов: два разных филиала могут иметь позицию «Секретарь» с
одинаковым названием и разными `external_id` — это не конфликт. Найден
`external_id` локально — обновление той же записи (в т.ч. переименование
для локализации). Не найден — новая запись от инсталляции-отправителя.

Для сотрудника логика ADR-0006 переносится без изменений: `external_id` +
совпадение ФИО = уверенное сопоставление; несовпадение ФИО при совпавшем
`external_id` = «конфликт идентификатора»; отсутствие `external_id` —
уровни уверенности LOW/AMBIGUOUS, как было спроектировано изначально.

### Часть 3 — формат пакета и инкрементальный экспорт (потабличная гранулярность)

Экспорт формирует пакет из отдельных наборов строк: `branches`,
`departments`, `divisions`, `positions`, `employees`. Инкрементальность —
**на уровне таблицы целиком**: если хотя бы одна строка таблицы изменилась
(`updated_at`) с момента последней успешной отправки конкретному
получателю — в пакет включается **вся таблица целиком**; если ни одна
строка не менялась — таблица в пакет не входит вовсе. Не построчный диф.

```sql
CREATE TABLE sync_watermarks (
    peer_signing_fingerprint TEXT NOT NULL,
    table_name TEXT NOT NULL,
    last_exported_at TEXT NOT NULL,
    PRIMARY KEY (peer_signing_fingerprint, table_name)
);
```

(`peer_signing_fingerprint` — signing identity получателя из ADR-0007;
криптографические детали не переопределяются, ADR-0007 остаётся источником
истины по транспорту.) После успешной отправки водяной знак таблицы для
данного получателя переносится на момент отправки.

### Часть 4 — применение пакета при импорте

Порядок обработки — строго последовательный, в одной транзакции:

1. Извлекаются справочники в порядке `branches` → `departments` →
   `divisions` → `positions` (родители раньше детей).
2. Каждая строка справочника сопоставляется с локальной по `external_id`:
   не найдена — `CREATE`; найдена и отличается — `UPDATE`; найдена и
   совпадает — no-op.
3. Для каждого `UPDATE`, способного задеть существующих активных
   сотрудников (смена `department_required`/`division_required` у
   должности, смена структурной привязки отдела и т.п.), прогоняется
   предпросмотр, аналогичный `preview_position_requirement_change` из
   ADR-0009, по всем предполагаемым изменениям пакета сразу.
4. **Если хотя бы один активный сотрудник пострадает — пакет отклоняется
   целиком**, ничего не применяется (транзакция откатывается полностью),
   администратору выдаётся точный отчёт: какая справочная запись,
   какое поле, каких сотрудников (ФИО, филиал, должность) это бы задело.
   Нет частичного применения и нет автоматического `needs_org_review` по
   этому пути — это выделяет ситуацию как несовместимость, требующую
   разрешения на уровне процесса (исправить локально или запросить у
   отправителя другой пакет), а не как рутинное «требует внимания».
5. Если пострадавших нет — пакет справочников применяется одной
   транзакцией, затем обрабатываются строки сотрудников
   (`employee_import`-логика без изменений — к этому моменту локальные
   названия синхронизированы, поэтому «unknown department» из-за
   рассинхронизации справочников больше не возникает; ошибка на уровне
   данных сотрудника — как и раньше, по-прежнему ошибка строки, см.
   ADR-0009).

`needs_org_review`/аудит-запись из ADR-0009 остаются исключительно
механизмом для **ручного** редактирования справочника через UI — пакетный
импорт этот путь не использует вовсе (он либо применяется целиком без
пострадавших, либо отклоняется целиком).

## Последствия

- Миграция `positions.branch_id` — table rebuild, база пересоздаётся.
- `employee_card_form.py`, `directories_dialog.py` — должность становится
  филиал-зависимой, аналогично отделу.
- ADR-0006 закрывается как отменённая, её решения перенесены сюда.
- Новая таблица `sync_watermarks` — первая структура, специфичная именно
  для протокола обмена.
- Потабличная гранулярность экспорта проще в реализации, чем построчная,
  но менее экономна по трафику при малых точечных правках в большой
  таблице — сознательный компромисс в пользу простоты.
- Полный отказ пакета при конфликте — исключает любые частичные
  рассинхронизации между инсталляциями (либо обе базы согласованы после
  импорта, либо ни одна не меняется вовсе).
