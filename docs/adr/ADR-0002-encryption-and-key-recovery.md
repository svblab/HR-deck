# ADR-0002: Модель шифрования БД и восстановления доступа

Статус: Принято
Дата: 2026-08-19
Автор: согласовано с заказчиком в ходе проработки ТЗ
Затронутый EPIC: EPIC-002, EPIC-003, EPIC-012

## Контекст

Заказчик явно потребовал: (1) шифровать базу данных целиком, а не только
защищать вход паролем, но (2) избежать риска безвозвратной потери всех данных
о персонале при утере одного пароля. Одновременно в программе несколько
учётных записей с разными ролями — ключ шифрования не может быть жёстко
привязан к паролю одного рядового пользователя.

## Рассмотренные варианты

1. Ключ шифрования = хэш пароля конкретного пользователя, вошедшего в систему.
   Просто в реализации, но: при увольнении/смене пароля любого пользователя с
   доступом к БД пришлось бы перешифровывать всю базу; риск потери данных при
   утере единственного пароля.
2. **Отдельный мастер-ключ шифрования БД, не совпадающий с паролем ни одной
   учётной записи; доступ к операциям, требующим ключ, есть только у роли
   Администратор; при первичной настройке генерируется резервный код
   восстановления, который показывается один раз и должен быть сохранён вне
   программы (выбрано).**
3. Ключ шифрования, привязанный к паролю каждой отдельной роли по отдельности
   (мульти-ключевое шифрование). Технически надёжнее, но существенно сложнее
   в реализации и избыточно для однопользовательского-в-моменте сценария
   (раздел 2.1 ТЗ — сотрудники работают по очереди, не одновременно).

## Решение

Вариант 2. Мастер-ключ управляется на уровне роли «Администратор». Резервный
код восстановления — единственный способ восстановить доступ при утере
пароля администратора; без пароля и без кода данные не восстанавливаются
(это осознанный компромисс, согласованный с заказчиком, а не недосмотр).

## Последствия

- Онбординг первого Администратора — критичный шаг: экран показа резервного
  кода не должен допускать пропуска без явного подтверждения «код сохранён».
- Резервные копии базы (EPIC-012) наследуют то же шифрование — бэкап не
  снижает уровень защиты по сравнению с рабочей базой.
- Смена пароля рядового «Сотрудника HR» или «Наблюдателя» не требует
  перешифровки базы — меняется только их хэш пароля для входа, мастер-ключ
  не затрагивается.
- Если в будущем потребуется многопользовательский сетевой режим (вне
  текущего скоупа, см. `ANCHOR_CORE.md` п.6), эта модель ключа подлежит
  пересмотру отдельной ADR — она рассчитана на «один ноутбук, одна БД».

## Как проверяется

Раздел 11 ТЗ, блок «Безопасность и роли»: без верного пароля данные
недоступны; резервный код выдаётся при первой настройке и позволяет
восстановить доступ. Тесты — см. `TESTING.md`, раздел «Безопасность».
