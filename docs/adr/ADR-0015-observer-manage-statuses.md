# ADR-0015: Наблюдатель может назначать статусы сотрудников

Статус: Принято
Дата: 2026-09-27
Автор: Cursor
Затронутый EPIC: вне EPIC — точечное изменение матрицы прав
Связанные документы: ADR-0004, EPIC-003, `domain/permissions.py`, ТЗ §4.1

## Контекст

Текущая матрица (`domain/permissions.py`): роль «Наблюдатель» (`RoleCode.OBSERVER`)
имеет только `VIEW_EMPLOYEES`, `VIEW_STATUSES`, `VIEW_DIRECTORIES`,
`VIEW_STANDARD_REPORTS`, `USE_ACTIVE_REPORT_TEMPLATES`.

`Permission.MANAGE_STATUSES` выдано только администратору и сотруднику HR.

`StatusAssignDialog` и `StatusHistoryService` уже проверяют
`Permission.MANAGE_STATUSES` через `has_permission` / `_require` — отдельной
гранулярной модели прав нет.

Операционная потребность: наблюдатель на площадке должен фиксировать смену
статуса (офис / удалёнка / больничный и т.п.) без привлечения HR/администратора,
сохраняя запрет на карточки сотрудников (редактирование), справочники, импорт,
бэкапы и прочие права управления.

Это меняет матрицу прав относительно ТЗ §4.1 → по `ANCHOR_PROTOCOL.md` §4
обязательна ADR до реализации.

## Рассмотренные варианты

1. **Оставить как есть (только VIEW)** — наблюдатель не может выполнять базовую
   операционную фиксацию статусов; UX-потребность не закрыта.
2. **Выдать `MANAGE_STATUSES` роли Наблюдатель (минимальное расширение)** —
   закрывает UX-потребность, не открывая остальных прав.
3. **Отдельное гранулярное разрешение или «гибкие роли»** — отклонено:
   `ANCHOR_CORE.md` §6 явно выносит гибкую настройку прав внутри ролей за рамки
   текущей версии; усложняет модель без необходимости.

## Решение

Принят вариант 2. Добавить `Permission.MANAGE_STATUSES` в frozenset `_OBSERVER`
в `domain/permissions.py`.

Это намеренное точечное отклонение от исходной матрицы ТЗ §4.1, зафиксированное
настоящим ADR.

Все прочие права Наблюдателя **не меняются**. Не выдаём
`MANAGE_EMPLOYEES`, `IMPORT_EXPORT`, `MANAGE_DIRECTORIES`, `CREATE_BACKUP`,
чувствительные поля и т.д. Новых кодов `Permission` не вводим.

UI и сервисы уже опираются на `has_permission` / `AuthorizationService.check` —
дополнительные жёсткие проверки `role == "observer"` не вводим.

## Последствия

- Наблюдатель может открыть `StatusAssignDialog` и успешно вызвать
  `assign_status` (тот же confirmation flow и аудит, что у HR).
- Журнал действий пользователей продолжает писать запись от текущего
  пользователя (уже реализовано).
- `ANCHOR_CORE` A6 / §6: ссылка на этот ADR как на допустимое точечное
  исключение из исходной матрицы ТЗ §4.1; «гибкие права» в общем виде
  **не** открываются.
- Тесты матрицы прав должны отражать новое поведение.
- Документация / ROADMAP: краткая пометка при необходимости.
- Миграция схемы БД не требуется.

## Как проверяется

- Unit-тесты `permissions_for` / `has_permission` для `RoleCode.OBSERVER`:
  `MANAGE_STATUSES == True`; все прочие `MANAGE_*` == False.
- Существующие тесты `StatusHistoryService` / `StatusAssignDialog` с ролью
  наблюдателя — перестать ожидать `AuthorizationError` / disabled Save при
  назначении статуса.
- Ручная проверка: под наблюдателем кнопка «Назначить» активна, поля
  редактируемы, назначение успешно, в `user_action_log` есть запись.
