# Верификация статуса эпика в ROADMAP

Дополнение к [`ANCHOR_PROTOCOL.md`](ANCHOR_PROTOCOL.md) §7 (пункт про обновление
`ROADMAP.md`). Применяется, когда PR **только документирует** прогресс или
закрытие эпика в `docs/ROADMAP.md` (в том числе после merge функциональных PR
в `origin/master`).

Принцип: **утверждение в ROADMAP должно быть проверяемо по артефактам в
`origin/master`**, а не по памяти чата или названию вкладки из старого текста
эпика.

---

## Когда обязательно

- Меняется строка эпика в сводной таблице «Статус реализации».
- Меняется блок эпика: «Статус», «Реализовано», «Осталось», **DoD / трассировка**
  (в том числе чек-листы `[x]` / `[ ]`).
- Закрытие эпика (✅) или снятие «В процессе» без полного DoD.

Не подменяет ADR-триггеры и не отменяет diff-first для кода.

---

## Режим работы (docs-only)

- Ветка от verified `origin/master` (см. [`CURSOR_GIT_COORDINATION.md`](CURSOR_GIT_COORDINATION.md)).
- **Меняется только** `docs/ROADMAP.md`, если задача — исключительно статус;
  процессный документ (этот файл) и скрипт проверки — отдельные `docs/` / `scripts/`
  PR по согласованию с тимлидом.
- Без amend и force-push; правки после ревью — **новым коммитом** поверх ветки.
- Cursor **не мержит** PR со статусом ROADMAP.

---

## VERIFY → FIX → REPORT

### 1. UI (если эпик про диалог, вкладки, кнопки)

1. Прочитать реализацию (например `src/ui/*_dialog.py`).
2. Зафиксировать **каждый** заголовок вкладки верхнего `QTabWidget` (`addTab`
   второй аргумент) и вложенных вкладок, если есть.
3. Явно ответить: существует ли вкладка с заявленным именем **на верхнем
   уровне** (частая ошибка — путать название из скоупа эпика с фактическим UI).
4. По матрице ролей в коде (`RoleCode`, `has_permission`, helpers visibility)
   перечислить, какие **верхнеуровневые** вкладки видят Администратор, HR,
   Наблюдатель (если диалог для роли недоступен — «вкладок нет», не выдумывать).

### 2. DoD: видимость по ролям (тесты)

Файл(ы) тестов — из DoD эпика или по имени компонента (`tests/unit/test_*`).

Для **каждой** роли из ROADMAP (обычно Администратор, HR, Наблюдатель):

| Роль | Имя тест-функции | Что доказывает |
|------|------------------|----------------|
| … | `test_…` | … |

Разделять:

- **(a)** видимость/содержимое **внутри** целевого диалога (вкладки, виджеты);
- **(b)** видимость **точки входа** на главном экране (кнопка, пункт меню).

**Правило:** тест **(b)** для Наблюдателя **не** засчитывается как выполнение
DoD «видимость вкладок по каждой из трёх ролей» в диалоге. Если для роли нет
**(a)**, пункт DoD остаётся `[ ]` с явной формулировкой ограничения (имена
тестов и что именно покрыто).

### 3. DoD: перенос функции (например бэкап)

Перечислить **точные** имена тестов, которые проверяют встроенный UI (create,
restore, права кнопок, отсутствие виджета у роли без доступа). Отметить `[x]`
только если эти тесты есть в `origin/master` и соответствуют формулировке DoD.

### 4. Документация (`docs/manual/*`)

Обойти **все** файлы в `docs/manual/`, не только administrator-guide и runbook.

По каждому релевантному совпадению (бэкап, восстановление, «Работа с базой
данных», transport, 💾):

- **файл:строка**;
- **полное предложение(я)** из manual (без сокращений в отчёте ревью);
- классификация:
  - **новое расположение** (например 💾 → «Работа с базой данных» → вкладка X);
  - **старое расположение** (⚙ в шапке и т.п.);
  - **ни то ни другое** (упоминание бэкапа без навигации по UI).

В ROADMAP:

- `[x]` — перечислить файлы с **подтверждённым** новым путём;
- `[ ]` — файлы с упоминанием темы **без** навигации (не называть файл
  «устаревшим», если в нём нет старого пути — только «без навигации по UI»).

Отдельные незакрытые пункты manual (например transport для администратора)
привязывать к issue, как в эпике (#137 и т.д.).

### 5. Правки `docs/ROADMAP.md`

- Таблица статусов: не завышать («Завершён» при открытом скоупе); имена вкладок
  — как в коде.
- Блок эпика: «Статус» — кратко (для крупных эпиков допустимо **ровно два
  предложения**: сделано в master; остаток).
- DoD: чек-лист только с обоснованием (имена тестов, файлы manual); снятые
  `[x]` — с объяснением в том же пункте.
- Не менять другие эпики и чужие разделы roadmap.

### 6. Валидация перед push

```bash
git diff --stat origin/master...HEAD   # ожидаемо только docs/ROADMAP.md для status-PR
git diff --check
python scripts/check_roadmap_markdown.py
```

### 7. Отчёт (PR или комментарий ревью)

Без многоточий в доказательной части:

- фактические заголовки вкладок и поведение по ролям;
- таблица тестов (a)/(b) по ролям;
- список тестов бэкапа/restore;
- manual: file:line + полный текст + классификация;
- полный `git diff` к `origin/master`;
- SHA коммита, `git status`, CI PR при наличии.

---

## Definition of Done (status-PR)

- [ ] `git fetch`; база — verified `origin/master`.
- [ ] VERIFY по §1–§4 выполнен; расхождения исправлены в ROADMAP.
- [ ] Diff только в разрешённых файлах задачи.
- [ ] `git diff --check` и `scripts/check_roadmap_markdown.py` — PASS.
- [ ] PR: что изменилось, почему, ссылки на issues; **не** merge агентом без
      явной команды человека.
